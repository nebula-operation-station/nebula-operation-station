# Milestone 0: implementation status

Milestone 0 (security prototype) is implemented and its acceptance criteria are covered by tests in `test/security/`. This page records what exists, where it deviates from or sharpens the specification, and what must be done before later milestones rely on it.

## Decisions taken during implementation

These sharpen the spec without changing its architecture. Each is a candidate for an ADR if contested.

1. **`request_version: 1`** is part of the canonical request, so a future change of the canonical form cannot collide with old digests.
2. **Set semantics in the canonical form.** `credential_refs` and `resolved_targets` are sorted before encoding. Order carries no meaning (stage assignment is bound through `stage_plan_hash`).
3. **Execution IDs are single-use.** Re-proposing an execution ID with different content is rejected (`execution_id_reused`). Identical re-proposal returns the live permit; once the permit is gone (expired, discarded, revoked by Lock) the ID is spent and a new execution must be created.
4. **Browser approval needs an active privileged session** for every risk class, not only LOW. The CLI path does not need one; the admin UID on the executor host is the authentication.
5. **Lock revokes all permits**, not only the privileged session. Locking means stop.
6. **The server role may call `Lock`.** Locking only removes capability, so the web UI's "Lock executor" works without a CLI.
7. **Three failed approvals discard a pending permit.**
8. **CLI-only permits expose no browser challenge.**
9. **Root is never an admin.** Admin users are personal accounts and must be members of the socket group `nebula-rpc`.
10. **Unlock is all-or-nothing with one passphrase.** Unencrypted, group-readable, symlinked or weak (RSA < 3072) key files are refused.
11. **One parameters hash, one meaning.** Parameters are sent with the proposal, must hash to `parameters_hash`, and the executor keeps the RFC 8785 form. Duplicate keys are rejected, and numbers must already be canonical and exactly representable (`1.0`, `1e0`, `-0`, `9007199254740993` are rejected). `nebula approve` shows the full canonical parameters with control and bidi characters escaped.
12. **Unknown UIDs are dropped during the handshake**, before any request is read; the per-method table then applies to known UIDs. Clients (`nebula`, `nebula-server`) verify that the socket is served by the executor's UID before sending anything.
13. **Keys:** only OpenSSH-format private keys (bcrypt KDF) are accepted; a Lock issued while an Unlock is decrypting wins.
14. **Lint toolchain:** staticcheck 2026.2.1 cannot read Go 1.27 export data yet, so `make lint` runs it under Go 1.26.9. The module requires Go 1.26.
15. **`executor.db` stores only what makes the executor stricter** (H02): spent execution IDs and WebAuthn signature counters. Permits, approvals and the privileged session are never written to disk, so every restart starts locked, with no permits and no session. A crash or restart is a revocation. This narrows spec 03 and 05, which list permits and session state among the contents of `executor.db`. Since H01 it also holds the admin's risk data (decisions 20 to 23), which can lower a minimum below HIGH; losing it falls back to HIGH (see decision 23).
16. **Durable before visible.** An execution ID is bound in `executor.db` before `Propose` returns a permit, and a new signature counter is stored before `Verify` reports success. If the store fails, the call fails closed with `storage_error`; the detail goes to the audit log only, and a counter that cannot be stored does not count as a failed approval.
17. **Counters never go down.** The stored counter only rises (`ON CONFLICT … WHERE excluded.sign_count > sign_count`); at startup each credential starts at the higher of the credential file and the store, so neither a stale credentials file nor a lost row can lower it.
18. **One executor per data directory.** `executordb.Open` holds a non-blocking `flock` on the data directory for the life of the process, so a second executor on the same directory refuses to start, independent of SQLite's connection handling. SQLite runs on one connection with `locking_mode=EXCLUSIVE` (set before WAL, so there is no `-shm` file), WAL and `synchronous=FULL`. The data directory must be an absolute path. The file is created `0600` with `O_EXCL|O_NOFOLLOW` and checked with `fsguard`, as is the `-wal` file; a looser or foreign-owned file is refused, never repaired. Migrations are embedded, forward-only, one transaction each; a database from a newer version is refused.
19. **Retention:** spent execution IDs are pruned at startup 30 days after their request expired. The cutoff never passes the newest stored `bound_at`, so a clock that jumps forward at boot cannot prune live IDs. Expired requests are rejected by `canonical.Canonicalize`, so a pruned ID can only return inside a new request with a new expiry, and that needs a fresh approval like any new execution.
20. **The executor's risk floor (H01).** A proposal whose `risk_class` is below the executor's minimum is rejected with `invalid_request`, naming only the minimum level; the reason goes to the audit log. A higher `risk_class` is kept. The action floor is the risk an admin declared with `nebula artifact trust` (the executor hashes the file itself). It counts only if the artifact is trusted for exactly this (`action_id`, `module_version`), and it is the highest level the same bytes are trusted at under any action, because the server chooses which action it presents. An untrusted artifact is HIGH (spec 10: unverified scripts running as root are at least HIGH; the executor cannot know whether a script runs as root).
21. **Host criticality is bound to the pinned key.** A host record (`nebula host criticality HOST FINGERPRINT LEVEL`) counts only for a target whose host ID and key fingerprint both match; `host_id` alone is a name the server chooses, so a critical host's key under a harmless name is unrecorded. A key belongs to one record (hosts that share a host key, such as clones, cannot both be recorded and stay HIGH). For actions above LOW the host floor is the recorded criticality, or HIGH without a matching record; a record that shares only the host ID or only the key can raise that floor, never lower it, so a CRITICAL host presented under another of its keys stays CRITICAL. LOW actions are read-only by declaration: they stay LOW on hosts recorded LOW to HIGH and need MEDIUM (a WebAuthn tap) on CRITICAL or unrecorded hosts. The floor is the maximum over action and targets.
22. **Re-checked per host run.** `AuthorizeRun` computes the minimum for the host being run; if trust was withdrawn or the host became more critical after approval, the run is denied with `risk_above_approval` and the host stays unused. Rejected proposals never consume their execution ID.
23. **Only the admin role reads or changes risk data**, through `TrustArtifact` (with the CLI's expected hash, so nothing is stored if the hashes differ), `UntrustArtifact`, `SetHostCriticality` (an explicit `clear` removes a record; a missing level is rejected) and the two list methods. The server learns only the minimum level of its own proposals. Every change is audited with the caller's UID. Losing these rows makes everything HIGH, which also lowers a CRITICAL record or artifact to HIGH: `executor.db` belongs in the backup.
24. **Unknown floor fails closed.** If the risk data cannot be read, Propose and AuthorizeRun fail with `storage_error`; the detail stays in the audit log.
25. **Every registration needs a one-time code from the executor host (H03).** An admin creates it with `nebula webauthn code` (100 bits, 15 minutes, single use; five wrong attempts invalidate it) and types it into the browser. The first credential needs only the code. Once a credential is registered, a further one also needs a user-verified assertion by a registered credential over a challenge that belongs to this registration (spec 05). Whether a confirmation is needed is checked again at `FinishRegistration`: a registration begun as "first" is rejected if another one finished in between. The browser alone can never add a credential: a compromised server cannot turn one hijacked authenticator gesture into a permanent key of its own. Recovery after losing every key: remove the lost credentials with `nebula webauthn remove`; then the code alone suffices.
26. **The executor verifies the attestation itself** with go-webauthn: challenge, origin on the allowlist, no cross-origin or top-origin use, RP ID hash, user presence and user verification, algorithm ES256, EdDSA or RS256, and the attestation statement. It also checks the key itself: P-256, Ed25519, or RSA with at least 2048 bits. Attestation conveyance is `none`; authenticator models are not restricted (no metadata service). The public key and the initial signature counter are stored together in one transaction, only in `executor.db`.
27. **Each registration is single-use.** `FinishRegistration` consumes the pending registration before verifying anything, so a failed, replayed or raced attempt needs a new `BeginRegistration` (and on the code path a new code). At most four registrations may be pending; each expires after five minutes.
28. **Removing a credential deactivates it immediately and locks the executor** (privileged session ended, permits revoked, outstanding code and pending registrations cancelled), because a credential is removed when it may be lost or compromised. `nebula lock` also cancels pending registrations. Removal is serialized with registrations. The row is deleted from the store first; the credential is deactivated in memory even if that fails, but then the RPC fails with "removal was not stored" (audited as `credential_removal_not_stored`), because the credential would be active again after a restart until the removal is retried. Its signature counter is kept, so a re-registered credential cannot start lower. `nebula webauthn list` prints full credential IDs and `remove` prefers an exact match, because authenticators choose their IDs and a prefix could be made to collide.
29. **`webauthn-credentials.json` is imported once.** At startup the Milestone 0 file is imported into `executor.db` and renamed to `*.imported`, so a credential removed later cannot return from it.
30. **Host keys are pinned on the executor host only (H05).** `nebula host pin` probes every endpoint (the handshake is aborted once the host key is known, so no user name or credential is sent), refuses if the endpoints present different keys, shows the fingerprint and pins only after the admin typed `yes`; `--known-hosts` imports exact (plain or hashed) entries instead, never wildcards, never `@revoked` keys, and refuses a file with a line it cannot parse. The server can list pins but cannot probe, pin, unpin or test. One key belongs to one host: cloned VMs must be re-keyed.
31. **Endpoint rules (spec 08) are decided in `internal/sshtransport`.** TCP failure: next endpoint. Handshake failure before the host key: next endpoint, at most once per connection. Host key differs from the pin, or the host offers no key of the pinned type: hard stop. Host key matched, then authentication failed: hard stop; no other endpoint sees the key. Before pinning the client prefers ed25519, ECDSA, `rsa-sha2-512`; after pinning it offers only the pinned type. Keys below RSA 2048 and non-standard types are refused. Connect 10 s, keepalive every 15 s, dropped after 4 missed replies. The host's banner is never shown.
32. **A host key mismatch blocks the host** in `executor.db` (first mismatch recorded with the presented fingerprint and endpoint; survives restarts) and is logged as `host_key_mismatch`. Every connection to a blocked host is refused before any traffic until the admin re-pins it (`nebula host unpin`, which must name the current fingerprint, then `nebula host pin`). An authentication failure is logged but does not block.
33. **Each host binds one SSH user and one keyring reference** at pin time (default `nebula` / `nebula-default`); only that key is offered. `Connect` also takes the fingerprint a permit names for the target and refuses before any traffic if it is not the pin.
34. **Host criticality follows the pin.** For a pinned host, `nebula host criticality HOST LEVEL` binds the record to the pinned key, and a different fingerprint is refused. Unpinning leaves the record; it no longer matches once another key is pinned, so the host counts as HIGH until the admin sets it again.
35. **Web login is verified by the executor (M2).** `BeginLogin`/`FinishLogin` (server role) run a WebAuthn assertion with user verification against the credentials in `executor.db`; the challenge is single-use (2 minutes, at most 32 pending) and the counter is checked as for approvals. The server keeps no credential store of its own and only creates its web session after `FinishLogin` succeeded. A login grants nothing on the executor; removing a credential (or `nebula lock`) cancels pending logins.
36. **Web sessions (M2, `internal/web/auth`).** After `FinishLogin` the server stores only the SHA-256 of a 256-bit session token in `server.db` (migration 0003). Cookie `__Host-nebula_session`: Secure, HttpOnly, SameSite=Strict, Path=/. Idle timeout 24 h, absolute 14 days; logout deletes the row. Every path except `/login`, `/setup`, their JSON endpoints and `/static/` needs a session (GET redirects to `/login`, anything else gets 401). The security middleware checks the Origin of every state-changing request first. `/setup` is public on purpose: the executor requires the one-time code, and for further keys an assertion by a registered key. Browser-facing errors are fixed texts; executor details go to the server log. Login and setup pages load `webauthn.js` plus their own script; no inline script (CSP). Pages send state-changing requests with `fetch` or htmx, never plain HTML forms: under `Referrer-Policy: no-referrer` a form POST carries `Origin: null` and the origin check rejects it (found by the browser test of the login flow).
37. **Privileged session and lock from the dashboard (M2).** With a web session, the dashboard opens the executor's privileged session (`BeginPrivilegedSession` now also returns request options with the registered credentials; `CompletePrivilegedSession` still requires a user-verified assertion, verified by the executor) and locks the executor (`Lock`: session ended, permits revoked, keys wiped). The web session alone opens nothing.
38. **Removing a credential ends its web sessions (M2).** The server asks the executor (`CheckCredential`, server role) at most every 5 minutes per session whether the session's credential is still registered; if not, the session is deleted and the browser sent to the login. If the executor cannot be asked, the session stays (it only reads; every privileged action is verified by the executor) and the check repeats on the next request.
39. **TOTP recovery (M2, spec 05).** `nebula totp setup` (executor host, admin) creates a 160-bit secret, shows it with an `otpauth://` URI and activates it only after one current code is typed back. The web login page offers "Lost your security key?": `RecoveryLogin` (server role) checks the code (RFC 6238, SHA-1, 6 digits, ±1 step), every code works once (last step in `executor.db`), and five wrong codes within 15 minutes block further attempts for the rest of the window. A successful recovery ends the privileged session, revokes every permit and sets a persistent recovery state: until a new WebAuthn credential is registered (one-time code from the executor host, and confirmation by a registered key if any are left), `BeginPrivilegedSession`, `CompletePrivilegedSession` and `SubmitAssertion` are refused and the dashboard says so. The recovery web session reads only and ends when TOTP is removed. The secret is stored unencrypted in `executor.db` (0600, executor user) until the vault exists. `nebula approve` on the executor host is not affected. A new key ends the recovery automatically only if a registered key confirmed it; a key registered with the one-time code alone (all keys lost) keeps the recovery pending until the admin picks it on the executor host with `nebula totp finish-recovery` (it lists the keys registered since the recovery login and needs the typed ID prefix), because a compromised server sees the code the admin types and could register its own key. A recovery login also cancels registrations in progress, like `Lock`. If the executor cannot read the TOTP state, `CheckCredential` answers with an error, so the server keeps the recovery session instead of ending it.
40. **Enrollment helper (M3, spec 08).** `nebula host enroll-script --from ADDR[,ADDR]` asks the executor for Nebula's public key (`GetSSHPublicKey`, admin role, keyring unlocked; the private key never leaves the executor) and prints a POSIX sh script for the admin to review and run as root on the new host: it creates the `nebula` user, adds the key idempotently with `from="<addresses>",no-agent-forwarding,no-port-forwarding,no-X11-forwarding` (0700/0600), writes `/etc/sudoers.d/nebula` (NOPASSWD, checked with `visudo -cf`; skipped with `--no-sudo`) and `/etc/tmpfiles.d/nebula.conf`, and prints the host key fingerprints for `nebula host pin`. Nebula never logs in with a password. All interpolated values are validated (IPs/CIDRs only, user name, key reference) and the key is re-encoded, so nothing can break out of the script's quoting.
41. **Vault (M2, spec 06, `internal/vault`).** `nebula vault init` (admin) creates a 256-bit master key, wrapped with XChaCha20-Poly1305 under a key derived from the passphrase with Argon2id (stored parameters, default 256 MiB, 3 passes, 4 lanes; passphrase at least 32 characters). Each secret (`nebula secret set ID`, value from the terminal or stdin, never argv) gets its own data key; data key and value are sealed with the secret's ID and version as associated data, so blobs moved between records or versions do not decrypt (tested). Only ciphertext is stored (`executor.db` migration 0006). `nebula unlock` tries one passphrase on the SSH keys and the vault and asks again only for the part it did not fit (`UnlockScope`); `Lock` drops the vault key with the SSH keys. Admin role only; no RPC returns a value (an acceptance test checks the service for reveal-style methods and bytes fields in the responses). Values are decrypted only inside the executor (`Vault.Open`, for Milestone 4 runs). Init and unlock are serialized so parallel calls cannot multiply the Argon2id memory. Parameters below 3 passes and 256 MiB are refused at init and when read back from the database (an offline attacker with a copy of `executor.db` guesses at their cost); the database CHECKs only bound them, tests lower the floor through `SetVaultParams`. A Lock during an unlock wins, as in the keyring: the derived key is dropped. `nebula secret set` strips one CRLF or LF from stdin; a lone trailing CR is part of the value.
42. **The TOTP secret stays outside the vault.** TOTP recovery is for a lost security key and must work while the executor is locked (after a reboot, before `nebula unlock`); sealing the secret under the vault key would make remote recovery impossible exactly then. It stays in `executor.db`, readable only by the executor user, like the WebAuthn credentials. Revisit if the threat model changes.
43. **Host key mismatch notifications (spec 13, first provider set).** `internal/notify` sends to a generic webhook (JSON; `X-Nebula-Signature: sha256=HMAC(secret, timestamp + "." + body)` with `X-Nebula-Timestamp`), ntfy (urgent priority, optional bearer token) and Telegram (plain text, no parse mode). Providers are configured under `notifications` in `server.json`; a config with any token must not be readable by others (0600 or the installer's 0640 root:nebula-server), else the server refuses to start. Tokens use the redacting `Token` type, request errors are reported without the URL (the Telegram token is part of it), and redirects are not followed. The server polls the executor's pins every 30 s (server role `ListHostKeys`) and delivers each block once to every provider (`server.db` migration 0004, one row per provider); a provider that failed is retried on each poll until it accepts, without repeating the block to the others, a re-pinned host is forgotten so a later block notifies again. Host text is reduced to printable characters and bounded. `nebula-server -notify-test` sends a test message. Other events (Ops State, executions, gates, executor locked) follow with Milestone 4.
44. **Attached runs (M4-1, spec 07, `internal/hostrun`).** `RunAttached` (server role) authorizes one host run like `AuthorizeRun` and runs it on the pinned host. Checks that need no permit come first (endpoints, timeout, keyring unlocked, host pinned and not blocked, the pin's credential equals the run's credential and is loaded), so a refused request does not use up the host. After `AuthorizeGrant` the host is used whatever happens, and every outcome is a response class (spec 07 error classes), never a retry with the same permit. The remote command is fixed: a POSIX sh bootstrap, with only the execution ID (a validated UUID) interpolated, reads one base64 line of parameters and then the script from stdin into a private `mktemp -d` directory (umask 077, removed on exit) and runs the script with `/bin/sh` as the SSH user, stdin from `/dev/null`, `NEBULA_PARAMS` and `NEBULA_EXECUTION_ID` in the environment. The parameters are the canonical bytes the executor kept from the proposal (`permit.Grant`), never the bytes of the run request. Nebula never adds `sudo`: a script that needs root calls `sudo -n` itself, and NOPASSWD sudo counts as root (spec 08). stdout must be exactly one UTF-8 JSON document of at most 1 MiB; stderr is the log, cut at 10 MiB with a visible marker. Timeouts default to 60 s, at most 600 s; longer work is a durable job.
45. **Durable jobs and reconciliation (M4-2, spec 07).** `StartDurable` (server role) makes the same checks as `RunAttached`, authorizes, and records the run in `executor.db` (migration 0007, state `dispatching`) before anything goes to the host. Dispatch is one fixed program via `sudo -n` (job directories are root's, enrollment creates the tmpfiles rule): it creates `/var/lib/nebula/jobs/<execution-id>/` with mode 0700 and refuses if it exists (so a job never starts twice), writes `action.sh`, puts the parameters into `/run/nebula/<execution-id>/params.json` (tmpfs, removed when the script ends) and starts a fixed wrapper with `systemd-run --collect --unit=nebula-job-<id> --property=RuntimeMaxSec=<timeout>`. The wrapper records `running` with its PID and the boot ID, runs the script (stdout to `result.json.tmp`, stderr to `execution.log`), syncs and renames `result.json`, and writes `finished` with the exit status (write `.tmp`, sync, rename). The job directory holds only `action.sh`, `state.json`, `result.json` and `execution.log`. The executor afterwards only reads: a reconciliation pass (every 15 s, only while unlocked, also for runs left open by an earlier process) reads `state.json`; `finished` → collect result and log with the attached-run limits and classes, store, remove the job directory; `running` with a dead PID or another boot ID → `script_interrupted` (or `execution_timeout` past the timeout; the check reads `state.json` again after a failed PID probe, so a job that finishes during the check keeps its result); a missing directory → `not_executed` if the dispatch never completed, otherwise `unknown`; stored but never started for 5 minutes → `not_executed`. Nothing is ever dispatched again. `GetRun` (server role) reports a run; with `release` the result and log are dropped from `executor.db` after the answer.
46. **Operations from the web UI (M4-3, `internal/executions`).** The server plans an operation of a built-in action (first: `core.facts` 1.0.0, read-only, base64-wrapped output) on hosts: endpoints come from the inventory, fingerprint and credential from the executor's pins (hosts that are missing, not enrolled or blocked are refused). It proposes with `raise_to_minimum`, so the executor's minimum decides the risk (a built-in script the admin has not trusted is at least HIGH) and the page shows the decided class. Browser approval uses the request options the executor now returns with the permit (`ProposeExecutionResponse.request_options_json`); the server only relays the assertion. Once approved, the server starts the host runs (at most 4 in parallel; attached via `RunAttached`, durable via `StartDurable` + `GetRun` polling; the result is stored before a second `GetRun` releases it, so a lost response never loses it) and keeps outcomes in `server.db` (migration 0005). After a server restart approved operations resume; attached runs that were in flight are shown as `unknown` (the executor never re-runs them). Result and log are rendered as text, the first 64 KiB each; `core.facts` results are decoded into a table of printable values.
47. **os-debian: update check and refresh (M5-1, spec 10/11).** Built-in actions `package.list_updates` 1.0.0 (read-only: `apt-get -s` with `Debug::NoLocking`, `upgrade` or on Proxmox `dist-upgrade`, no root; plus `/var/run/reboot-required(.pkgs)` and the age of the package lists) and `package.refresh` 1.0.0 (`sudo -n apt-get update`, waits up to 8 minutes for the apt lock inside the 10-minute attached run). The host returns raw apt output base64-wrapped; the server parses it (`internal/executions/osdebian`) with a strict line format, size and count limits: a package is a security update if one of its archives is a security archive (`-security`, `Debian-Security`), a kernel update by package name. The latest result per host is kept in `server.db` (migration 0006) and shown in the inventory (security/total, kernel, reboot required, time) and as a table on the operation page.
48. **os-debian: installing updates (M5-2, spec 11).** `package.install_security` and `package.install_all` 1.0.0 are durable jobs (they run as root in the job unit). Prechecks: at least 500 MB free on `/` and `/var`, the job directory's filesystem writable, `dpkg --audit` clean; a failed precheck exits 10 and the executor reports `precheck_failed` (adapter convention; exit 11 is `postcheck_failed`), with the reason in the result. Security updates are the packages whose new version comes from a security archive, installed with `apt-get install --only-upgrade`; "install all" is `apt-get upgrade`, on Proxmox VE `full-upgrade`. apt runs with `DEBIAN_FRONTEND=noninteractive`, `--force-confold` and `DPkg::Lock::Timeout=600`; a lock still held after that ends as `precheck_failed`. Postchecks: `dpkg --audit` (not clean → `postcheck_failed`), reboot required, systemd units that failed since the start (shown as a WARNING), running Docker containers. No reboot. A finished install marks the host's stored update list as stale. The security package list comes from the host's own apt simulation, so every name must be a plain Debian package name (optionally `:arch`) before it reaches the root `apt-get` as a separate argument (no globbing); anything else ends as `precheck_failed` with nothing installed. A held lock is `precheck_failed` only if the installed package set did not change (`dpkg-query` fingerprint before and after), so host-controlled stderr text cannot hide an install that happened.
49. **Reboot (M5-3, spec 11).** `system.reboot` 1.0.0 is a durable job that schedules `systemctl reboot` 15 seconds later (`systemd-run --on-active`) and returns `{"await_reboot":true,"boot_id":<current>}`. Any successful durable result of that form makes the executor keep the run open (`executor.db` migration 0008) after collecting it: later reconciliation passes connect (pinned key as always) and read the boot ID with a fixed read-only command; a new boot ID ends the run as `success`, the deadline (dispatch time plus the action's timeout, 20 minutes) as `host_not_returned`. No reboot happens after patching unless the operator runs this action.
50. **Ops State (spec 12/13).** After every finished host run the server derives the host's state from that run and the stored update list: a run that could not reach the host or the host not coming back → UNREACHABLE; any other failed run → WARNING; security updates or a required reboot → WARNING; otherwise READY; nothing run yet or not executed → UNKNOWN. A blocked pin shows as UNREACHABLE on the page whatever the last run said. The last state is kept (`server.db` migration 0007) and a change notifies once (worse or recovered), never a repeat; evaluations are serialized, so runs finishing at once on one host cannot report the same change twice.
51. **CSV import in the web UI (spec 12).** `/inventory/import`: the browser reads the file (at most 768 KiB, below the 1 MiB request limit) and sends its text with a column mapping (host ID, display name, environment, criticality, tags, endpoints 1–4) and defaults for an empty environment or criticality. The server parses it with `csvimport` (untrusted input) into a staging preview with per-row problems and whether the ID exists. Import sends only the selected row numbers; the server parses the file again and creates only rows without problems whose ID is free, so nothing the browser says about a row is trusted. One audit line per created host plus a summary. The file is never stored.
52. **Action parameters and service actions (spec 10).** An action declares its parameters with a strict pattern; the server refuses missing, extra or non-matching values before anything is proposed, stores the canonical parameter JSON with the execution (`server.db` migration 0008) and the executor hashes exactly those bytes into the permit, so an approved restart of `nginx.service` cannot run on another unit. The host script reads the unit again from `$NEBULA_PARAMS` with the same pattern (exit 10, precheck) and calls `systemctl <verb> -- <unit>`, so a value can never become an option. `service.list` and `service.status` are LOW read-only; restart, start, stop and reload are MEDIUM. `systemctl show` output is reduced to a fixed property allow-list and the journal to the last lines, all shown as text.
53. **Execution and executor notifications (spec 13).** An execution that finishes with failed hosts notifies once: WARNING if some hosts succeeded, FAILED if none did or the execution could not start; the message names the action, the counts and up to five hosts with their result class, never host output. A successful execution is not notified. The finishing update only matches an unfinished execution, so a resume cannot notify twice. The server polls the executor every 30 seconds and notifies a locked executor when it was unreachable before (an executor restart) or at server start; a Lock while the executor stays reachable is deliberate and not notified. A server restart with a locked executor notifies again.
54. **Retry classes (spec 07).** Every built-in action has a retry class: `safe` (facts, update check, package list refresh, service list and status, the Docker reads), `reconcile-first` (installs, reboot: durable jobs whose outcome the reconciler collects; never run twice) and `never` (service control). The executor marks a permit's host used when it authorizes the run; if the connection then fails with `network_unreachable` (every endpoint failed before the host key arrived, so no credential was offered and nothing ran), it releases the host again (`permit.ReleaseHost`, audited as `released`) and answers `retryable`. Spec 07 asks for "unused for this host", and the stage engine's Retry of an unreachable host needs it. A run that reached the host (any other class, including authentication failures) keeps it used. The server retries only `safe` actions automatically, twice (after 20 s and 1 min), within the permit's lifetime; other actions report `network_unreachable` and need a new operation.
55. **Re-pin from the web UI (spec 08).** A host blocked by a host key mismatch can be re-pinned to the key it presented from the dashboard. The server names only the host (`ProposeRepin`, server role); the executor builds the request from its own block record: the reserved action `nebula.host_key.repin` with a fixed artifact and the parameters host, pinned and presented fingerprint, endpoint, block time, SSH user and credential, at least HIGH (user verification; a CRITICAL host stays CRITICAL, hardened mode needs `nebula approve`). `ProposeExecution` refuses the `nebula.` action namespace, so the server cannot make such a permit itself. `CommitRepin` rebuilds the request from the current record (a host re-pinned or blocked anew meanwhile no longer matches the approval), uses up the approval, probes the recorded endpoint for a key of the pinned type (the type the block was recorded with) and pins only if it still presents the approved key, in one transaction that also moves the host's criticality record to the new key. A failed probe or a changed key changes nothing and needs a new approval. The dashboard asks the user to confirm that they compared the new fingerprint on the host's console. The authenticator still signs a challenge, not the text: `nebula pending`/`nebula approve` show the executor's parameters.
56. **Bulk enrollment from the web UI (spec 08).** `/inventory/enroll` lists inventory hosts without a pin. For the selected hosts (at most 50; endpoint one of the host's inventory endpoints, SSH user, credential `nebula-default`) the executor reads every host key itself (`ProposeEnroll`, server role; already pinned hosts, keys pinned elsewhere or shared within the list, unreachable endpoints and unloaded credentials are left out with a reason) and proposes the reserved action `nebula.host_key.enroll` with all hosts, endpoints, fingerprints, users and credentials as parameters, at least HIGH. After the approval `CommitEnroll` authorizes each host against it (a changed list no longer hashes to the approval), reads each key again (in parallel, at most 8 at a time) and pins only an unchanged key; with unlocked keys it then tries a login and reports it. UI-pinned hosts get no criticality record and count as HIGH: the server cannot lower a host's risk this way; an admin sets the criticality on the executor host.
57. **Read-only API (spec 13).** `/api/v1` is off unless `api.enabled` is set in `server.json` with at least one token. `nebula-server -api-token NAME:SCOPES` creates a random 256-bit token, prints it once and the entry for `server.json`, which holds only its SHA-256 (so the file holds no usable token). Requests need `Authorization: Bearer <token>`; every configured hash is compared in constant time; only GET and HEAD; no session cookie is accepted. Scopes: `inventory.read` (`/hosts`, `/hosts/{id}`: environment, criticality, Ops State, update summary), `operations.read` (`/operations`, `/operations/{id}`: action, state, classes, exit codes) and `execution_logs.read` (adds the operation's parameters and detail and the detail, result and log of each host run, as text, at most 64 KiB each, because host output and operator input can be sensitive). Every request is audited with the token name.
58. **Listing Docker containers (M8, spec 11).** `docker.list` 1.0.0 is a LOW read-only built-in action and the first part of Milestone 8. On a host without a `docker` command it succeeds with `"present":false`. Otherwise it uses `docker` directly when the SSH user is root or may use the daemon (the `docker` group, root-equivalent like NOPASSWD sudo, spec 08), else `sudo -n docker`; an unreachable daemon or refused access is a precheck (exit 10). It reports the server version and `docker ps -a --no-trunc` with a fixed tab-separated template: ID, name, image, state, status, ports and the Compose labels `com.docker.compose.project`, `.service` and `.project.working_dir` (spec 11 finds Compose stacks through them). The server keeps at most 2000 lines and only lines whose ID, name and state match strict patterns and whose other fields are single lines without control characters (C0, C1), bidirectional marks, embeddings, overrides or isolates, line separators or byte order marks; a malformed project name drops the Compose fields, not the container. Health comes from docker's status text. The operation page shows counts (running, stopped, unhealthy), the Compose projects and a table sorted by project and name. `docker.logs` 1.0.0 (LOW, read-only) takes one parameter, `container`, a name or ID matching `^[A-Za-z0-9][A-Za-z0-9_.-]{0,127}$` (no leading `-`, no spaces, quotes or slashes); the script reads it again with the same pattern and passes it after `--`. It reports the container state (`docker inspect --type container`; an unknown container is a precheck) and `docker logs --tail 100 --timestamps` with stdout and stderr, cut at 256 KiB. The server keeps the last 100 lines, at most 1000 bytes each, replaces invalid UTF-8 and the same unsafe characters as in the listing (but tab), and shows them as text. `docker.inspect` 1.0.0 (LOW, read-only, same parameter) reads one container through a fixed `docker inspect` template: ID, name, image and image ID, `.State` as a whole (docker's template fails on `.State.Health` for a container without a health check), restart count and policy, mounts, port bindings and networks, plus the image's `RepoDigests` (the current digest of spec 11). It never reads the environment, command line, entrypoint or labels, which often hold secrets; a test pins that. The server keeps only fields that match their pattern or set: image ID `sha256:<64 hex>`, digests `<repo>@sha256:<64 hex>` (at most 20), known states, restart policies, health states and mount types, absolute mount destinations, `<port>/<tcp|udp|sctp>` with numeric host ports and IP-literal host addresses, network names like container names; at most 100 mounts, 200 ports and 50 networks; other text fields are single safe lines. Container start/stop/restart, the registry digest check and Compose updates follow as separate actions. `docker.start`, `docker.stop` and `docker.restart` 1.0.0 are MEDIUM (decided 2026-10-15, like service control), retry class `never`, with the same `container` parameter: after the same access and existence checks they run `docker <verb> -- <container>` and report the state before and after (`docker-control-v1`), docker's output cut at 4 KiB, and exit with docker's status. Nothing is recreated or pulled (spec 11). `docker.check_updates` 1.0.0 (LOW, read-only, `safe`; decided 2026-10-15: on the host) compares, for the image of every running container (at most 50, `docker ps`), the local `RepoDigests` with the registry's digest for its tag: one `curl -I` manifest request with the manifest-list and OCI index media types (HEAD only, so nothing is pulled and Docker Hub does not count it), HTTPS only, no redirects, 5 s connect and 10 s total per request, no credentials. On a 401 it follows an anonymous Bearer challenge (only an `https://` realm, `service` and a `repository:<repo>:pull` scope; the token taken from `token` or `access_token` with a strict character set) and asks once more. Images pinned by digest are `pinned`; anything else that does not yield a `sha256:` digest is `unknown` with a reason. A registry the host can reach can steer the anonymous token request to another HTTPS URL; that is a request from the host, which already trusts what it pulls from that registry, carries no secret, and the answer is only scanned for a token. The server keeps lines whose image reference and status match strict patterns (a malformed digest makes the line `unknown`), at most 50. `docker.compose_update` 1.0.0 (MEDIUM, durable, `reconcile-first`, 30 min; spec 11 "manual Compose update") takes `project` (`^[a-z0-9][a-z0-9_-]{0,99}$`, Compose's own rule). As root in the job directory it finds the project by `com.docker.compose.project`, takes the working directory and config files from the first container's labels (absolute paths only, the files must exist; each file is one argument after `-f`), lists the project's containers (service, name, state, status, ports, image), runs `docker compose -p P --project-directory DIR -f … pull` and, only if that succeeded, `up -d`, waits up to 60 s while a health check is still starting, and lists the containers again. The server judges the two lists (postflight): FAILED if pull or up failed, fewer containers run, or a container that was healthy is unhealthy or starting; WARNING if a container is not healthy, a running service's published ports changed, or the number of containers changed; else OK. The list lines are kept only if name and state match strict patterns (at most 200).
59. **Stage engine, executor part (M6-1, spec 07).** A request may carry a stage plan (`stages-v1`, `internal/stageplan`): stages with name, hosts, `max_failed`, `max_unreachable`, `continue` (`manual` or `auto`) and `timeout_s`. The plan document is sent with `ProposeExecution` (`stage_plan_json`) and must hash (RFC 8785, SHA-256) to the request's `stage_plan_hash`; it must be exactly the form it decodes to (no unknown, missing or differently cased members), cover every target exactly once, and have 1 to 20 stages. Without a plan the hash must be that of `{"plan":"single-stage-v1"}` and the request is one stage of all targets, as before. A HIGH or CRITICAL plan cannot continue automatically (decision 2 of the M6 plan, checked after raising to the executor's minimum). The permit enforces the plan: `AuthorizeGrant` refuses a host whose stage is not open (`stage_not_open`), every host after a stage had more failed hosts than allowed (`rollout_stopped`, final) and every host after an abort (`rollout_aborted`). Stage 1 opens with the approval. The executor records each host's outcome from its own runs only (attached responses, durable results via `finishRun`): `success` succeeded, `network_unreachable` unreachable, anything else failed; failed and succeeded are final, unreachable is replaced by a retry of a released host (decision 54). Every open stage is re-checked on each outcome, so a host of an earlier stage that is retried after the stage passed and then fails still stops the rollout; release and the unreachable outcome are recorded in one step (`ReleaseUnreachable`), so no second run of the host can be authorized in between (both from the Hermes review). A stage passes when every host has an outcome and failed and unreachable are within the thresholds; skipped hosts count neither way. Gates (decisions 3 and 4): `BeginGate`/`CommitGate` (server role) open the next stage or skip a host of an open stage that has no outcome or was unreachable; LOW and MEDIUM need the privileged session, HIGH and CRITICAL also a user-verified assertion over a single-use challenge SHA-256(`nebula-gate-v1` 0 ‖ digest ‖ kind 0 ‖ stage ‖ host 0 ‖ nonce ‖ expiry), so an assertion opens only that gate of that rollout; hardened mode needs `nebula approve --stage N DIGEST` or `--skip HOST DIGEST` (`ApproveGateCLI`, admin), which shows the executor's view of the rollout first. A passing stage with `continue: auto` opens the next one by itself. `AbortRollout` (server role) needs no approval because it only takes permission away. `GetRollout` (server, admin) returns stages, outcomes, the open stage, a stop reason and what the next gate needs; `ListPending` includes the plan, and `nebula approve` prints it. Stage state lives with the permit and, like every permit, ends with a restart or a lock; the M6 plan's `executor.db` migration is therefore not needed. Every decision is audited (`outcome`, `stage_passed`, `stage_failed`, `stage_opened`, `host_skipped`, `aborted`).
60. **Stage engine, server part (M6-2, spec 07/13).** The planning page offers presets that the server turns into a `stages-v1` plan: canary (first N hosts in stage `canary` with no failures allowed, the rest in `rest`), waves of N (at most 20), and DEV → QA → PROD by inventory environment (a host without one is refused). Each stage allows the chosen number of failed and of unreachable hosts (capped at its size); `continue` is the chosen mode, and the last stage is always manual. A stage's `timeout_s` is the action timeout times the rounds of 4 parallel hosts plus 5 minutes; the permit expires after the sum plus an hour, at most just under 24 h. The plan document is stored with the execution (`server.db` migration 0009: `stage_plan`, `waiting`, `execution_hosts.stage`). The dispatcher of a staged execution asks the executor (`GetRollout`) and runs only the waiting hosts of open stages; it marks hosts the executor skipped as `skipped`, and every waiting host as `not_run` once the rollout stopped or was aborted, or `not_executed` once the permit is gone. While nothing can run it records what it waits for and notifies that once (`WAITING`, spec 13). The operation page shows the stages with the executor's view, a gate button (session for LOW/MEDIUM; the security key over the executor's gate challenge for HIGH/CRITICAL; the CLI command in hardened mode), Retry for an unreachable host of an attached operation in an open stage, Skip (a gate) and Abort (two clicks, no browser dialog). The server never decides a stage; buttons appear only from the executor's view. Skipped and not-run hosts change no Ops State, and skipped hosts do not count as failed in the finish notification. An execution whose hosts all have an outcome keeps running while the executor's open stage has not passed (an unreachable host over the threshold): it waits for a retry, a skip or an abort, or for the permit to end; an unreachable host skipped later becomes `skipped`. A retry lands only while the execution runs (one statement against the finish), and a start while the dispatcher runs makes it run once more.
61. **Schedule grants, executor part (decision 5 of the M6 plan, spec 01).** Scheduled read-only work runs under a standing grant (`docs/implementation/schedule-grants.md`, `internal/schedgrant`): a `read-schedule-v1` document with an ID, 1 to 10 actions (action, version, artifact hash, parameters hash), 1 to 100 targets (host and pinned key), `min_interval_s` (15 min to 7 days) and an expiry (1 hour to 90 days ahead), exactly in the form it decodes to. `ProposeScheduleGrant` (server role, privileged session) accepts it only if every target is pinned with that key and not blocked and the executor rates every action LOW on every target (the artifact trusted as LOW, i.e. read-only by the admin's declaration, and the host recorded at most HIGH); approval needs a user-verified assertion over SHA-256(`nebula-schedule-grant-v1` 0 ‖ digest ‖ nonce ‖ expiry) within 5 minutes (`CommitScheduleGrant`), or `nebula schedule approve` in hardened mode. The approved canonical document is stored in `executor.db` (migration 0009) and, unlike permits, survives a restart and a lock (runs still need the unlocked keyring); pending grants end with a lock. `RunScheduled` (server role) runs one attached host run with a fresh execution ID if the grant is active, covers the action, version, artifact bytes, parameters and the host with its pinned key, the action is still LOW there (trust withdrawn or criticality raised stops it), and the last run of that action on that host under the grant is at least the interval ago (claimed atomically before the run). `RevokeScheduleGrant` (server, admin) needs no approval; `ListScheduleGrants` (server, admin); `nebula schedule pending|approve|list|revoke`. Every step is audited.
62. **Scheduled checks in the server (decision 5 of the M6 plan).** `/schedules` proposes a schedule grant for read-only built-ins without parameters (the actions the UI offers) on enrolled, unblocked hosts, every hour, 6 hours, day or week, for 1 to 90 days (default 30); the server builds the `read-schedule-v1` document with the action's artifact hash and the hash of `{}`, the executor checks it (decision 61) and the browser approves it with the security key (or the page shows the `nebula schedule approve` command in hardened mode). `server.db` migration 0010 keeps the schedules (pending, active, revoked) and tags executions with `schedule_id`. Once a minute the scheduler runs, one at a time, every action of every active, unexpired schedule on every host whose last scheduled run of that action is at least the interval ago (`RunScheduled`); an executor refusal for the interval is skipped silently, other refusals are logged. Each run is stored as a finished execution of one host created by "schedule" and goes through the same result handling as any run (update lists, Ops State). Revoking calls the executor first. The server's schedule state follows the executor's grant where the two steps can part: an approval the executor already holds (the server missed its answer) is recorded on the next attempt from `ListScheduleGrants`; an approval that lands after a revoke is withdrawn again; Revoke also revokes on the executor for a pending schedule; and a run refused because the grant is unknown or revoked ends the schedule instead of retrying every minute.
63. **Safety Scanner (M7-1, spec 10).** `internal/scanner` is a fixed, versioned pattern list (`scanner-v1`) over a script's logical lines (continuations joined, full-line comments skipped): download and execute, `eval` or encoded payloads piped to a shell, destructive filesystem commands, bootloader changes are HIGH; users and groups, network and firewall, package removal, reboot or power, Docker removal are MEDIUM. Command words match only in command position (after a separator or wrappers such as `sudo -n`), so JSON keys like `reboot_required` do not count. The executor's minimum risk is max(risk policy, scanner): the permit authority scans bytes it hashed itself, at proposal when the server sends them (`ProposeExecutionRequest.artifact`, which must hash to `artifact_sha256`) and at every host run, where the bytes are always present; results are cached by SHA-256 (at most 1024). A proposal without the bytes is approved without the scanner's floor, and a run whose scan raises the floor above the approval is refused (`risk_above_approval`). The scanner applies to trusted artifacts too (decision 1 of the M7 plan): it can only raise, and a clean scan proves nothing. The server shows the same findings on the planning and operation pages (ASCII-quoted excerpts). The built-ins are pinned: only `system.reboot` has a finding (`reboot_or_power`, below its declared HIGH). The cost is bounded (review m71): the scanner reads at most 256 KiB and 5000 logical lines (the size of a runbook or module script) and reports `too_large_to_scan` (HIGH) for anything longer, and at most two scans run at once in the executor. Two-stage download-and-execute (`curl -o f … && sh f`), stopping or disabling SSH, `ifdown`/`nmcli … down`, and package removal with dnf, yum, zypper, rpm, pacman and apk count too. A logical line longer than 4096 bytes, of which only the start is matched, counts HIGH too (`too_large_to_scan`).
64. **Runbooks (M7-2, spec 10).** `internal/runbooks` stores runbooks in `server.db` (migration 0011): `runbooks` and `runbook_versions`; triggers refuse any UPDATE or DELETE of a version, and reading a version re-checks its hash, its validity and that the stored artifact is exactly what the version generates. A version is the action `runbook.<slug>` at `N.0.0`. Parameters are typed (decision 2 of the M7 plan): `name`, `int`, `path`, `choice`, each with a pattern written so Go's regexp and POSIX ERE read it alike. The artifact is a generated prelude plus the author's script as a shell function: the prelude extracts each value from the one-line canonical parameters (values cannot contain quotes or backslashes), checks it with `grep -Ex` and the same pattern (else `precheck_failed`, exit 10), exports `NEBULA_P_<NAME>`, runs the script in a subshell with stdin from /dev/null and stdout to the log, and prints the one result document itself (`runbook-v1`, the script's exit status). Scripts must be UTF-8 without control or Unicode format characters (no Trojan Source: what is reviewed is what runs), at most 256 KiB; attached timeouts 10 s to 10 min, durable up to 6 h; durable runbooks retry `reconcile-first`, attached ones `never`. The executions service looks actions up by ID and version (`Action`, `Catalog`), so an execution runs exactly its planned version; the executor treats the script like any other (untrusted: at least HIGH, plus the scanner). The UI lists runbooks, shows a version with its scanner findings, parameters, script and the `nebula artifact trust` command, serves the artifact as a download only (`application/octet-stream`, attachment, nosniff), and edits by saving a new version (`/runbooks/new?from=`). The slug `new` is reserved.
65. **Secret slots (M7-3, spec 06).** A runbook declares secret slots (migration 0012); planning maps each to a vault secret ID, and the mapping is the reserved member `nebula_secrets` of the parameters document, so it is hashed into the approval (runbook parameter and slot names may not start with `nebula`, and a slot may not share a parameter's name). The executor validates the mapping at proposal (1 to 8 slots, slot and vault ID patterns) and raises its minimum risk to MEDIUM for any run that uses secrets (decision 4 of the M7 plan); scheduled runs with secrets are refused. Before a run uses its permit's host, the executor opens each secret from its vault (`vault_locked` / `secret_unavailable` otherwise, nothing reserved); the values go to the host on the SSH channel only, after the parameters line, as `N` and `slot base64` lines read by fixed bootstrap text. Attached runs store them in a new private directory under `$XDG_RUNTIME_DIR` (must be a tmpfs; systemd-logind removes it when the user's last session ends), durable jobs in `/run/nebula/<id>/secrets` (removed with the run directory when the script ends; a failure while reading removes the job). Scripts get `$NEBULA_SECRETS_DIR`; the runbook prelude checks each slot's file and exports its path as `NEBULA_SECRET_<SLOT>`, never the value. Known values (4 bytes or more) are replaced in the log and result as an extra safeguard: for attached runs at once, for durable runs when the executor collects them (the run records its slot → secret ID mapping, executor migration 0010, never a value; with the vault locked the job waits on the host, and output whose secret can no longer be opened is withheld). Cleanup after review m73: a killed or vanished durable job is removed by the reconciler (job and run directory), a dispatch cut off after the secrets were written removes them itself (EXIT/HUP/INT/TERM trap until the job is handed over) or ends as `not_executed` (`incomplete` phase), durable secrets are only written to a tmpfs run root, and a timed-out attached run gets SIGTERM (its bootstrap trap cleans up) before SIGKILL.
66. **Trusting an artifact from the browser (M7-4).** `BeginTrustArtifact` (server role) takes the artifact bytes, action, version, risk and a label; the executor hashes the bytes itself, needs the privileged session, refuses in hardened mode (`cli_required`; `nebula artifact trust` stays), and returns a challenge SHA-256("nebula-artifact-trust-v1\0" ‖ hash ‖ action ‖ version ‖ risk, each NUL-terminated ‖ nonce ‖ expiry) valid for the approval window; at most 16 requests wait, and Lock drops them. `CommitTrustArtifact` consumes the request whatever happens and stores the trust only for a user-verified assertion over that challenge (`webauthn:` and the first 16 bytes of the credential ID as actor); `GetArtifactTrust` (server, admin) reports it. The runbook page shows the executor's view, offers *Trust this version as <declared risk>* when not trusted, and checks that the executor hashed exactly the version's bytes. Trust still only lowers the trust floor: host criticality, secrets and the Safety Scanner apply on top. Signers and signed modules follow in M7-5.
67. **Signed modules, executor part (M7-5).** A module's security-relevant content is its lock (`internal/modulelock`, format `nebula-module-v1`): canonical JSON in its exact form with module name (2 to 31 characters, not a built-in family, `runbook`, `nebula`, `os` or `test`), version, and per action the script path, the script's SHA-256, declared risk, attached or durable, timeout, typed parameters and secret slots (as for runbooks) and declarations (`requires_root`, `writes_config`, `network_access`). The author signs the lock bytes with `ssh-keygen -Y sign -n nebula-module` (Ed25519 only); `internal/sshsig` verifies OpenSSH SSHSIG signatures (SHA-256 or SHA-512, tested against real ssh-keygen output). `RegisterModule` (server role) parses the lock, looks the signing key up among trusted signers, verifies the signature over the exact bytes, requires exactly the scripts the lock names, checks each against its hash, builds each action's artifact itself with the same prelude as runbooks (`internal/prelude`), and in one transaction records the version (a version's lock never changes) and trusts each artifact at the declared risk, raised to MEDIUM by `requires_root` or `writes_config`, with `signer:<fingerprint>` as actor; an existing trust entry for the same bytes is kept. The first registration binds the module name to its signer; a version signed by another signer is refused (`signer_changed`) until `nebula module confirm-signer` (admin). Signers are added only with `nebula signer add` after typing the full fingerprint (CRITICAL); `nebula signer remove` also removes every trust entry the signer's modules created. Unsigned modules get no trust: at least HIGH.
68. **Modules, server part and authoring (M7-5).** `nebula module pack DIR` reads `module.yaml` (strict keys; risk in any case, timeout as whole seconds, parameters sorted by name) and writes the canonical lock `module.lock.json` to sign with `ssh-keygen -Y sign -n nebula-module`; `--archive OUT.tar.gz` packs lock, signature and scripts after checking the lock is still what `module.yaml` and the scripts give (ADR 0003: YAML only here). The server imports the archive as the raw request body (`application/gzip`, at most 1 MiB; regular files with plain relative paths only, at most 64 entries and 4 MiB unpacked), parses the lock, checks every script, and asks the executor (`RegisterModule`); the version is stored with the executor's verdict: verified (the executor's artifacts must equal the server's), or unverified (not signed, untrusted signer, signer change, or executor unavailable; *Verify again* asks once more). A stored version never changes (`server.db` migration 0013, triggers; re-checked when read); only the verdict is renewed. Module actions are `name.action` at the module's version in the operation catalog; an execution runs exactly its version. The pages show every action's script, declarations, parameters, secret slots and scanner findings, rendered as text.
69. **Declarative module UI and results (M7-6, spec 10).** A script of a runbook or module action may write one JSON object (at most 64 KiB) to `$NEBULA_RESULT` (a private temporary file the prelude creates and removes); the prelude embeds it as `result` in its one result line, and anything that is not one JSON object makes the run's result invalid. A module lock may carry `ui.host_tab`: a title and 1 to 10 cards, each naming one of the module's actions and 1 to 20 fields (plain labels, paths of member names such as `service.active`). The host page (`/hosts/<id>`, linked from the inventory) shows each module's tab with the fields of the latest successful result of the card's action on that host (any version). Module texts and values are rendered as text by the core template only: values are read from the result object, objects and arrays shown as compact JSON, control and invisible formatting characters replaced, cut at 200 bytes; modules provide no HTML, URLs, buttons or JavaScript (the only link, *Run <action>*, is built by the core). Acceptance test: hostile titles, labels and values (script tags, `javascript:`, event attributes, escape sequences, bidi overrides) render inert. Module state is the module's own action results on each host; modules have no other storage.
70. **Assets and IPAM-light (M9-1, spec 12).** `server.db` keeps assets (kind server/nas/firewall/switch/printer/iot/unknown, name, hostname, MAC, notes, up to 16 addresses, an optional link to the managed host it became), networks (prefix, at most /8 for IPv4 and /32 for IPv6, masked; VLAN; gateway inside the prefix; up to 16 named pools as first–last ranges), and entries per address (reserved or excluded, with a note, user and time). Nested networks are allowed, the same prefix twice is not. The status of an address is computed, never stored, in this order: EXCLUDED (an exclusion, or the IPv4 network and broadcast address of a prefix up to /30), CONFLICT (more than one owner, where an asset and the managed host it is linked to count as one; or discovery saw another MAC than the asset's; or a reserved address a device answered on in the last 30 days), ASSIGNED (one owner, or the gateway), RESERVED, DISCOVERED, FREE. Managed hosts count with their literal IP endpoints only (IPAM never resolves names). Networks up to 1024 addresses list every address; larger ones and IPv6 list only claimed addresses (all others UNKNOWN). The free-address suggestion (decision 1 of the M9 plan) lists up to 5 FREE addresses, or ones discovery last saw more than 30 days ago, of the network or a pool, labeled a suggestion; it never probes. Names and notes are plain text (no control or invisible formatting characters) and render as text. "Add to managed hosts" opens the inventory form prefilled from the asset; once the host exists the page links it to the asset (`POST /network/a/link`, the host must exist). Discovery (M9-2) fills `discovered_addresses`.
71. **Discovery (M9-2, spec 12).** The server and `nebula-discovery` share a spool, `/var/lib/nebula/discovery` (`discovery_dir` in `server.json`): `jobs/` is owned by `nebula-server` and readable by group `nebula-discovery`, `results/` the other way round, so each side writes only its own directory (the server unit gets `ReadWritePaths=` for `jobs/` from a drop-in `install.sh` rewrites). A job is one JSON file (`nebula-discovery-job-v1`, at most 16 KiB): ID, mode, targets, ports or custom options. Both sides validate it completely (`internal/discoveryjob`): targets are 1 to 16 addresses or prefixes of one family, IPv4 at most /16 and IPv6 at most /112 each, at most 65 536 addresses together; the server also requires each target to lie inside a known network. Decision 2 of the M9 plan: modes `ping` (`-sn`), `ports` (`-sS -p LIST`, at most 32 normalized items), `services` (`-sS -sV --top-ports 100`), `full_tcp` (`-sS -p-`) and `custom`, a fixed set of options (versions, OS, UDP with ports, no ping, open only, ports or top N ports up to 1000, timing T2 to T4), never free-form arguments. Nmap always gets `--privileged -oX - --no-stylesheet --max-retries 2 --host-timeout 10m` and `-T3` unless chosen; targets come last and are canonical addresses or prefixes, so nothing can become an option. `nebula-discovery` is a oneshot unit started by a path unit on `jobs/` (and a timer every 10 minutes as a fallback that only runs queued jobs), with `AmbientCapabilities=CAP_NET_RAW` only (verified: SYN and ARP scans work with `--privileged` and this one capability), `ProtectSystem=strict` and write access to `results/` only; it runs each job with a one-hour limit (process group killed), a clean environment, and parses Nmap's XML (strict, at most 64 MiB, no entities) into hosts that are up. Everything from the network is cleaned on both sides: addresses parsed, MACs normalized, hostnames kept only when they are valid DNS names, other texts made plain (control and invisible formatting characters replaced) and cut at 128 bytes, at most 200 ports per host; a result is at most 32 MiB. The server polls every 30 s, stores the hosts in `discovery_staging`, updates `discovered_addresses` (keeping a known MAC when a routed scan has none) and removes the job file; a job without a result after 3 hours fails. Classification is computed when shown, against the current assets and managed hosts: with a MAC, an asset with that MAC is EXISTING (CONFLICT if the address belongs to another asset), another asset with a different MAC at the address is CONFLICT; otherwise one asset at the address is a POSSIBLE MATCH (several: CONFLICT), a managed host at the address without a linked asset is a POSSIBLE MATCH, and anything else is NEW. Import (selected rows, or all importable) never touches a CONFLICT: a NEW host becomes an asset of kind unknown (ID from the hostname's first label or `ip-<address>`, made unique; notes list vendor, OS and open ports), a host matching only a managed host becomes an asset linked to it, EXISTING and POSSIBLE MATCH rows add the address, MAC or hostname the asset lacks. Schedules: once at a time or every N hours (at least one hour), at most 32, no default schedule; a due schedule advances before it queues, and missed runs are not caught up one by one. Jobs and their staging are kept 90 days; discovery prunes result files after 7 days.
