# Milestone 0: implementation status

Milestone 0 (security prototype) is implemented and its acceptance criteria are covered by tests in `test/security/`. This page records what exists, where it deviates from or sharpens the specification, and what must be done before later milestones rely on it.

## Decisions taken during implementation

These sharpen the spec without changing its architecture. Each is a candidate for an ADR if contested.

1. **`request_version: 1`** is part of the canonical request, so a future change of the canonical form cannot collide with old digests.
2. **Set semantics in the canonical form.** `credential_refs` and `resolved_targets` are sorted before encoding. Order carries no meaning (stage assignment is bound through `stage_plan_hash`).
3. **Execution IDs are single-use.** Re-proposing an execution ID with different content is rejected (`execution_id_reused`). Identical re-proposal returns the live permit; once the permit is gone (expired, discarded, revoked by Lock) the ID is spent and a new execution must be created.
4. **Browser approval needs an active privileged session** for every risk class, not only LOW. The CLI path does not need one; the admin UID on the executor host is the authentication.
5. **Lock revokes all permits**, not only the privileged session. Locking means stop.
6. **The server role may call `Lock`.** Locking only removes capability, so the web UI's "Lock executor" works without a CLI.
7. **Three failed approvals discard a pending permit.**
8. **CLI-only permits expose no browser challenge.**
9. **Root is never an admin.** Admin users are personal accounts and must be members of the socket group `nebula-rpc`.
10. **Unlock is all-or-nothing with one passphrase.** Unencrypted, group-readable, symlinked or weak (RSA < 3072) key files are refused.
11. **One parameters hash, one meaning.** Parameters are sent with the proposal, must hash to `parameters_hash`, and the executor keeps the RFC 8785 form. Duplicate keys are rejected, and numbers must already be canonical and exactly representable (`1.0`, `1e0`, `-0`, `9007199254740993` are rejected). `nebula approve` shows the full canonical parameters with control and bidi characters escaped.
12. **Unknown UIDs are dropped during the handshake**, before any request is read; the per-method table then applies to known UIDs. Clients (`nebula`, `nebula-server`) verify that the socket is served by the executor's UID before sending anything.
13. **Keys:** only OpenSSH-format private keys (bcrypt KDF) are accepted; a Lock issued while an Unlock is decrypting wins.
14. **Lint toolchain:** staticcheck 2026.2.1 cannot read Go 1.27 export data yet, so `make lint` runs it under Go 1.26.9. The module requires Go 1.26.
15. **`executor.db` stores only what makes the executor stricter** (H02): spent execution IDs and WebAuthn signature counters. Permits, approvals and the privileged session are never written to disk, so every restart starts locked, with no permits and no session. A crash or restart is a revocation. This narrows spec 03 and 05, which list permits and session state among the contents of `executor.db`. Since H01 it also holds the admin's risk data (decisions 20 to 23), which can lower a minimum below HIGH; losing it falls back to HIGH (see decision 23).
16. **Durable before visible.** An execution ID is bound in `executor.db` before `Propose` returns a permit, and a new signature counter is stored before `Verify` reports success. If the store fails, the call fails closed with `storage_error`; the detail goes to the audit log only, and a counter that cannot be stored does not count as a failed approval.
17. **Counters never go down.** The stored counter only rises (`ON CONFLICT … WHERE excluded.sign_count > sign_count`); at startup each credential starts at the higher of the credential file and the store, so neither a stale credentials file nor a lost row can lower it.
18. **One executor per data directory.** `executordb.Open` holds a non-blocking `flock` on the data directory for the life of the process, so a second executor on the same directory refuses to start, independent of SQLite's connection handling. SQLite runs on one connection with `locking_mode=EXCLUSIVE` (set before WAL, so there is no `-shm` file), WAL and `synchronous=FULL`. The data directory must be an absolute path. The file is created `0600` with `O_EXCL|O_NOFOLLOW` and checked with `fsguard`, as is the `-wal` file; a looser or foreign-owned file is refused, never repaired. Migrations are embedded, forward-only, one transaction each; a database from a newer version is refused.
19. **Retention:** spent execution IDs are pruned at startup 30 days after their request expired. The cutoff never passes the newest stored `bound_at`, so a clock that jumps forward at boot cannot prune live IDs. Expired requests are rejected by `canonical.Canonicalize`, so a pruned ID can only return inside a new request with a new expiry, and that needs a fresh approval like any new execution.
20. **The executor's risk floor (H01).** A proposal whose `risk_class` is below the executor's minimum is rejected with `invalid_request`, naming only the minimum level; the reason goes to the audit log. A higher `risk_class` is kept. The action floor is the risk an admin declared with `nebula artifact trust` (the executor hashes the file itself). It counts only if the artifact is trusted for exactly this (`action_id`, `module_version`), and it is the highest level the same bytes are trusted at under any action, because the server chooses which action it presents. An untrusted artifact is HIGH (spec 10: unverified scripts running as root are at least HIGH; the executor cannot know whether a script runs as root).
21. **Host criticality is bound to the pinned key.** A host record (`nebula host criticality HOST FINGERPRINT LEVEL`) counts only for a target whose host ID and key fingerprint both match; `host_id` alone is a name the server chooses, so a critical host's key under a harmless name is unrecorded. A key belongs to one record (hosts that share a host key, such as clones, cannot both be recorded and stay HIGH). For actions above LOW the host floor is the recorded criticality, or HIGH without a matching record; a record that shares only the host ID or only the key can raise that floor, never lower it, so a CRITICAL host presented under another of its keys stays CRITICAL. LOW actions are read-only by declaration: they stay LOW on hosts recorded LOW to HIGH and need MEDIUM (a WebAuthn tap) on CRITICAL or unrecorded hosts. The floor is the maximum over action and targets.
22. **Re-checked per host run.** `AuthorizeRun` computes the minimum for the host being run; if trust was withdrawn or the host became more critical after approval, the run is denied with `risk_above_approval` and the host stays unused. Rejected proposals never consume their execution ID.
23. **Only the admin role reads or changes risk data**, through `TrustArtifact` (with the CLI's expected hash, so nothing is stored if the hashes differ), `UntrustArtifact`, `SetHostCriticality` (an explicit `clear` removes a record; a missing level is rejected) and the two list methods. The server learns only the minimum level of its own proposals. Every change is audited with the caller's UID. Losing these rows makes everything HIGH, which also lowers a CRITICAL record or artifact to HIGH: `executor.db` belongs in the backup.
24. **Unknown floor fails closed.** If the risk data cannot be read, Propose and AuthorizeRun fail with `storage_error`; the detail stays in the audit log.
25. **Every registration needs a one-time code from the executor host (H03).** An admin creates it with `nebula webauthn code` (100 bits, 15 minutes, single use; five wrong attempts invalidate it) and types it into the browser. The first credential needs only the code. Once a credential is registered, a further one also needs a user-verified assertion by a registered credential over a challenge that belongs to this registration (spec 05). Whether a confirmation is needed is checked again at `FinishRegistration`: a registration begun as "first" is rejected if another one finished in between. The browser alone can never add a credential: a compromised server cannot turn one hijacked authenticator gesture into a permanent key of its own. Recovery after losing every key: remove the lost credentials with `nebula webauthn remove`; then the code alone suffices.
26. **The executor verifies the attestation itself** with go-webauthn: challenge, origin on the allowlist, no cross-origin or top-origin use, RP ID hash, user presence and user verification, algorithm ES256, EdDSA or RS256, and the attestation statement. It also checks the key itself: P-256, Ed25519, or RSA with at least 2048 bits. Attestation conveyance is `none`; authenticator models are not restricted (no metadata service). The public key and the initial signature counter are stored together in one transaction, only in `executor.db`.
27. **Each registration is single-use.** `FinishRegistration` consumes the pending registration before verifying anything, so a failed, replayed or raced attempt needs a new `BeginRegistration` (and on the code path a new code). At most four registrations may be pending; each expires after five minutes.
28. **Removing a credential deactivates it immediately and locks the executor** (privileged session ended, permits revoked, outstanding code and pending registrations cancelled), because a credential is removed when it may be lost or compromised. `nebula lock` also cancels pending registrations. Removal is serialized with registrations. The row is deleted from the store first; the credential is deactivated in memory even if that fails, but then the RPC fails with "removal was not stored" (audited as `credential_removal_not_stored`), because the credential would be active again after a restart until the removal is retried. Its signature counter is kept, so a re-registered credential cannot start lower. `nebula webauthn list` prints full credential IDs and `remove` prefers an exact match, because authenticators choose their IDs and a prefix could be made to collide.
29. **`webauthn-credentials.json` is imported once.** At startup the Milestone 0 file is imported into `executor.db` and renamed to `*.imported`, so a credential removed later cannot return from it.
30. **Host keys are pinned on the executor host only (H05).** `nebula host pin` probes every endpoint (the handshake is aborted once the host key is known, so no user name or credential is sent), refuses if the endpoints present different keys, shows the fingerprint and pins only after the admin typed `yes`; `--known-hosts` imports exact (plain or hashed) entries instead, never wildcards, never `@revoked` keys, and refuses a file with a line it cannot parse. The server can list pins but cannot probe, pin, unpin or test. One key belongs to one host: cloned VMs must be re-keyed.
31. **Endpoint rules (spec 08) are decided in `internal/sshtransport`.** TCP failure: next endpoint. Handshake failure before the host key: next endpoint, at most once per connection. Host key differs from the pin, or the host offers no key of the pinned type: hard stop. Host key matched, then authentication failed: hard stop; no other endpoint sees the key. Before pinning the client prefers ed25519, ECDSA, `rsa-sha2-512`; after pinning it offers only the pinned type. Keys below RSA 2048 and non-standard types are refused. Connect 10 s, keepalive every 15 s, dropped after 4 missed replies. The host's banner is never shown.
32. **A host key mismatch blocks the host** in `executor.db` (first mismatch recorded with the presented fingerprint and endpoint; survives restarts) and is logged as `host_key_mismatch`. Every connection to a blocked host is refused before any traffic until the admin re-pins it (`nebula host unpin`, which must name the current fingerprint, then `nebula host pin`). An authentication failure is logged but does not block.
33. **Each host binds one SSH user and one keyring reference** at pin time (default `nebula` / `nebula-default`); only that key is offered. `Connect` also takes the fingerprint a permit names for the target and refuses before any traffic if it is not the pin.
34. **Host criticality follows the pin.** For a pinned host, `nebula host criticality HOST LEVEL` binds the record to the pinned key, and a different fingerprint is refused. Unpinning leaves the record; it no longer matches once another key is pinned, so the host counts as HIGH until the admin sets it again.
35. **Web login is verified by the executor (M2).** `BeginLogin`/`FinishLogin` (server role) run a WebAuthn assertion with user verification against the credentials in `executor.db`; the challenge is single-use (2 minutes, at most 32 pending) and the counter is checked as for approvals. The server keeps no credential store of its own and only creates its web session after `FinishLogin` succeeded. A login grants nothing on the executor; removing a credential (or `nebula lock`) cancels pending logins.
36. **Web sessions (M2, `internal/web/auth`).** After `FinishLogin` the server stores only the SHA-256 of a 256-bit session token in `server.db` (migration 0003). Cookie `__Host-nebula_session`: Secure, HttpOnly, SameSite=Strict, Path=/. Idle timeout 24 h, absolute 14 days; logout deletes the row. Every path except `/login`, `/setup`, their JSON endpoints and `/static/` needs a session (GET redirects to `/login`, anything else gets 401). The security middleware checks the Origin of every state-changing request first. `/setup` is public on purpose: the executor requires the one-time code, and for further keys an assertion by a registered key. Browser-facing errors are fixed texts; executor details go to the server log. Login and setup pages load `webauthn.js` plus their own script; no inline script (CSP). Pages send state-changing requests with `fetch` or htmx, never plain HTML forms: under `Referrer-Policy: no-referrer` a form POST carries `Origin: null` and the origin check rejects it (found by the browser test of the login flow).
37. **Privileged session and lock from the dashboard (M2).** With a web session, the dashboard opens the executor's privileged session (`BeginPrivilegedSession` now also returns request options with the registered credentials; `CompletePrivilegedSession` still requires a user-verified assertion, verified by the executor) and locks the executor (`Lock`: session ended, permits revoked, keys wiped). The web session alone opens nothing.
38. **Removing a credential ends its web sessions (M2).** The server asks the executor (`CheckCredential`, server role) at most every 5 minutes per session whether the session's credential is still registered; if not, the session is deleted and the browser sent to the login. If the executor cannot be asked, the session stays (it only reads; every privileged action is verified by the executor) and the check repeats on the next request.
39. **TOTP recovery (M2, spec 05).** `nebula totp setup` (executor host, admin) creates a 160-bit secret, shows it with an `otpauth://` URI and activates it only after one current code is typed back. The web login page offers "Lost your security key?": `RecoveryLogin` (server role) checks the code (RFC 6238, SHA-1, 6 digits, ±1 step), every code works once (last step in `executor.db`), and five wrong codes within 15 minutes block further attempts for the rest of the window. A successful recovery ends the privileged session, revokes every permit and sets a persistent recovery state: until a new WebAuthn credential is registered (one-time code from the executor host, and confirmation by a registered key if any are left), `BeginPrivilegedSession`, `CompletePrivilegedSession` and `SubmitAssertion` are refused and the dashboard says so. The recovery web session reads only and ends when TOTP is removed. The secret is stored unencrypted in `executor.db` (0600, executor user) until the vault exists. `nebula approve` on the executor host is not affected. A new key ends the recovery automatically only if a registered key confirmed it; a key registered with the one-time code alone (all keys lost) keeps the recovery pending until the admin picks it on the executor host with `nebula totp finish-recovery` (it lists the keys registered since the recovery login and needs the typed ID prefix), because a compromised server sees the code the admin types and could register its own key. A recovery login also cancels registrations in progress, like `Lock`. If the executor cannot read the TOTP state, `CheckCredential` answers with an error, so the server keeps the recovery session instead of ending it.
40. **Enrollment helper (M3, spec 08).** `nebula host enroll-script --from ADDR[,ADDR]` asks the executor for Nebula's public key (`GetSSHPublicKey`, admin role, keyring unlocked; the private key never leaves the executor) and prints a POSIX sh script for the admin to review and run as root on the new host: it creates the `nebula` user, adds the key idempotently with `from="<addresses>",no-agent-forwarding,no-port-forwarding,no-X11-forwarding` (0700/0600), writes `/etc/sudoers.d/nebula` (NOPASSWD, checked with `visudo -cf`; skipped with `--no-sudo`) and `/etc/tmpfiles.d/nebula.conf`, and prints the host key fingerprints for `nebula host pin`. Nebula never logs in with a password. All interpolated values are validated (IPs/CIDRs only, user name, key reference) and the key is re-encoded, so nothing can break out of the script's quoting.
41. **Vault (M2, spec 06, `internal/vault`).** `nebula vault init` (admin) creates a 256-bit master key, wrapped with XChaCha20-Poly1305 under a key derived from the passphrase with Argon2id (stored parameters, default 256 MiB, 3 passes, 4 lanes; passphrase at least 32 characters). Each secret (`nebula secret set ID`, value from the terminal or stdin, never argv) gets its own data key; data key and value are sealed with the secret's ID and version as associated data, so blobs moved between records or versions do not decrypt (tested). Only ciphertext is stored (`executor.db` migration 0006). `nebula unlock` tries one passphrase on the SSH keys and the vault and asks again only for the part it did not fit (`UnlockScope`); `Lock` drops the vault key with the SSH keys. Admin role only; no RPC returns a value (an acceptance test checks the service for reveal-style methods and bytes fields in the responses). Values are decrypted only inside the executor (`Vault.Open`, for Milestone 4 runs). Init and unlock are serialized so parallel calls cannot multiply the Argon2id memory. Parameters below 3 passes and 256 MiB are refused at init and when read back from the database (an offline attacker with a copy of `executor.db` guesses at their cost); the database CHECKs only bound them, tests lower the floor through `SetVaultParams`. A Lock during an unlock wins, as in the keyring: the derived key is dropped. `nebula secret set` strips one CRLF or LF from stdin; a lone trailing CR is part of the value.
42. **The TOTP secret stays outside the vault.** TOTP recovery is for a lost security key and must work while the executor is locked (after a reboot, before `nebula unlock`); sealing the secret under the vault key would make remote recovery impossible exactly then. It stays in `executor.db`, readable only by the executor user, like the WebAuthn credentials. Revisit if the threat model changes.

## Known gaps (must close before the named milestone)

| Gap | Risk | Close by |
| --- | --- | --- |
| The minimum risk comes from admin-trusted artifacts and host criticality only; the Safety Scanner and signed manifests are not yet sources, and nothing checks that a declared risk fits the script. | Medium | Milestone 7: executor-side scanner over the trusted bytes and signed manifests as further floor sources (they can only raise it) |
| Host criticality is maintained twice: in the inventory (server) and on the executor. Only the executor's copy counts; for pinned hosts it is bound to the pin (H05), for unpinned hosts the fingerprint is still typed. | Low | Milestone 3: set criticality as part of `nebula host pin`, and refuse records for unpinned hosts once all hosts are enrolled |
| Re-pinning a changed key is an admin action on the executor host (unpin with the current fingerprint, then pin with typed confirmation); spec 08 asks for a HIGH action with user verification. | Low | Milestone 3 web enrollment: re-pin from the UI only through a HIGH permit with UV; the executor-host path stays |
| A host key mismatch is logged, blocks the host and is shown on the dashboard (host, endpoint, presented fingerprint), but nothing is pushed yet. | Medium | Milestone 4 notifications (spec 13): `host_key_mismatch` always notifies |
| There is no bulk enrollment table; the enrollment script (decision 40) is generated per address set on the CLI. | Low | Milestone 3: bulk table in the UI |
| The transport is tested against in-process servers; real OpenSSH on Debian 12 / Ubuntu 22.04 / 24.04 needs the test VMs (`make test-integration`). | Medium | Before Milestone 4: run `make test-integration` against the three VMs |
| A pending permit whose floor rose after the proposal can still be approved; it is stopped at `AuthorizeRun`. | Low | Optional: re-check the floor in `SubmitAssertion` and `ApproveCLI` for a clearer message |
| `nebula approve` shows the artifact hash, not the script. A compromised server could propose an expected action whose artifact differs from what the operator assumes. | Medium | Milestone 7: executor-side artifact store; approval shows the script (or its signed manifest identity) |
| Milestone 4 must send `Permit.Parameters` (canonical bytes held by the executor) to the host, never the raw bytes of a run request. | High if missed | Milestone 4 |
| The protected-path checks are tripwires: the hook can be bypassed, the label and the agent identity are self-declared, and a `pull_request` workflow runs the PR's own workflow file. The binding control is branch protection with required code-owner review and dismissal of stale approvals. | Medium | Configure on GitHub before the first agent PR |
| A missing `executor.db` is recreated empty (counters and spent IDs restart; the executor logs a warning when credentials exist). Refusing would break upgrades from before H02. Because of the exclusive lock, a backup cannot read the database while the executor runs. | Low | Milestone with `nebula backup` (spec 15): back up through the executor, restore `executor.db` with its `-wal`, and refuse a missing database once an install marker exists |
| A fully compromised server sees the one-time code the admin types into the browser and can use it for its own key instead (and, for a further key, also misuse the confirming gesture of that same ceremony). Prevention would need a channel to the authenticator that bypasses the server. Detection: the admin's own attempt fails (the code is used up) and `nebula webauthn list` shows every credential with time and origin. | Medium | Documented limit (same class as UI deception); register keys right after installation; `nebula webauthn code` says to check the list afterwards |
| Credentials confirmed by a credential that is later removed stay registered. | Low | Shown in `nebula webauthn list` (`created_by` names the confirming credential); remove them explicitly if the removed one was compromised |
| The TOTP secret is stored unencrypted in `executor.db` (private to the executor user) by decision 42. | Low | Revisit with the threat model (Milestone 10) |
| Vault secrets are stored and listed, but nothing uses them yet; tmpfs delivery to hosts (`/run/nebula/<execution-id>/`) and output redaction come with execution. | Low | Milestone 4 |
| Web unlock (opt-in, weaker) is not implemented; unlock is CLI only. | Low | Optional, later |
| `peercred.Listen` changes the process umask briefly; call it only during startup. | Low | documented |
| Executor events are not yet signed; audit goes to the structured log. | Medium | Milestone 10 |

## How to run the tests

```
make test              # unit and acceptance tests, race detector
sudo -E make test-privileged   # multi-UID tests (need root to drop privileges)
make test-integration  # SSH against real OpenSSH test VMs (NEBULA_IT_TARGETS, NEBULA_IT_KEY; see test/integration)
make test-browser      # login/setup in Chromium with virtual authenticators (Node.js + Playwright; see test/browser)
make lint              # vet, staticcheck (Go 1.26.9), buf lint
make fuzz              # short fuzz runs of host-input parsers
```
