# ADR 0013: One-step host enrollment with pairing code and optional NetBird join

Status: Accepted, 2026-11-11 (previously: proposed, 2026-11-11); amended
2026-11-12 ("Amendment 2026-11-12: no NetBird Management API" below: NOS
does not talk to the NetBird Management API; the operator supplies a
one-off setup key, Q8 decided). The
maintainer's decisions on Q1–Q9 are recorded in "Decisions of the maintainer
(2026-11-11)" below and are worked into D1–D9. Implementation status and
ticket plan:
[`docs/implementation/one-step-enrollment.md`](../implementation/one-step-enrollment.md)
(previously: "Nothing here is implemented").

## Context

Maintainer request of 2026-11-11: "SSH to the host, run a script, enter the
key/code in NOS, done", also for remote hosts such as the IONOS VPS that NOS
reaches over NetBird.

Today enrollment ([admin guide §7](../admin/guide.md#7-adding-and-enrolling-hosts),
[spec 08](../spec/08-ssh-transport.md)) takes these steps:

1. Create the inventory entry (web UI).
2. On the executor host run `nebula host enroll-script --from ADDR,...`
   (`cmd/nebula/enroll.go`), read the script, copy it to the new host and run
   it there as root. It creates the `nebula` user, installs the executor's
   public key with `from="…",no-agent-forwarding,no-port-forwarding,no-X11-forwarding`,
   the NOPASSWD sudo rule, the sshd `AllowUsers`/`AllowGroups` drop-in and the
   tmpfiles rule, and prints the host key fingerprints.
3. Pin: either `nebula host probe/pin/test` on the executor host, or
   **Enroll hosts** in the web UI (`ProposeEnroll`/`CommitEnroll`: the
   executor probes, the admin compares every fingerprint with
   `ssh-keygen -lf` output from the host, approves with the security key as a
   HIGH action with user verification, the executor re-probes, pins only
   unchanged keys and tries a login).
4. For a host outside the LAN: install and join NetBird by hand first, find
   its NetBird IP, and put that IP into the inventory endpoint.

Steps 2 and 3 are the friction: a file copied by hand between two machines,
and a 43-character base64 fingerprint compared by eye. The comparison is what
protects against a machine in between, so it must not simply be dropped.

Constraints that shape every decision below:

- The executor alone holds SSH keys and vault secrets (spec 02, 06). The
  server is not trusted for approval: WebAuthn binds the permit, not the page.
- A host key is pinned per host; every endpoint must present it; a mismatch
  blocks the host until an approved re-pin (spec 08, `internal/executor/hostkeys.go`).
- Everything a host reports is untrusted input (spec 09).
- No new dependencies, no self-written cryptography, no `ssh` binary or shell
  from Go production code (`AGENTS.md`).
- Profiles never contain secret values; a NetBird setup key is an executor
  vault entry (ADR 0008 §1). Provider tokens are executor-held, least
  privilege, typed calls only, no generic HTTP proxy (ADR 0006). Since the
  amendment of 2026-11-12 one-step enrollment holds no NetBird token and
  makes no NetBird API call at all.

## Terms

- **Enrollment offer:** an executor-held, single-use record that authorises
  one script download and one pairing for one inventory host. Identified by
  an **offer ID**.
- **Offer salt:** 256 random bits generated by the executor per offer,
  embedded in the script; it binds the pairing code to this offer.
- **Pairing code:** a short code the script prints, derived from the host's
  ed25519 host key and the offer salt (D3). The operator carries it from the
  host's terminal to the NOS web UI.
- **Paired enrollment permit:** the HIGH permit that pins the key that
  matched the code (D4). It replaces the eye comparison of fingerprints, not
  the approval.

## Decisions

### D1: Flow

1. **Web UI, "Add host (one step)".** The operator picks the inventory
   host or creates it in the same dialog (Q4: a normal inventory entry shown
   "not enrolled" until the pin; if the offer fails it is deleted only when
   the operator chooses so), and enters SSH user (default `nebula`),
   credential reference (default `nebula-default`), sudo yes/no, and
   whether to join NetBird (D6, only offered when the executor has a
   NetBird management URL configured; amended 2026-11-12, previously "when
   a NetBird token is configured"). With NetBird the operator also enters
   a **one-off setup key** they created in the NetBird dashboard (D6
   "Operator-supplied setup key"), in a masked input of the dialog or with
   the executor-local CLI (dialog entry is not enabled before open
   question Q11 is decided, D6 "Entry"; fix round 3; the executor refuses
   a key sent with the create until then, fix round 4). An open privileged
   session (ADR 0007) is required.
2. **Offer.** The server calls the executor (`CreateEnrollOffer`). The
   executor creates the offer: offer ID (D2), salt, expiry **15 minutes**,
   bound to the host ID, SSH user, credential reference and the web session
   that created it. Without NetBird the executor renders the script (D5) at
   once in memory and stores only its SHA-256, never the bytes (D2
   "Retention"). Audit `enroll_offer_created`.
   - **With NetBird**, until open question Q11 is decided, every offer
     starts in `awaiting_key`: `CreateEnrollOffer` carries no key, the
     executor refuses a create that carries one (D6 "Entry", reason class
     `dialog_entry_disabled`), and the operator enters the key with the
     executor-local CLI, which validates it (D6), seals it into the vault
     and moves the offer to `awaiting_approval` in one commit (D6 "Link to
     the offer"); the web session that created the offer stays its only
     binding (D2). Only once the Q11 decision enables dialog entry does an
     offer whose key was typed into the dialog start directly in
     `awaiting_approval`, with the key validated and sealed at creation
     (fix round 5; previously this step described dialog
     entry as the main path and the CLI entry as the operator's
     alternative). In `awaiting_approval` the offer holds only the vault
     reference of the key; it has no stored download hash and cannot be
     downloaded yet; its render inputs are fixed and "Show script" already
     renders the placeholder variant, as in `awaiting_key` (step 3, D2).
     The executor proposes a **NetBird offer permit** (HIGH,
     user verification; binds offer ID hash, host ID, SSH user, credential
     reference and the setup-key check value of D6). Only after the
     operator approves it with the security key does the executor render
     the script with the key in memory, store its hash (again not the
     bytes) and move the offer to `open`. A compromised server with an open
     privileged session can therefore not get any setup key into a script
     without a security-key touch whose view names the key check value.
     That touch detects a substituted key only if the operator compares
     the check value with a reference the server cannot forge: the value
     printed by the executor-local CLI entry, or the value the operator
     computes on their own machine for a key typed into the dialog (D6
     "Check value"). For a key typed into the dialog without that
     comparison, every check value the operator sees derives from what the
     server forwarded, so substitution is not detected (D6 "Compromised
     server"; fix round 2, previously this sentence claimed protection
     against substitution for both entry paths; Q11 options (b) and (c)
     close this gap, fix round 3; until Q11 is decided only the CLI entry
     exists, fix round 4). NetBird offers also
     have their own lower limits (D2). (Amended 2026-11-12; previously:
     the offer had no setup key until approval, the permit bound managed
     group, ephemeral flag and setup-key expiry, and on approval the
     executor created the key through the NetBird Management API under a
     persisted pending record. Before that, amended 2026-11-11: "no setup
     key and no script yet".)
3. **Command.** The UI shows one command block for the operator's POSIX
   shell (bash, dash, zsh), for example:

   ```
   ( umask 077
     for t in /dev/shm "${XDG_RUNTIME_DIR:-}" "${TMPDIR:-/tmp}"; do
       [ -n "$t" ] && [ -d "$t" ] && [ -w "$t" ] && break; done
     d=$(mktemp -d "$t/nos-enroll.XXXXXXXX") || exit 1
     trap 'rm -rf "$d"' EXIT; trap 'exit 130' HUP INT TERM
     cd "$d" &&
     printf 'url = "https://nos.example.lan/enroll/%s"\noutput = "nos-enroll.sh"\n' \
       '<offer-id>' |
       curl --proto '=https' --tlsv1.2 -fsS -K - &&
     echo '<sha256>  nos-enroll.sh' | sha256sum -c - &&
     sudo sh nos-enroll.sh )
   ```

   The offer ID never appears in a process's argument list: `printf` is a
   shell builtin in bash, dash and zsh (no `exec`, so nothing in
   `/proc/<pid>/cmdline`), and `curl` reads URL and output file from its
   config on standard input (`-K -`). Another local user on the host
   therefore cannot read the ID from the process list and race the
   operator's download. The `wget` variant reads the URL from standard
   input the same way (`wget --https-only -i - -O nos-enroll.sh`). The
   pasted command, including the ID, can still land in the operator's shell
   history file; that file belongs to the operator (`0600` by default) and
   the ID is consumed by the download seconds later, after which it only
   yields the uniform `404`. This residual is accepted (threat table).

   The subshell sets `umask 077`, downloads into a fresh `mktemp -d`
   directory (mode `0700`, file mode `0600`) and removes that directory from
   a `trap` on exit, hang-up, interrupt or termination. So the script, which
   may contain the NetBird setup key, is never readable by other local users
   and is not left behind when the download, the hash check or the script
   fails or the operator presses Ctrl-C. Only `SIGKILL` or a power loss can
   leave the file in the temporary directory (`0700`, root or the operator
   only); the setup key is then one-off and short-lived when the operator
   created it as D6 recommends, and NOS tells the operator to revoke it in
   NetBird when the offer becomes final, `enrolled` included (D6 "Final
   state"; fix round 3, previously "when the offer ends without
   enrollment"). (Amended
   2026-11-12; previously: "still one-off, at most 1 hour valid and
   revoked when the offer becomes final", which NOS enforced through the
   NetBird API.)

   **Which directory, and what reaches a disk.** The command creates its
   directory in the first writable one of `/dev/shm` and
   `$XDG_RUNTIME_DIR`, both RAM-backed `tmpfs` on the supported hosts, so
   the script and the setup key in it normally never touch a disk. Only if
   neither exists does it fall back to `$TMPDIR` or `/tmp`, which is
   disk-backed on Debian 12, Ubuntu and Proxmox VE; then `rm -rf` removes
   the file but the key can remain in freed blocks (and in SSD spare
   areas). A `tmpfs` page can also be written to swap. Both are accepted
   residuals (threat table): a key created as D6 recommends is one-off and
   short-lived, and a used key cannot join a second peer, so a copy
   recovered from freed blocks or swap is useless once it was used or has
   expired; an unused key stays valid until its NetBird expiry or until
   the operator revokes it, which NOS asks for when the offer becomes
   final, `enrolled` included (fix round 3, previously "when the offer
   ends without enrollment"; amended 2026-11-12; previously: "one-off, at most
   1 hour valid and revoked when the offer is final"). The same directory rule
   applies to the script's own key file (D5). The UI shows a second variant
   for a root login without `sudo` (common on minimal Debian and VPS
   images): identical except that the last line is `sh nos-enroll.sh )`.
   Users of non-POSIX shells (fish) start `sh` first.

   Download, hash check, then run; never `curl | sh` (D7). A "Show script"
   link shows the script for review without consuming the offer: the
   executor renders it through the RPC `ShowEnrollScript` (server role, only
   for the session that created the offer, D2 "Binding") with the setup-key
   value replaced by the fixed placeholder `<netbird-setup-key-withheld>`,
   so "Show script" never returns the setup key, however often it is called.
   Apart from that line the bytes are those of the download (checked via
   the placeholder hash stored at creation, D2 "Retention"); the page says
   so, and the hash on the page is the hash of the downloaded script. For a
   NetBird offer still in `awaiting_approval` there is no stored hash yet
   (the supplied setup key is already sealed in the vault, but "Show
   script" never reads it); "Show script" then shows the placeholder render
   without a hash and says so (amended 2026-11-11, see "Amendments";
   amended 2026-11-12, previously "there is no setup key and no stored
   hash yet"). The
   server serves the view as its own `text/plain` response with the same
   headers as the download (`Cache-Control: no-store`,
   `X-Content-Type-Options: nosniff`,
   `Content-Security-Policy: default-src 'none'; sandbox`, D7). A "Download
   in browser" fallback exists for hosts that cannot reach the NOS origin;
   it is not offered for NetBird offers (D8).
4. **On the host** the operator runs the command as root (in their existing
   SSH session or on the console). The script is today's enrollment script
   plus, optionally, the NetBird join (D6), and at the end it prints:

   ```
   NOS pairing code:  K7QXM-2PD9H-TR4AB-6CJWN-0FE5S
   Addresses:         192.168.0.21  fd00::21  100.92.14.7 (netbird)
   ```

5. **Pairing in NOS.** The UI page of the offer (still open in the
   operator's session) asks for the code and the endpoint to use: one of the
   inventory endpoints, or one of the printed addresses typed or picked by
   the operator. The server passes code and endpoint to the executor
   (`SubmitPairingCode`). The executor probes the endpoint (no credential
   sent), takes the presented **ed25519** host key, computes the code from it
   and the offer salt, and compares in constant time.
   - The probe offers **only** `ssh-ed25519` as host key algorithm, so the
     server cannot negotiate ECDSA or RSA instead; a server without an
     ed25519 host key fails the probe ("no ed25519 key", not a mismatch).
     Every later connection to the host restricts `HostKeyAlgorithms` to the
     pinned key's type, as `internal/sshtransport` already does for pinned
     keys, so a host that later presents only another key type fails the
     connection instead of being accepted under a different algorithm.
   - **Endpoint not yet in the inventory.** If the operator types or picks an
     address that is not one of the host's inventory endpoints, the paired
     enrollment permit binds it as "endpoint to add", and the approval page
     and `nebula approve` show "will be added to the inventory host". The
     endpoint is validated exactly like a manually entered inventory
     endpoint (spec 09, spec 12). It is added to the host's endpoint list
     (appended last) only after a successful commit, in the same step as the
     pin, audited as `inventory_endpoint_added` with source `paired`; a
     failed, expired or revoked offer adds nothing. This is the same
     privileged-session edit an operator could make by hand, now covered by
     the HIGH approval as well; it never replaces or reorders existing
     endpoints, and every endpoint must still present the pinned key
     (spec 08).
   - Match: the executor proposes a paired enrollment permit (D4). The UI
     shows host, endpoint, SSH user, credential, full SHA-256 fingerprint and
     "matches the pairing code from the host"; the operator approves with the
     security key, exactly like **Enroll hosts** today (HIGH, user
     verification).
   - Mismatch: see D3 failure handling.
6. **Commit.** As in `CommitEnroll`: the executor re-probes the endpoint,
   pins only if the presented key is still the approved one, then tries a
   login when the keys are unlocked and reports the result. The offer becomes
   `enrolled`. Hosts pinned this way get no criticality record (they count as
   HIGH until set on the executor host), as today.

Nothing is sent from the host to NOS by the script (no callback, no token in
the other direction). The only channel host → NOS is the operator.

### D2: Offer ID and offer lifecycle

- **Offer ID:** 128 random bits or more from `crypto/rand` (recommended 160
  bits, 32 characters of lowercase RFC 4648 base32 without padding), generated
  by the executor. It is a capability for one download; the executor stores
  only its SHA-256, never the ID itself, and logs only the first 8 hex
  characters of that hash.
- **States:** `open` → `downloaded` → `pairing_proposed` → `enrolled`;
  until open question Q11 is decided, every NetBird offer starts in
  `awaiting_key`, moves to `awaiting_approval` when the key is sealed at
  CLI entry, and moves to `open` only after the NetBird offer permit is
  approved and the full render's hash is stored (D1 step 2, D6 "Entry",
  D6 "Supply order"; fix round 6; previously "NetBird offers start in
  `awaiting_approval`" and only a NetBird offer whose key is entered with
  the executor-local CLI "starts one step earlier in `awaiting_key`",
  added 2026-11-12, and before that "and the setup key is recorded", D6
  "Creation order"). Only once the Q11 decision enables dialog entry
  does a NetBird offer whose key was typed into the dialog start directly
  in `awaiting_approval` (D1 step 2); from any non-final state → `expired`,
  `revoked` or `failed`. Final states never return to `open`. Every state
  change is one atomic compare-and-set on the offer row (expected old state
  → new state); a transition whose expected state no longer holds fails and
  changes nothing.
- **Expiry:** 15 minutes in total from creation for the download and the
  code submission (Q2, default; a named constant). An approval started
  before expiry may finish within the permit's own lifetime; a commit after
  the permit expired fails. With the 120-bit code (D3) a later change may
  raise the total window up to 60 minutes without weakening the grinding
  bound materially; that is a separate change of the constant, not part of
  this decision.
- **Single use:** the first successful download moves the offer to
  `downloaded`; a second download returns the same `404` as an unknown ID
  (no oracle). One well-formed code submission is accepted per offer (D3).
- **Binding:** only the web session that created the offer may submit the
  code, approve and commit; another session (also of the same user) sees the
  offer read-only and may revoke it. Lock, restart or session end of the
  privileged session does not resurrect it. The executor-local CLI never
  creates an offer and never becomes a binding: it can only supply the
  setup key of a NetBird offer in `awaiting_key` that a web session
  created; approval, code submission and commit stay with that creating
  web session (D6 "Entry"; added 2026-11-12).
- **Revocation:** the operator can revoke an open offer in the UI; the
  executor-local CLI can list and revoke offers (`nebula host offers`,
  `nebula host offer-revoke`). NOS cannot revoke the NetBird setup key
  (it does not talk to the NetBird Management API): revoking a NetBird
  offer wipes the key from the vault and, unconditionally (no "is it
  used?" check), shows the operator in the UI, in the CLI output of
  `nebula host offer-revoke` and in the audit record that the key must be
  revoked in the NetBird dashboard unless it was one-off and is used up
  (D6 "Final state", which gives the same advice for every final state,
  `enrolled` included; fix round 3, previously "if it was not used").
  (Amended 2026-11-12; previously: "Revoking also revokes the NetBird
  setup key (D6), unconditionally" through the NetBird API.)
- **Limits** (named constants in the implementation): at most 10 non-final
  offers per executor, at most 30 offers created per hour, at most 5 probes
  per offer, at most 3 rejected (malformed) code submissions per offer.
  NetBird offers have separate, lower limits on top: at most 2 non-final
  NetBird offers and at most 5 NetBird offers (that is, supplied setup
  keys) created per hour (each one also needs its own security-key
  approval, D1 step 2; amended 2026-11-12, previously "at most 5 setup
  keys created per hour"). Refused setup keys count against
  `NetBirdSetupKeyRejectsPerHour` = 10 per executor and hour, in one
  budget for keys sent through the server and a separate one for the
  CLI entry (D6 "Rejection limit"; fix round 3, per-source budgets since
  fix round 4, previously one budget for both).
- **Audit** (executor and server, no secret values): `enroll_offer_created`,
  `enroll_offer_approved` (NetBird offers),
  `enroll_script_downloaded` (with the client address determined as in D7
  "Client address", and the direct peer address),
  `enroll_script_hash_mismatch`,
  `enroll_code_rejected` (malformed), `enroll_code_mismatch`,
  `enroll_paired_proposed`, `host_enrolled`, `enroll_offer_expired`,
  `enroll_offer_revoked`, `inventory_endpoint_added`,
  `netbird_setup_key_supplied`, `netbird_setup_key_rejected`,
  `netbird_setup_key_wiped`, `netbird_setup_key_revoke_advised`,
  `netbird_possible_orphan_peer` (D6; amended 2026-11-12, previously
  `netbird_setup_key_pending`, `netbird_setup_key_created`,
  `netbird_setup_key_invalid`, `netbird_setup_key_reconciled`,
  `netbird_setup_key_unresolved`, `netbird_setup_key_revoked`,
  `netbird_setup_key_revoke_failed`, `netbird_setup_key_expired_unrevoked`,
  `netbird_peer_joined`, `netbird_peer_orphaned`, `netbird_peer_deleted`,
  `netbird_peer_kept`, all of which needed the NetBird API and are
  dropped).
- **Retention:** the offer store never holds script bytes. It holds every
  render input, fixed when the offer is created (script options, NetBird
  choice, `from=` addresses, Nebula's key line, and for NetBird
  offers the management URL, the key-passing mode per client version and
  the setup key's vault reference and check value, and the script
  template version; amended 2026-11-12, previously also the ephemeral
  flag, managed group, NOS NetBird address read from the API and
  setup-key expiry), so a render never reads live executor
  configuration. At creation it also stores the SHA-256 of the placeholder
  variant, for every offer; an executor whose template version differs
  from the stored one refuses to render the offer and fails it with
  `enroll_script_template_changed` instead of a hash mismatch (amended
  2026-11-11). The stored SHA-256
  covers the full render: computed at creation for an offer without
  NetBird, and for a NetBird offer when its NetBird offer permit is
  approved (D6 "Supply order"; amended 2026-11-12, previously "in the step
  that records the validated setup key", D6 "Creation order"). The executor renders the script on
  demand in two variants:
  - **Download** (`FetchEnrollScript`, `DownloadEnrollScript`): the full
    script from the stored render inputs, the salt and, for NetBird
    offers, the setup key read from the vault; it checks the rendered bytes
    against the stored SHA-256 (a difference refuses the download with the
    uniform `404`, moves the offer to `failed` and audits
    `enroll_script_hash_mismatch`), hands them to the RPC response and
    overwrites its buffer afterwards. For a NetBird offer the setup key is
    wiped from the vault in the same step that moves the offer to
    `downloaded`, because no further render of the full script is allowed
    (D6 "Final state"; added 2026-11-12, previously wiped only at the
    final state).
  - **"Show script"** (`ShowEnrollScript`): the placeholder variant
    directly, with `<netbird-setup-key-withheld>` in the setup-key line; it
    never reads the setup key from the vault, is checked against the
    stored placeholder hash, not the download hash (amended 2026-11-11;
    previously not hash-checked), never changes the
    offer's state and can never move it to `failed`; a render error refuses
    only that request. In `awaiting_approval` it shows no hash (D1).
    (Previously: "Show script" was rendered with the setup key from the
    vault and hash-checked like the download; amended 2026-11-11.)

  No rendered script is written to the offer store, a temporary file, a cache or a log on the executor or the server (the server
  streams the RPC response to the client without buffering it to disk; the
  reverse proxy in front of it must not buffer it to disk either, D7
  "Reverse proxy").
  The setup key itself exists at rest only encrypted in the vault (D6).
  Final offers are kept as audit records without salt and setup key; the
  salt is wiped when the offer becomes final, the setup key as described
  in D6 "Final state" (amended 2026-11-12; previously "the setup key and
  its NetBird key ID as described in D6 'Revocation at the final state'";
  there is no NetBird key ID any more).

### D3: Pairing code

**Construction (decided, Q1).**

```
digest = SHA-256( "nos-enroll-pair-v1" || 0x00 || salt[32] || ed25519 host key blob )
v      = first 120 bits of digest (big-endian)
hi, lo = the two 60-bit halves of v (bits 1–60 and 61–120)
code   = hi as 12 Crockford base32 characters, then lo as 12 Crockford base32
         characters (24 data characters, 120 bits), then 1 Crockford check
         character for v mod 37; 25 characters in total,
         shown as XXXXX-XXXXX-XXXXX-XXXXX-XXXXC
```

Input is case-insensitive with Crockford folding (`O` → `0`, `I` and `L`
→ `1`); hyphens and spaces anywhere are ignored. After folding and removing
separators the input must be exactly 24 data characters from the 32-symbol
alphabet and one check character from the 37-symbol alphabet.

The host key blob is the SSH wire format of the public key (the bytes the
SHA-256 fingerprint is computed over), so the code is "derived from the host
key fingerprint" with the offer salt mixed in. The script computes it with
coreutils (`base64 -d`, `sha256sum`, `cut`, `tr`) and POSIX shell arithmetic,
present on every supported host (Debian 12, Ubuntu 22.04/24.04, Proxmox VE);
the executor computes it with `crypto/sha256`. This is a composition of
SHA-256 and an encoding, not new cryptography; shared test vectors bind
script and Go code (EN-03, EN-04).

`basenc` is not used: it produces RFC 4648 base32 or base32hex, not
Crockford. A 120-bit number does not fit shell arithmetic, so the script
never forms it:

1. It takes the first 30 hex digits of the `sha256sum` output (exactly 120
   bits) and splits them into hex digits 1–15 (`hi`) and 16–30 (`lo`),
   each exactly 60 bits.
2. It reads each half as one number with `$((0x…))`. 60 bits fit the
   64-bit signed shell arithmetic of dash and bash on the supported hosts
   (the value is below 2^60, so the sign bit is never set); the script
   checks 64-bit arithmetic at start.
3. For each half it emits twelve 5-bit groups from the most significant end
   (`$(( (x >> s) & 31 ))` for `s` = 55, 50, …, 0) as base32hex digits
   (`0-9A-V`), `hi` first, and maps all 24 to Crockford with
   `tr 0123456789ABCDEFGHIJKLMNOPQRSTUV 0123456789ABCDEFGHJKMNPQRSTVWXYZ`.
   Because 60 is a multiple of 5, the 24 characters of the two halves are
   exactly the 24 characters of `v`.
4. It computes the check value without the 120-bit number, using
   `v = hi · 2^60 + lo` and `2^60 mod 37 = 10`:
   `c = ( (hi % 37) * 10 + lo % 37 ) % 37`. Every intermediate value is
   below 400. The script writes the constant as `10` with a comment; the
   Go code computes `v mod 37` from the full 120-bit value
   (`math/big` or the same split), and the shared vectors bind both.
5. It indexes `c` into the fixed 37-symbol string
   `0123456789ABCDEFGHJKMNPQRSTVWXYZ*~$=U` (quoted so `$` and `*` stay
   literal) and prints the 25 characters in groups of five.

The shared EN-03/EN-04 test vectors are chosen so that together they contain
every one of the 32 data symbols at every one of the 24 positions, every one
of the 37 check values (including the five check-only symbols `*~$=U`), and
values with the top bit of `hi` set, with the top bit of `lo` set, and with
both set.

The script reads the key sshd actually serves: the `hostkey` lines of
`sshd -T` whose public half is `ssh-ed25519`, falling back to
`/etc/ssh/ssh_host_ed25519_key.pub`. A host without an ed25519 host key gets
no code and a message to use the classic path (§7.2); one-step enrollment
pins ed25519 only.

**Why salted, not the plain fingerprint.** A plain truncated fingerprint is
a function of a public, long-lived value: anyone who can connect to the
host's sshd before enrollment can read its key, compute the code and grind a
key with the same code at leisure, so a 15-minute window would bound
nothing. With the salt, grinding can start only when the attacker knows the
salt, which is in the script and the offer page, and must finish before the
executor's probe, inside the 15-minute offer lifetime.

**Entropy versus grinding.** The attacker needs a second preimage of the
truncation (an ed25519 key whose code equals the host's), not a collision:
expected work 2^n key generations plus hashes for an n-bit code; for the
decided 120 bits that is 2^120 ≈ 1.3·10^36.

| Code bits | Grind rate (keys/s) | Expected time |
| --- | --- | --- |
| 40 (8 chars) | 10^9 (one large GPU, optimistic) | ≈ 18 minutes: too weak |
| 60 (12 chars) | 10^9 | ≈ 37 years |
| 60 (12 chars) | 10^12 (large cluster) | ≈ 13 days; P(success in 15 min) ≈ 2^-10, in 60 min ≈ 2^-8 |
| 80 (16 chars) | 10^12 | ≈ 38,000 years |
| 120 (24 chars) | 10^12 | ≈ 4·10^16 years; P(success in 15 min) ≈ 2^-70, in 60 min ≈ 2^-68 |

Decision (Q1): **120 bits, 24 data characters + 1 check character.** 60
bits would already leave a cluster-scale attacker below 1 in 1,000 within 15
minutes; 120 bits removes the grinding question altogether, also for a
window of up to 60 minutes (Q2) and for attackers far beyond today's
clusters, for the cost of typing 12 more characters than the 60-bit
variant. The attacker must in any case also have learned the salt and sit
in the network path at probe time.

**Online guessing does not apply.** The operator types the code; an attacker
gains nothing from submitting codes. The probe limit (5 per offer) bounds the
other direction: an attacker in the path who answers each probe with a fresh
random key has a 2^-120 chance per probe.

**Failure handling.**

- *Malformed code* (not 25 characters after folding and removing
  separators, characters outside Crockford base32, wrong check character):
  rejected before any probe, counted (max 3), audit
  `enroll_code_rejected`. The check character catches typing errors so that
  a typo is not mistaken for an attack.
- *Well-formed code that does not match the presented key*: one mismatch
  ends the offer (Q7; there is no second submission). The offer
  becomes `failed`, the endpoint is not pinned, the NetBird setup key is
  wiped from the vault and the operator is told to revoke it and to check
  NetBird for a peer it joined (D6 "Final state"; amended 2026-11-12,
  previously "revoked (unconditionally, D2) and a peer it joined is
  handled as an orphan"), audit `enroll_code_mismatch` with the presented
  fingerprint and endpoint, dashboard notice and notification as for a host
  key mismatch. The UI states: "The host at this endpoint presents a key that
  does not match the code from the host. Either the endpoint is a different
  machine, or something is in between. Check the endpoint, then create a new
  offer." Re-offer means a new salt, so the script must be run again (it is
  idempotent) and prints a new code.
- *Probe failure* (unreachable, timeout, no ed25519 key): not counted as a
  mismatch; the operator may pick another endpoint within the probe limit.
- *Host already pinned*: the offer cannot be created for a pinned or blocked
  host; re-pinning stays the existing approved re-pin flow (§7.3).

### D4: Approval and pinning are unchanged in strength

- The paired enrollment permit is a HIGH action with user verification, the
  same requirement as `ProposeEnroll`. It binds offer ID hash, host ID,
  endpoint, SSH user, credential reference, the full SHA-256 fingerprint and
  the fact "code matched" (with the code). It is single-use and expires like
  other enrollment permits.
- The executor, not the server, decides whether the code matched; the server
  only forwards the operator's input.
- Commit re-probes and pins only an unchanged key, then tests the login,
  exactly as `CommitEnroll` does. The pin is per host; every endpoint added
  later must present the same key; a mismatch later blocks the host (spec 08).
- `nebula approve` on the executor host shows the same binding (host,
  endpoint, fingerprint, "code matched", offer creation time and download
  address), so the hardened, independent view of ADR 0007 is available.

**What the code replaces, and its trust anchor.** The code replaces the
operator's eye comparison of fingerprints; it does not replace the approval.
Its authenticity rests on the operator's own session to the host where they
read the code. On the console or over an SSH session whose host key the
operator already trusts, this is as strong as today's comparison. Over a
first SSH login with trust on first use (typical for a fresh VPS), the code
is only as authentic as that first login: an attacker who intercepts the
operator's session can also forge the printed code. The UI and the guide say
so and recommend the provider's web console or a verified known_hosts entry
for internet-facing hosts.

**Residual risk equal to today.** A compromised server can show the operator
one thing and submit another code or endpoint; WebAuthn signs the permit's
challenge, not the page (ADR 0007). To pin a wrong key it must also control
the network path to the endpoint. This is the same exposure as the web
**Enroll hosts** flow today; the executor-local `nebula approve` view is the
mitigation.

### D5: Script generation

- The executor generates the script from the same template as
  `nebula host enroll-script` (shared generator, EN-04); the CLI output stays
  byte-identical for the same options (golden test).
- `from=` addresses come from **executor-local configuration** (new executor
  flag or config entry: enrollment source addresses), never from the server
  or the browser. With D6 the NOS machine's own NetBird address is one of
  these executor-local source addresses, set by the operator in the
  executor configuration, never read from input (amended 2026-11-12;
  previously "the executor adds the NOS machine's own NetBird address,
  read from the NetBird API").
- The user name and credential reference are validated as in
  `cmd/nebula/enroll.go`; the key line is re-encoded from the parsed key.
- One-step additions, all at the end: the optional NetBird section (D6),
  the pairing code (D3) and the address list (`ip -o addr show scope global`,
  plus the NetBird address). Addresses are hints for the operator; NOS
  treats whatever the operator types as an endpoint to validate (spec 09:
  syntax, length, IP or DNS name), never as trusted.
- The script carries no secret except, optionally, the NetBird setup key.
  The script file itself lives only in the `0700` `mktemp -d` directory of
  the command in D1 step 3, which removes it by `trap` on every exit path
  (success, failure, hang-up, interrupt, termination). The script sets
  `umask 077` itself as well, writes the setup key only to a `0600` file
  under its own `mktemp -d` directory (created in `/dev/shm` or
  `$XDG_RUNTIME_DIR` by the same rule as the command, D1 step 3; the
  disk-backed fallback is the named residual there) removed by its own
  `trap` on `EXIT`, `HUP`, `INT` and `TERM`, and passes the key to the
  NetBird client **only** through an environment variable or that key file,
  never as a command-line argument: an argument can be persisted to disk
  logs by auditd `execve` rules, process accounting or the client's own log.
  The same rule holds for an executor SSH step that hands the key to a
  pinned host (D6 "Join on the host"): the key travels on the SSH
  session's standard input into a `0600` file or the client's
  environment, never in the remote command line (added 2026-11-12).
  EN-12 (since 2026-11-12 its follow-up EN-16e) verifies per supported client version which of the two the client
  accepts; for a client version that accepts neither, the NetBird option is
  not offered and the script stops before the join. If the operator runs the
  script outside the documented command, it still removes its own key file,
  and when it contained a setup key it deletes itself from its `trap`.
- Every stored render input that reaches the script has a format rule and
  is placed only inside one single-quoted shell literal whose format
  excludes `'`, or only selects fixed template text (booleans, the
  key-passing mode); this includes the NetBird management URL (`https`
  only, at most 256 bytes ASCII, no userinfo, query, fragment, quote or
  shell metacharacter) and the key-passing mode table (client versions
  `MAJOR.MINOR.PATCH`, mode `env` or `file`). Values are checked at
  creation and at every render (spec 03 "Render-input format"; amended
  2026-11-11, previously only the setup key and `from=` had a rule).
- Size limit of the rendered script: 64 KiB; the executor refuses larger.

### D6: Optional NetBird join

is refused before anything is stored: no offer is created, and
`netbird_setup_key_rejected` is audited with the reason class only, never

*Rejection limit* (fix round 3; previously a refused dialog key was bound
by no limit, because it creates no offer and so no per-offer count
applies). Refused keys are counted per source, in two budgets of
`NetBirdSetupKeyRejectsPerHour` = 10 refusals per executor and hour each,

- *Server budget:* every key refused in `CreateEnrollOffer`, that is
  every key that arrived through the server, for any reason class,
  `dialog_entry_disabled` included. While it is reached, every
  `CreateEnrollOffer` that carries a key is refused before the key is
  looked at, valid keys included; this check is the first one
  `CreateEnrollOffer` makes on a key-carrying request, before the Q11
  gate of "Entry" (fix round 5). CLI entries are not affected.
- *CLI budget:* every key refused in the executor-local CLI entry, for
  any reason class. While it is reached, every CLI key entry is refused
  before the key is read, valid keys included. Creates through the server
  are not affected.

The source is the path the key took into the executor (the
`CreateEnrollOffer` RPC or the local CLI), never a value the caller
names, so a key sent through the server cannot be counted against the
CLI budget.

*Window and records* (fix round 5; previously "at most 11 such audit
records per hour", which the sliding window did not guarantee, and it was
open whether refusals while a budget is reached extend the window):

- "Hour" is a sliding window: a budget is reached when it holds 10
  counted refusals whose times lie within the last 60 minutes, measured
  with the executor's injected clock.
- Only refusals made while the budget is not reached are counted; each
  is audited as `netbird_setup_key_rejected` with its reason class and
  source. A refusal because the budget is reached is not counted and
  does not extend the window, so the budget frees up 60 minutes after
  the oldest counted refusal in it.
- A refusal because the budget is reached is audited as
  `netbird_setup_key_rejected` with reason class `rate_limited` and the
  source only if no `rate_limited` record for that source was written in
  the last 60 minutes; otherwise it is not audited. The dashboard notice
  naming the source is shown while the budget is reached.
- So any 60 minutes hold at most 10 counted-refusal records and one
  `rate_limited` record per source, 11 per source and 22 together, and
  none of them carries the value.

The counted refusal times and the time of the last `rate_limited`
record are kept per source in the executor database (EN-16d), at most 10
times and one time per source, older ones pruned, never the value, a
part of it, the check value or the client; a restart of the executor
does not reset a budget (fix round 5; fix round 4 kept the counters in
memory, so a restart reset them, which contradicted EN-16d). If the
executor cannot read or write this record, it refuses the key entry of
that source without looking at the key (fail closed) and reports the
store error without the key; such a refusal is neither counted nor
audited as a key refusal.

Availability residuals (fix round 4): a compromised server or any open
privileged session can exhaust the server budget, which blocks only
key-carrying creates and so not the keyless web create of the CLI entry,
and the NetBird offer limits of D2 (2 non-final, 5 per hour), which
serve the web create that every NetBird offer, CLI entry included,
starts with (fix round 6; previously both were said to serve that
create); that is the
existing residual of a compromised server with an open privileged
session, which can also revoke any offer (threat table, "Compromised
server"); a restart of the executor does not end it, the budget frees up
60 minutes after its oldest counted refusal (fix round 5). It cannot
exhaust the CLI budget, and it cannot make the CLI
refuse a key for an offer that a web session created in `awaiting_key`
other than by revoking that offer. Only a process running as
the admin UID on the executor host can exhaust the CLI budget; that
process can already use the CLI itself.

*Check value.* The executor computes `check = first 8 hex characters of
SHA-256("nos-netbird-setup-key-check-v1" || 0x00 || key)` (a composition of
SHA-256 and an encoding, not new cryptography). It is bound into the
NetBird offer permit, shown in its approval view, in `nebula approve`, in
`nebula host offers` and printed by the CLI entry, so the operator can
confirm that the approval names the key they entered without the key being
shown anywhere. 32 bits of a hash of a 122-bit random key reveal nothing
usable about the key.

*Trusted reference for the check value* (fix round 2). The comparison only
detects a substituted key if the operator's reference value does not come
from the server, because a compromised server can show any value on its
pages and forward another key to the executor, whose check value then
appears consistently in the approval view and in `nebula approve`:

- **CLI entry:** the reference is the value the executor-local CLI prints;
  the key never passes the server, so the server cannot substitute it.
  This is the entry the dialog, the CLI help and the guide recommend
  whenever the operator wants substitution protection (and for
  high-assurance hosts, as for the server-memory exposure).
- **Dialog entry:** the dialog's own display of the check value is
  convenience only and is labelled "shown by the server". The reference
  is a value the operator computes on their own machine from the key
  copied out of the NetBird dashboard, with standard tools that the guide
  and the dialog document, for example
  `printf 'nos-netbird-setup-key-check-v1\0%s' "$KEY" | sha256sum | cut -c1-8`
  after `read -rs KEY` in bash (the key read without echo and kept out of
  argv and shell history; a test vector in EN-16g checks that the
  documented command and the executor compute the same value; already in the
  canonical uppercase form the NetBird dashboard shows; the guide shows
  the uppercase fold for a key copied in lowercase). The operator compares
  this value with `nebula approve` on the executor host before the
  security-key touch. Without this step, dialog entry gives no protection
  against substitution by a compromised server; that is a named residual
  (threat table, "Compromised server substituting a setup key").
- Rejected: computing the check value in the browser (the JavaScript
  comes from the same server, so a compromised server can make it show
  the value of the key it forwarded), and comparing with a value from the
  NetBird dashboard (NOS cannot check what the dashboard displays for a
  key, and a prefix of the key would weaken the key's secrecy).

Whether dialog entry should stay available at all, given this residual,
is open question Q11 (amendment). Only Q11 options (b) and (c) keep the
key's integrity at least as strict as before; until the maintainer
decides, dialog entry is not enabled and NetBird offers use the CLI entry
(fix round 3; previously this ADR specified option (a) in the meantime).
The executor enforces this itself and refuses a key sent with
`CreateEnrollOffer` ("Entry"; fix round 4).

*Storage.* The executor stores the setup key only encrypted in the vault,
written in the same commit as the offer row (a vault that is locked refuses
the offer; a failed commit leaves neither). The offer row holds only the
vault reference and the check value. The key never exists in plaintext at
rest on the executor or the server: not in the offer store, not as rendered
script bytes (D2 "Retention"), not in a temporary file, not in a log, an
error, an audit record or an RPC response other than the full-script
download. It is never displayed: "Show script" renders the placeholder (D1
step 3), and no UI page, CLI output or `nebula approve` view shows it. On
the target host it is kept off disk as far as D1 step 3 and D5 describe,
with the residuals named there. (Previously: the offer row also held
NetBird's key ID for the revoke call.)

**Supply order.** A setup key is never rendered without an approval that
names it, and never kept longer than needed:

1. `CreateEnrollOffer` with NetBird (dialog entry, only once Q11 enables
   it; until then the executor refuses every create that carries a key,
   "Entry", and every NetBird offer takes the CLI path below; fix round
   4): the executor checks the limits (D2),
   validates the key, computes its check value, and in one commit seals the
   key into the vault and creates the offer in `awaiting_approval` with the
   vault reference, the check value and the fixed render inputs, including
   the placeholder hash (D2 "Retention"). Audit
   `netbird_setup_key_supplied` (offer, check value, client address, entry
   path `dialog` or `cli`; never the key). For CLI entry, step 1 is split:
   the web create makes the offer in `awaiting_key` with the same checks
   and fixed render inputs but no key; the CLI then validates, computes
   the check value and seals the key in one commit with `awaiting_key` →
   `awaiting_approval` ("Entry" above). A web create that selects CLI
   entry and still carries a key is refused, by the executor too.
2. It proposes the NetBird offer permit (D1 step 2).
3. On approval it first checks the offer's stored script template version
   against its own; on a difference it fails the offer, wipes the key and
   audits `enroll_script_template_changed`. Otherwise it reads the key
   from the vault, renders the placeholder and the full variant in memory,
   checks that they differ only in the setup-key line and that the
   placeholder matches the stored placeholder hash, and in one atomic
   compare-and-set stores the full render's SHA-256 and moves the offer
   `awaiting_approval` → `open`, **only if** the offer is still
   `awaiting_approval` and not expired. If the compare-and-set fails or a
   check fails, nothing is stored, the offer is failed (if not final
   already) and the key is wiped (see "Final state").

There is no create call, no `pending` record and no reconcile: nothing on
NetBird's side has to be found again by NOS. (Previously, "Creation order"
steps 1–5: a persisted `pending` record with key name, offer ID hash,
managed group and creation time window before the API create call; one
bounded create call; validation of the create response as untrusted
provider data with `netbird_setup_key_invalid`; storing the key ID before
any revoke; reconcile after restart or timeout by listing setup keys
(`GET /api/setup-keys`, unpaginated, `NetBirdKeyListMaxKeys` = 10 000,
`NetBirdKeyListMaxBytes` = 16 MiB, `NetBirdKeyGetMaxBytes` = 64 KiB),
matching by exactly the requested key name, with
`netbird_setup_key_pending`, `netbird_setup_key_created`,
`netbird_setup_key_reconciled`, `netbird_setup_key_unresolved` and
`netbird_setup_key_expired_unrevoked`, and the foreign-key residuals R1–R3
of spec 06. All of this needed the NetBird API and is dropped with it.)

**Final state.** (Previously "Revocation at the final state".)

1. **Wipe after use.** The setup-key secret is wiped from the vault in the
   same step that moves the offer to `downloaded` (the full script is
   never rendered again), and at the latest when the offer becomes final
   (`enrolled`, `expired`, `revoked`, `failed`), also straight from
   `awaiting_approval`. Audit `netbird_setup_key_wiped` (offer, check
   value, reason `downloaded` or the final state). A wipe that fails is
   retried with bounded backoff (first after 1 minute, then at most every
   5 minutes, also after an executor restart), shown as a dashboard notice
   and listed in `nebula host offers` until it succeeds; an offer whose
   wipe is outstanding is never rendered again. (Previously: wiped only at
   the final state.)
2. **No revoke by NOS, advice instead.** NOS cannot revoke the key. When a
   NetBird offer becomes final in any state (`enrolled`, `expired`,
   `revoked` or `failed`), the executor audits
   `netbird_setup_key_revoke_advised` (offer, final state, check value,
   whether the script was downloaded), and the offer page, the dashboard,
   `nebula host offers` and, for `revoked`, the output of
   `nebula host offer-revoke` show: "NOS cannot revoke NetBird setup keys
   or see which peers used them. Revoke the setup key with check value
   `<check>` in the NetBird dashboard unless it was one-off and is used
   up, and check NetBird for any peer that joined with it." For `enrolled`
   the text adds: "Only the enrolled host should have joined with this key;
   delete any other peer." The advice is given unconditionally in every
   final state, without asking whether the key was used, was one-off or
   was used by the enrolled host: NOS cannot know, and a leaked copy can
   have been used by another peer before the real host's join failed while
   the host still enrolled over a LAN endpoint ("Why a stolen setup key is
   bounded"). It stays on the dashboard until the operator dismisses it in
   a privileged session. (Fix round 3; fix rounds 1 and 2 showed no advice
   for `enrolled`, and the guide said a key that was not one-off must be
   revoked by hand after enrollment; before fix round 3 the text read
   "unless it was used; if the script was downloaded, also check NetBird
   for a peer that joined with it".) (Previously, in this order: wipe the secret,
   call revoke for the NetBird key ID unconditionally,
   `netbird_setup_key_revoked` and only then wipe the key ID, or
   `netbird_setup_key_revoke_failed` with retries until success or the
   key's expiry, then `netbird_setup_key_expired_unrevoked`; `pending`
   records included.)

So a supplied key always has either a completed wipe or an open, audited
and visible wipe retry on the NOS side, and every NetBird offer that became
final, `enrolled` included, carries an audited, visible request to revoke
the key in NetBird (fix round 3; previously "every NetBird offer that
ended without enrollment"). Whether the key is still valid in NetBird is the operator's
responsibility; the residual is in the threat table. (Previously: "a live
key always has either a successful revoke or an open, audited and visible
retry or reconcile record".)

**Peers from offers that did not enrol, or not only the enrolled host.**
(Heading before fix round 3: "Peers from offers that did not enrol".) NOS
cannot see NetBird peers. When a NetBird offer whose script was downloaded
becomes final in any state, a peer other than the enrolled host may have
joined with its key and stays in NetBird: for `failed`, `expired` or
`revoked` any such peer, and for `enrolled` a rogue peer that used a
leaked copy before the real host's join failed while the host still
enrolled over a LAN endpoint. The executor audits
`netbird_possible_orphan_peer` (offer, final state, check value, download
time and address), and the dashboard and `nebula host offers` list the
offer as a **possible orphan peer** with the advice to look for that peer
in the NetBird dashboard and delete or keep it there (for `enrolled`:
every peer that joined with the key other than the enrolled host). NOS
never deletes, keeps or attributes a peer itself. (Fix round 3; fix rounds
1 and 2 listed only `failed`, `expired` and `revoked`.) The revoke advice
of "Final state" also asks for this check when the script was not
downloaded, because a key typed into the dialog can leak before any
download.
(Previously: the executor looked up the peer through the API, recorded it
as an orphan peer with `netbird_peer_orphaned`, and the operator chose
**Delete** (typed delete call, `netbird_peer_deleted`; with a **NetBird
peer delete permit** when the peer was attributed only by the time-window
fallback) or **Keep** (`netbird_peer_kept`); unattributable peers were
reported as "unknown peer joined `nos-managed`". The NetBird peer delete
permit is no longer used.)

**Join on the host.** The script installs the NetBird client from the
official package repository if it is missing (repository signing key
fingerprint pinned in the script template, not fetched blindly), runs the
join with the setup key and the configured management URL, passing the
key only as D5 describes, and then **checks the join on the host** with
`netbird status`: it waits a bounded time (60 s) for the NetBird address
and prints it as the first address, or prints that no address appeared
and that the operator should check `netbird status` and the NetBird
dashboard. NOS itself does not verify the join: the operator confirms in
the NetBird dashboard that the host appears as a peer (in the managed
group) and picks the printed NetBird address as the endpoint in step 5 of
D1. That address is an operator hint like every printed address (spec 09);
the pairing code still decides the pin.

*SSH step.* For a host that is already pinned (for example one enrolled
without NetBird through D8), a later executor SSH step over the pinned
connection may run the same join with an operator-supplied key. It follows
the same rules: the key is entered and stored as above, travels on the SSH
session's standard input into a `0600` file under a `0700` `mktemp -d`
directory (or into the client's environment), never in the remote command
line, the directory is removed on every exit, the join is checked with
`netbird status` on the host, and the key is wiped and the revoke advice
given as in "Final state". It is a separate privileged action with its own
approval and ticket; this amendment fixes only its secret handling.

**Executor cross-check.** Removed 2026-11-12. (Previously: before the code
could be submitted with a NetBird endpoint, the executor read the peer
list through the API, found exactly one peer that joined with this offer's
key in exactly the managed group and suggested its NetBird IP; otherwise no
NetBird endpoint was offered.) The protection it gave the endpoint
suggestion is replaced by the operator's check in the NetBird dashboard;
the pin is protected by the pairing code as before.

**Peer attribution (Q8, decided 2026-11-12).** NOS does not attribute peers
to setup keys: there is no API access, so neither the API attribution nor
the time-window fallback is used. (Previously: whether the API can name the
setup key a peer joined with was to be checked before EN-12; failing that,
the time-window fallback "exactly one new peer in the managed group whose
registration time lies between the offer's approval and the key's recorded
use, and the key's use count is 1" applied, and deletes based on it needed
the NetBird peer delete permit.)

**Policy (operator-set, documented, not created by NOS).**

- Groups: `nos` (the NOS machine only) and `nos-managed` (enrolled hosts)
  (names decided, Q3; the managed group stays configurable, EN-06).
- One policy rule, **one direction**: source `nos` → destination
  `nos-managed`, TCP 22 (plus the hosts' SSH port if different). NetBird
  rules can be bidirectional; this one must not be.
- No rule from `nos-managed` to anything, including to `nos-managed` itself,
  unless the operator adds it deliberately for other reasons.
- Every new NetBird account has a group **`All`** that contains every peer
  and a **default policy that allows all traffic between `All` and `All` in
  both directions**. While that policy is enabled, a `nos-managed` peer can
  reach the NOS machine and every other peer, and the one-way assumption
  above is false. The operator must disable or delete the default policy
  (or restrict it so that it covers neither `nos` nor `nos-managed`) before
  using the NetBird option.
- The guide documents how to check this in the NetBird dashboard. NOS does
  not read policies (no API access); the NetBird option in the one-step
  dialog always shows a static reminder next to the checkbox: the default
  `All` ↔ `All` policy must be disabled, and only the one-way rule `nos` →
  `nos-managed` may cover these groups. (Amended 2026-11-12; previously:
  NOS read the policies through the API and warned when the default
  `All` ↔ `All` policy was enabled, when an enabled rule had `All` as
  source or destination together with a group containing `nos` or
  `nos-managed` peers, when a rule was bidirectional, or when a rule let
  `nos-managed` reach `nos` or other groups; read-only, Q3.)

**Why a stolen setup key is bounded.** If the setup key leaks (the
operator's dialog input on a compromised server, proxy log of the download,
the host's disk residuals), the holder can join peers into the key's auto
groups while the key is valid. For a key created as recommended above
(one-off, short validity, only `nos-managed`) that is one peer in
`nos-managed`, reachable by NOS on TCP 22 and by nothing else under the
documented policy (default `All` policy disabled); it cannot reach NOS. It
cannot get pinned, because the pairing code is bound to the real host's
key. Its use consumes a one-off key, so the real host's join fails visibly
in the script output ("netbird up failed", no NetBird address), and the
operator removes the rogue peer in the NetBird dashboard. The real host
can still enrol over a LAN endpoint, so the offer can end `enrolled`
although a rogue peer used the key; the revoke advice and the
possible-orphan notice are therefore also given for `enrolled` ("Final
state", "Peers from offers that did not enrol, or not only the enrolled
host"; fix round 3). NOS no longer
detects or deletes such a peer itself, and how long and for how many peers
a key is usable now depends on the properties the operator gave it in
NetBird. (Amended 2026-11-12; previously: "within the hour", enforced by
NOS, and the executor's cross-check reported the rogue peer, which the
executor deleted on confirmation, with the NetBird peer delete permit for a
time-window attribution.)

**Compromised server.** NOS mints no setup key, so a compromised server
cannot obtain a new key from NOS at all. What it can try with an open
privileged session:

- *Read the key the operator types into the web dialog.* The same class of
  exposure as before, when the key passed the server in the download
  stream; the CLI entry on the executor host avoids it (above).
- *Substitute another key* (for example one of an account it controls on a
  shared management service such as NetBird Cloud), so that the new host
  joins a network of the attacker's choosing. The key reaches a script only
  after a NetBird offer permit approved with the security key (HIGH, user
  verification; D1 step 2) whose binding includes the key's check value;
  `nebula approve` on the executor host shows the same binding. That
  binding names the key the executor received, so it detects substitution
  only against a reference the server cannot forge (D6 "Trusted reference
  for the check value"): with CLI entry the key never passes the server
  and cannot be substituted; with dialog entry the operator must compare
  `nebula approve` with the value they computed themselves, because the
  dialog's display of the check value comes from the server and a
  compromised server shows the value of the key it forwarded. Dialog entry
  without that comparison is not protected against substitution (only Q11
  options (b) and (c) close this; until Q11 is decided dialog entry is not
  enabled, fix round 3); the
  operator's check that the host appears in their own NetBird dashboard
  then detects it only after the join. With a self-hosted management
  server a key of another account does not join at all. (Fix round 2;
  previously: "the operator compares the check value with the one the
  dialog or the CLI entry showed", which for the dialog compared two
  server-controlled values.)
- *Flood offers.* The separate limits (2 open NetBird offers, 5 NetBird
  offers per hour, D2) still apply.

- *Seal secrets without a touch.* Creating a NetBird offer seals the
  supplied key into the vault before any security-key approval (CLI entry:
  when the CLI supplies it), so a compromised server with an open
  privileged session can make sealed secrets of its choice exist on the
  executor without a touch. Bounded by the NetBird limits (2 open, 5 per
  hour), the 15-minute expiry with wipe at the final state, and the
  approval required before any of them is rendered; it gives the server
  no read path to the vault (fix round 2).

The NetBird offer permit stays, now as the approval of exactly one
supplied key (check value) for exactly one offer. (Amended 2026-11-12;
previously: every setup key the executor created needed its own NetBird
offer permit, whose approval showed host, managed group and expiry, so a
compromised server could not mint keys silently; chosen over "only a lower
limit".)

**Token scope.** Removed 2026-11-12: NOS holds no NetBird token.
(Previously: NetBird's role model might not allow a token that can only
create setup keys; a service user with the admin role could also change
policies and groups, a widening of executor authority the maintainer
accepted in Q3.)

### D7: Download security

- **Origin:** the URL is built from the server's configured public origin
  (the reverse proxy's `https://<rp-id>`); plain HTTP is never offered. The
  command uses `curl --proto '=https' --tlsv1.2 -fsS` (or `wget --https-only`)
  and never `-k`. If the host does not trust the proxy's CA, the guide shows
  `--cacert`; with a NetBird setup key in the script, TLS verification is
  mandatory, because the hash check protects integrity but not the key's
  confidentiality.
- **Endpoint:** `GET /enroll/<offer-id>`, outside the authenticated UI. The
  server validates the ID's syntax, rate-limits per client address (10 per
  minute, 60 per hour; IPv6 clients per /64), calls the executor
  (`FetchEnrollScript`, server role) and streams the bytes. Responses: `200`
  with `Content-Type: text/plain; charset=utf-8`, `Content-Disposition:
  attachment`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`,
  `Content-Security-Policy: default-src 'none'; sandbox`; every refusal
  (unknown, expired, consumed, revoked, malformed, rate-limited, trusted
  proxy without a usable forwarded header) is the same
  `404` body with the same headers. The server does not log the path; the
  guide tells operators to exclude `/enroll/` from proxy access logs.
- **Reverse proxy.** A script with a setup key passes through the reverse
  proxy, whose default buffering (nginx) spills responses larger than its
  memory buffers to `proxy_temp_path` on disk; the 64 KiB script limit
  allows that. The shipped reverse-proxy configuration and the guide
  therefore require for `/enroll/` (and the UI's "Download in browser" and
  "Show script" routes): `proxy_buffering off`,
  `proxy_max_temp_file_size 0`, no proxy cache, and the access-log
  exclusion above. The server additionally sends `X-Accel-Buffering: no`
  on these responses. The one-step create route, whose request body
  carries a setup key typed into the dialog (D6 "Entry"), gets the same
  rules for the request direction: `proxy_request_buffering off`,
  `client_body_in_file_only off`, a client body buffer
  (`client_body_buffer_size`) at least as large as the create form's size
  limit `onestepFormMax` (8 KiB, D6 "Input bounds") and a
  `client_max_body_size` for that route no larger than that buffer, so
  nginx refuses a larger body instead of writing it to
  `client_body_temp_path` (fix round 3; previously "a client body buffer
  at least as large as the create form's size limit", which named no
  value), no access log with request bodies, and no
  WAF or body-logging module that records the body (fix round 2). A proxy configured otherwise is an operator error the
  guide warns about; the NetBird option's key is then one-off and
  short-lived only if the operator created it so (D6), and NOS asks the
  operator to revoke it when the offer becomes final, `enrolled` included
  (fix round 3, previously "ends without enrollment"; amended
  2026-11-12; previously "still one-off, short-lived and revoked at the
  final state").
- **Client address behind the reverse proxy.** The server sits behind the
  reverse proxy, so the TCP peer (`r.RemoteAddr`) is usually the proxy. A
  new server setting, **trusted proxies** (list of IP addresses, default
  empty, validated at startup), decides whose forwarded headers count:
  - **Only proxies, never clients.** Any address in the list can name any
    client address in `X-Forwarded-For`, so a list entry that also covers
    clients (for example the LAN or the NetBird range) would let such a
    client drain another operator's bucket. Entries are therefore single
    addresses (bare, `/32` or `/128`); a network prefix is accepted only in
    the separate setting **trusted proxy networks**, documented as "networks
    that contain reverse proxies and no clients" (for example a container
    network used only by the proxy), and logged at startup with that
    statement. Any other prefix fails startup.
  - **Normalisation.** Every address is normalised before it is compared
    or used, the same way for the TCP peer, every `X-Forwarded-For` entry
    and every configured trusted-proxy entry (`net/netip`): a port is
    stripped (`r.RemoteAddr` and entries of the form `a.b.c.d:port` or
    `[v6]:port`), an IPv6 zone ID is stripped, and an IPv4-mapped IPv6
    address (`::ffff:10.0.0.1`) is unmapped to its IPv4 form. So a
    dual-stack listener that sees the proxy as `[::ffff:10.0.0.5]:41234`
    still matches a trusted proxy configured as `10.0.0.5`. A trusted-proxy
    entry that does not parse fails startup. "Trusted proxy" below means an
    address in either setting.
  - If the TCP peer is not a trusted proxy, `X-Forwarded-For` and
    `Forwarded` are ignored and the peer address is the client address.
  - If the TCP peer is a trusted proxy, the server reads only
    `X-Forwarded-For` (`Forwarded` is never used; at most 1 KiB, at most 16
    entries, each a syntactically valid IP after normalisation; several
    header lines count as one comma-joined list) and walks it from the
    right, skipping entries that are themselves trusted proxies; the first
    untrusted entry is the client address. Entries left of it are
    client-supplied and ignored for the address, but still count for size,
    entry and syntax checks (never a partial parse).
  - **A trusted proxy without a usable header is refused.** If the header
    is missing, larger than 1 KiB, has more than 16 entries, contains an
    entry that is not a valid IP, or contains only trusted proxies, the
    request gets the uniform `404` at once: the executor is not called, the
    offer is not touched, and **no** rate-limit bucket is charged, neither
    the proxy's address nor any address from the header. The refusal is
    counted in a metric and logged without the path. There is no fallback
    to the proxy's peer address, so behind an appending proxy (for example
    nginx `$proxy_add_x_forwarded_for`) a client that sends a long or
    garbage header only refuses its own request and cannot exhaust a bucket
    shared by other operators. A separate global ceiling for such refusals
    is not needed because they cost no executor call.
  - The per-client rate limit (10 per minute and 60 per hour per client
    address, IPv6 clients bucketed per /64 after normalisation) and the
    `enroll_script_downloaded` audit record use this client address; the
    audit record also carries the peer address and whether the forwarded
    header was used.
  - **Bounded rate-limit table.** The buckets (one per IPv4 address, one
    per IPv6 /64) live in a table with a fixed maximum size (named
    constant, default 4096 buckets). When it is full, the least recently
    used bucket is evicted (LRU) to make room; a request is never refused
    because the table is full. Eviction fails open for the evicted client
    (its counters restart), which is acceptable because the limit is
    defence in depth: offer IDs are ≥ 128 bits and single use. A client
    with a large IPv6 allocation can therefore reset buckets but neither
    grow memory without bound nor lock other operators out.
  - The shipped reverse proxy configuration should set (overwrite, not
    append) `X-Forwarded-For` to the address it saw; with an appending proxy
    the rules above still hold. If the endpoint is enabled and no trusted
    proxy is configured while the server is not reachable directly, all
    clients share the proxy's bucket: the server logs a startup warning in
    that case (enrollment enabled, trusted proxies empty, listener on
    loopback, a private address or a wildcard address `0.0.0.0` / `::`),
    and the guide makes the setting part of the reverse-proxy setup.
  - **Same client address for the whole flow.** The authenticated UI
    requests of the enrollment flow (create offer, NetBird offer approval,
    "Show script", browser download, code submission, approval, commit,
    revoke, dismissal of the setup-key revoke advice; amended 2026-11-12,
    previously "orphan-peer decision") determine the operator's client address
    with the same rule and pass it to the executor, so every audit record of
    the flow (`enroll_offer_created`, `enroll_offer_approved`,
    `enroll_code_rejected`, `enroll_code_mismatch`, `enroll_paired_proposed`,
    `host_enrolled`, `enroll_offer_revoked`, `inventory_endpoint_added`,
    and the setup-key records triggered by an operator action, such as
    `netbird_setup_key_supplied` and `netbird_setup_key_rejected`; amended
    2026-11-12, previously also `netbird_peer_deleted` and
    `netbird_peer_kept`) carries the client address and the
    peer address, not only the proxy's address. For these authenticated
    requests a trusted proxy without a usable header is refused like the
    download (`400` with the UI's normal error page; no state change).
  Other routes keep their current address handling and rate limits until a
  separate decision; this ADR only adds the shared client-address function
  and uses it for the routes above.
- **Integrity:** the SHA-256 of the script is computed by the executor and
  shown on the offer page; the command checks it before running. A changed
  script (proxy, cache, wrong offer) does not run.
- **No `curl | sh`:** the command writes a file, checks the hash, then runs
  it; the operator can read it in between.
- **New exposure:** this is the first unauthenticated endpoint that returns
  executor-generated content. It returns only scripts of open offers, at most
  once each, and the content is public except for the optional setup key.
  Spec 02 and 03 must record it (EN-02).
- **Residual:** a compromised server can serve a different script and show
  its hash, and so run code as root on the new host. The same server can
  already show a manipulated script today when the operator copies from the
  web UI; with the CLI path the script comes from the executor host. For
  high-assurance hosts the guide recommends `nebula host enroll-script` or
  comparing the hash with `nebula host offers` on the executor host. The
  maintainer accepted this residual risk with the documented CLI
  alternative (Q6); the CLI hash display is not mandatory per offer.

### D8: Hosts that cannot reach NOS

A remote host may not reach the NOS origin before it is in NetBird (for
example the IONOS VPS when NOS is LAN-only). Then the operator uses
**Download in browser** on the offer page and copies the file once (scp,
paste); the rest of the flow is unchanged. The browser download goes through
the RPC `DownloadEnrollScript` (server role, only for the session that
created the offer); it consumes the offer exactly like `FetchEnrollScript`
(same single use, same hash, same uniform refusal) and the server sends the
D7 download headers (`Cache-Control: no-store`, `nosniff`, `attachment`,
`Content-Security-Policy: default-src 'none'; sandbox`).

**Not for NetBird offers.** A file in the operator's Downloads folder and a
hand-copied file on the host are outside the `umask 077`, `mktemp -d` and
`trap` guarantees of D1 step 3, so a script carrying a setup key must never
take this path. The executor refuses `DownloadEnrollScript` for an offer
with NetBird (uniform refusal; the offer is not consumed and stays usable
for the normal download), and the UI does
not show the button for such offers. A remote host that cannot reach the
NOS origin joins NetBird by hand first (today's step 4, with a setup key the
operator creates in NetBird), and then gets an offer without the NetBird
option, through the browser download or, once the NOS origin is reachable,
the normal command. The maintainer accepted this manual NetBird step for
such hosts for now (Q9); a variant in which a keyless downloaded script
asks for the setup key at run time would need a later ADR and is not part
of this decision. Making the NOS origin reachable for this purpose is not part of
this ADR either.

### D9: Compatibility

- `nebula host enroll-script`, `nebula host probe/pin/test`, `known_hosts`

## Non-goals

- No agent, callback or polling from the host to NOS.
- No automatic trust on first use: an endpoint is never pinned without a
  matching code and an approval.
- No creation of NetBird policies or groups by NOS.
- No NetBird Management API access by NOS: no token, no setup-key
  creation or revocation, no peer or policy reads, no peer deletion
  (added 2026-11-12).
- No change to how existing pins, blocks and re-pins work.
- Windows, BSD and network devices (ADR 0010).

## Decisions of the maintainer (2026-11-11)

The open questions Q1–Q9 of the proposed ADR were decided on 2026-11-11 as
follows; D1–D9 above already reflect these decisions.

- **Q1: Code length and format.** 25 characters: 24 Crockford base32 data
  characters (120 bits) plus 1 Crockford check character (mod 37, symbols
  `0-9A-Z` without `I L O U`, plus `*~$=U`), shown as
  `XXXXX-XXXXX-XXXXX-XXXXX-XXXXC` in groups of five. Input is
  case-insensitive with Crockford folding (`O` → `0`, `I`/`L` → `1`);
  hyphens and spaces are ignored. The script computes the code as two
  60-bit halves in POSIX shell arithmetic and the check value as
  `((hi mod 37) · (2^60 mod 37) + lo mod 37) mod 37` without a 120-bit
  number (D3). (Previously recommended: 60 bits, 12 characters + check,
  `XXXX-XXXX-XXXX-C`.)
- **Q2: Offer lifetime.** 15 minutes in total for download and code
  submission is the default (D2). Note: with the 120-bit code a later
  extension of the total window up to 60 minutes is admissible (grinding
  chance ≈ 2^-68 at 10^12 keys/s, D3); it needs only a change of the named
  constant, not a new ADR. No separate window after the download.
- **Q3: NetBird token scope and group names.** A NetBird service user in
  the executor vault is accepted. Group names `nos` and `nos-managed`. NOS
  only reads policies and warns; it never creates or changes them. Whether
  the reference lab uses self-hosted management or NetBird Cloud (TLS trust
  setting) is established in the lab test before EN-12. *Superseded in
  part on 2026-11-12 (Q8 below):* there is no service user, no token and
  no policy read; the group names stay as the documented, operator-set
  policy; whether the lab uses self-hosted management or NetBird Cloud
  still matters for the management URL and for the substitution residual
  (threat table).
- **Q4: Inventory entry in the same step.** Yes: the one-step dialog may
  create the inventory host as a normal inventory entry shown "not
  enrolled" until the pin; if the offer fails it is deleted again only when
  the operator chooses so.
- **Q5: Platforms.** Windows and BSD are out of scope. Proxmox VE nodes are
  Debian and included.
- **Q6: Script authenticity against a compromised server.** The residual
  risk of D7 is accepted with the documented CLI alternative
  (`nebula host enroll-script`, hash comparison with `nebula host offers`);
  a CLI hash display is not required for every offer.
- **Q7: Mismatch handling.** One well-formed mismatch ends the offer
  (`failed`); the check character catches typos. No second submission.
- **Q8: Peer attribution in NetBird. Decided 2026-11-12:** NOS does not
  talk to the NetBird Management API. The operator creates the setup key in
  the NetBird dashboard as before, the host joins with it and then appears
  in NetBird; NOS works only through the enrollment script or an SSH step.
  There is no peer attribution, neither by the API nor by the time-window
  fallback; EN-11 (typed NetBird API client) is dropped. Details in
  "Amendment 2026-11-12: no NetBird Management API". (Previously, open:
  whether the management API can attribute a peer to the setup key it
  joined with was to be checked against the real API before EN-12; if it
  could not, the time-window fallback of D6 was accepted, with the NetBird
  peer delete permit for deletes based on it.)
- **Q9: NetBird for hosts that cannot reach NOS.** For now such a host
  joins NetBird by hand (D8). A keyless downloaded script that reads the
  setup key at run time would need a later ADR.

## Amendment 2026-11-12: no NetBird Management API

**Decision of the maintainer (2026-11-12, on Q8 / EN-11).** NOS does not
talk to the NetBird Management API. The operator creates the setup key in
the NetBird dashboard as before; the host joins with this key and then
appears in NetBird. For the join NOS works only through the enrollment
script or an SSH step. EN-11 (typed NetBird API client) is dropped. Q8 is
decided by this (see "Decisions of the maintainer").

**New rules** (worked into D1–D9 above):

1. The operator enters a one-off setup key per NetBird offer in the
   one-step dialog (masked input) or with the executor-local CLI
   (non-echoing input or standard input, never argv or environment);
   dialog entry is not enabled until Q11 is decided, so until then the
   CLI is the only entry, and the executor refuses a key sent with
   `CreateEnrollOffer` (D6 "Entry"; fix round 3, executor gate fix round
   4). The CLI only supplies the key of an offer that a web session created in
   `awaiting_key`; it never creates an offer and never becomes a binding
   (D2 "Binding", D6 "Entry"; added in fix round 1). The
   dialog, the CLI help and the guide recommend creating it in NetBird
   one-off, with a short validity (recommended 1 hour, never more than
   1 day), with only the managed group as auto group and ephemeral only
   when wanted (D6 "Operator-supplied setup key").
2. The executor treats the key as a secret: strict format check before
   storage (refusal audited without the value), stored only encrypted in
   the vault, never displayed (only a 32-bit check value), never logged,
   never in an error, audit record or RPC response other than the
   full-script download, wiped at the download and at the latest at the
   final state, a failed wipe retried and shown (D6 "Storage", "Final
   state").
3. The script or the SSH step passes the key to the NetBird client only
   through a `0600` key file under a `0700` `mktemp -d` directory or the
   client's environment, never in argv; an SSH step carries it on the
   session's standard input, never in the remote command line (D5, D6
   "Join on the host").
4. The join is checked on the host with `netbird status`, not through the
   API; the operator confirms the peer in the NetBird dashboard (D6 "Join
   on the host").
5. NOS cannot revoke the key: when a NetBird offer becomes final in any
   state (`enrolled`, `revoked`, `expired`, `failed`) it wipes the key,
   audits `netbird_setup_key_revoke_advised` and tells the operator in the
   UI and the CLI to revoke it in NetBird and to check for peers that
   joined with it (D2 "Revocation", D6 "Final state"; fix round 3,
   previously "on revoke, expiry or failure", without `enrolled`).
6. The NetBird offer permit stays (HIGH, user verification) and now binds
   the supplied key's check value instead of managed group, ephemeral flag
   and setup-key expiry (D1 step 2, D6 "Compromised server").
7. Raw key input is bounded before trim and validation
   (`SetupKeyInputMaxBytes`, `onestepFormMax`), and refused keys are
   limited per executor and hour (`NetBirdSetupKeyRejectsPerHour`),
   with separate budgets for keys sent through the server and for the
   CLI entry (D6 "Input bounds", "Rejection limit"; fix round 3,
   per-source budgets fix round 4).

"Fix round 3" in this amendment is the review follow-up to #540 (the
amendment's earlier fix rounds 1 and 2 are named as such above); "fix
round 4" is the review follow-up to fix round 3.

**Secret handling compared with before.** Unchanged or stricter: vault
only, never displayed or logged, placeholder in "Show script", no browser
download for NetBird offers, `umask 077`/`mktemp -d`/`trap` on the host,
never argv, one security-key approval per key before it is rendered; the
key is now wiped at the download instead of only at the final state, and
the executor holds no NetBird token at all. Weaker, because NOS can no
longer act in NetBird: the key's lifetime, use count and groups are the
operator's choice and NOS cannot revoke the key, detect a rogue peer or
delete a peer; these residuals are named in the threat table and answered
with recommendations, the audited revoke advice and the possible-orphan
listing. Also weaker (fix round 2, previously not listed here):

- *Exposure in transit:* a key typed into the web dialog passes the
  server and the reverse proxy in memory (as the download stream did
  before); the D7 proxy rules now cover the create route; the CLI entry
  avoids both.
- *Integrity:* before, NOS created the key itself, so a compromised
  server could not substitute it. Now a key typed into the dialog can be
  substituted by a compromised server, and the check value detects that
  only if the operator compares `nebula approve` with a value computed on
  their own machine (D6 "Trusted reference for the check value"); the CLI
  entry is not affected. Open question Q11: only its options (b) and (c)
  restore "at least as strict as before"; until it is decided, dialog
  entry is not enabled (fix round 3), and the executor itself refuses
  any key sent with `CreateEnrollOffer`, so the gate does not depend on
  the server it protects against (fix round 4).
- *Revoke advice:* before, NOS revoked the key in every final state. The
  advice that replaces it is now also given for `enrolled`, together with
  the check for other peers (fix round 3; fix rounds 1 and 2 gave none for
  `enrolled`).
- *Input bounds:* raw key input and the create body now have named bounds
  and refused keys an hourly limit (fix round 3), counted per source so
  that keys sent through the server cannot lock out the CLI entry (fix
  round 4); before, NOS took no key as input at all.
- *Secrets before approval:* before, no key existed until the security-key
  approval. Now a NetBird offer seals the supplied key at creation (CLI:
  at entry), so a compromised server with an open privileged session can
  make sealed secrets exist in the vault without a touch, bounded by the
  NetBird limits, the 15-minute expiry and the wipe; none is rendered
  without the approval.
- *Operator client:* NOS no longer claims that the browser does not save
  the field; whether a browser or password manager keeps the typed key is
  the operator's client residual (D6 "Entry").

**Open question Q11 (fix round 2, revised in fix round 3; for the
maintainer): dialog entry and key substitution.** Still open: no
maintainer decision on Q11 is recorded in this ADR or in
`docs/implementation/one-step-enrollment.md`. The decision of 2026-11-12
allows the key in the web dialog. A compromised server can substitute
such a key, and only a check value the operator computes outside NOS
detects it. Options: (a) keep dialog entry, label the dialog's check
value "shown by the server", and document the workstation computation as
an optional comparison step before the touch (D6 "Trusted reference for
the check value"); (b) keep dialog entry but make the NetBird offer
permit's approval in `nebula approve` require the operator to type the
self-computed check value, so the comparison cannot be skipped; (c) drop
dialog entry and require the CLI entry for every NetBird offer.

*Review point (fix round 3).* Only (b) and (c) keep the setup key's
handling at least as strict as before. Before the amendment NOS created
the key itself, so a compromised server could not substitute it. With
(a), dialog entry, the default path, is weaker for integrity: a
substituted key is detected only if the operator performs a step outside
NOS that nothing enforces. With (b) the approval cannot be given without
a match against a value the server cannot forge; with (c) the key never
passes the server. That substitution is in the same class as the
existing residual "a compromised server can serve a malicious script"
(threat table, "Compromised server") holds for root on the new host, but
does not make (a) as strict as before for the setup key itself.

*Until Q11 is decided* (fix round 3): dialog entry is not enabled; a
NetBird offer takes its key only by the CLI entry, which is the same
under all three options and keeps the key off the server. The executor
enforces this with the compile-time constant
`NetBirdDialogKeyEntryEnabled` = `false`: `CreateEnrollOffer` refuses
every request that carries a key, before validation and vault, so a
compromised server cannot get a key of its choice sealed (D6 "Entry";
fix round 4; previously only the server refused it). Enabling (a) or
(b) changes that constant together with the recorded decision. D6 "Entry",
"Input bounds", "Validation", "Rejection limit" and every other rule for
the dialog stay specified so that (a) or (b) can be enabled without a
further ADR change; (b) adds only the typed comparison in
`nebula approve`. With (b) or (c) the dialog's check value display,
labelled "shown by the server", stays convenience only.

(Previously, fix round 2: "**Recommendation: (a) now, (c) as the guide's
default for high-assurance hosts.** (a) matches the decision as given and
keeps the extra exposure named; (b) adds a typed step to every NetBird
enrollment and still fails when the operator computes from the wrong
copy; (c) changes the decision of 2026-11-12, so it needs the
maintainer." Withdrawn in fix round 3 because (a) falls short of "at
least as strict as before"; the cost of (b) remains one typed 8-hex value
per NetBird enrollment, and a value computed from a wrong copy of the key
does not match and refuses the approval, which fails safe. Which of (b)
and (c) to take, or to accept (a) with its named residual, is the
maintainer's choice.)

**Open question Q10 (fix round 1, for the maintainer): link of the CLI
key entry to an offer.** The decision of 2026-11-12 names the key entry
but not how a CLI-entered key reaches an offer that D2 binds to a web
session. Options: (a) the web session creates the offer in a new state
`awaiting_key` and the CLI only supplies the key for it; (b) the CLI
creates the offer itself, which needs a new kind of binding (a CLI-created
offer that some web session later claims for code submission and commit);
(c) the CLI seals a key without an offer and the web dialog picks it up,
which leaves a secret in the vault with no offer lifecycle, expiry or
wipe. **Recommendation and what this ADR now specifies: (a)**, because it
is the strictest: D2 "Binding" stays exactly as it is (one creating web
session, no claim step), the CLI gains no authority beyond supplying one
key for one existing offer, every sealed key belongs to an offer with
its expiry and wipe, and the permit's check value ties the CLI entry to
the web approval. If the maintainer prefers to drop the CLI entry
instead, D6 "Entry" loses its second bullet, `awaiting_key` and
`OfferMaxRejectedSetupKeys` go away, and the server-memory exposure of
the dialog stays the only entry path's residual; because dialog entry
is not enabled until Q11 is decided, that choice also needs a Q11
decision enabling dialog entry (option (a) or (b)), otherwise NetBird
offers would have no entry path at all (fix round 6; previously this
sentence did not name the Q11 gate).

## Consequences

- Enrollment of a single host becomes: one dialog, one command on the host,
  one code typed into NOS, one security-key touch (two with NetBird: one
  to approve the supplied setup key, one to pin; amended 2026-11-12,
  previously "to release the setup key"). With NetBird the operator also
  creates the setup key in the NetBird dashboard and revokes it there when
  NOS advises it. The fingerprint
  comparison is done by the executor against a value the operator carried,
  not by eye.
- Host-key pinning is not weakened: the same pin, the same HIGH approval,
  the same re-probe and the same mismatch block apply; precomputation is
  ruled out by the salt.
- NOS gains its first unauthenticated content endpoint. With NetBird it
  holds one short-lived operator-supplied secret per offer, but no
  provider credential and no egress destination for the executor (amended
  2026-11-12; previously "a second provider credential and an egress
  destination for the executor").
- The pairing code's strength depends on the operator's own session to the
  host; the documentation must say that plainly.
