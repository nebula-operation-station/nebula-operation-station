# ADR 0013: One-step host enrollment with pairing code and optional NetBird join

Status: proposed, 2026-11-11. Awaiting the maintainer's decision on the open
questions below; do not merge before that discussion. Nothing here is
implemented; the ticket plan is
[`docs/implementation/one-step-enrollment.md`](../implementation/one-step-enrollment.md).

## Context

Maintainer request of 2026-11-11: "SSH to the host, run a script, enter the
key/code in NOS, done", also for remote hosts such as the IONOS VPS that NOS
reaches over NetBird.

Today enrollment ([admin guide §7](../admin/guide.md#7-adding-and-enrolling-hosts),
[spec 08](../spec/08-ssh-transport.md)) takes these steps:

1. Create the inventory entry (web UI).
2. On the executor host run `nebula host enroll-script --from ADDR,...`
   (`cmd/nebula/enroll.go`), read the script, copy it to the new host and run
   it there as root. It creates the `nebula` user, installs the executor's
   public key with `from="…",no-agent-forwarding,no-port-forwarding,no-X11-forwarding`,
   the NOPASSWD sudo rule, the sshd `AllowUsers`/`AllowGroups` drop-in and the
   tmpfiles rule, and prints the host key fingerprints.
3. Pin: either `nebula host probe/pin/test` on the executor host, or
   **Enroll hosts** in the web UI (`ProposeEnroll`/`CommitEnroll`: the
   executor probes, the admin compares every fingerprint with
   `ssh-keygen -lf` output from the host, approves with the security key as a
   HIGH action with user verification, the executor re-probes, pins only
   unchanged keys and tries a login).
4. For a host outside the LAN: install and join NetBird by hand first, find
   its NetBird IP, and put that IP into the inventory endpoint.

Steps 2 and 3 are the friction: a file copied by hand between two machines,
and a 43-character base64 fingerprint compared by eye. The comparison is what
protects against a machine in between, so it must not simply be dropped.

Constraints that shape every decision below:

- The executor alone holds SSH keys and vault secrets (spec 02, 06). The
  server is not trusted for approval: WebAuthn binds the permit, not the page.
- A host key is pinned per host; every endpoint must present it; a mismatch
  blocks the host until an approved re-pin (spec 08, `internal/executor/hostkeys.go`).
- Everything a host reports is untrusted input (spec 09).
- No new dependencies, no self-written cryptography, no `ssh` binary or shell
  from Go production code (`AGENTS.md`).
- Profiles never contain secret values; a NetBird setup key is an executor
  vault entry (ADR 0008 §1). Provider tokens are executor-held, least
  privilege, typed calls only, no generic HTTP proxy (ADR 0006).

## Terms

- **Enrollment offer:** an executor-held, single-use record that authorises
  one script download and one pairing for one inventory host. Identified by
  an **offer ID**.
- **Offer salt:** 256 random bits generated by the executor per offer,
  embedded in the script; it binds the pairing code to this offer.
- **Pairing code:** a short code the script prints, derived from the host's
  ed25519 host key and the offer salt (D3). The operator carries it from the
  host's terminal to the NOS web UI.
- **Paired enrollment permit:** the HIGH permit that pins the key that
  matched the code (D4). It replaces the eye comparison of fingerprints, not
  the approval.

## Decisions

### D1: Flow

1. **Web UI, "Add host (one step)".** The operator enters or picks the
   inventory host (open question Q4), SSH user (default `nebula`), credential
   reference (default `nebula-default`), sudo yes/no, and whether to join
   NetBird (D6, only offered when a NetBird token is configured). An open
   privileged session (ADR 0007) is required.
2. **Offer.** The server calls the executor (`CreateEnrollOffer`). The
   executor creates the offer: offer ID (D2), salt, expiry **15 minutes**,
   bound to the host ID, SSH user, credential reference, the web session that
   created it and, with D6, a fresh NetBird setup key. The executor renders
   the script (D5) and stores its SHA-256. Audit `enroll_offer_created`.
3. **Command.** The UI shows one command block, for example:

   ```
   curl --proto '=https' --tlsv1.2 -fsS -o nos-enroll.sh \
     https://nos.example.lan/enroll/<offer-id>
   echo '<sha256>  nos-enroll.sh' | sha256sum -c - && sudo sh nos-enroll.sh
   ```

   Download, hash check, then run; never `curl | sh` (D7). A "Show script"
   link shows the same bytes for review; reading it does not consume the
   offer. A "Download in browser" fallback exists for hosts that cannot reach
   the NOS origin (D8).
4. **On the host** the operator runs the command as root (in their existing
   SSH session or on the console). The script is today's enrollment script
   plus, optionally, the NetBird join (D6), and at the end it prints:

   ```
   NOS pairing code:  K7QX-M2PD-9HTR-4
   Addresses:         192.168.0.21  fd00::21  100.92.14.7 (netbird)
   ```

5. **Pairing in NOS.** The UI page of the offer (still open in the
   operator's session) asks for the code and the endpoint to use: one of the
   inventory endpoints, or one of the printed addresses typed or picked by
   the operator. The server passes code and endpoint to the executor
   (`SubmitPairingCode`). The executor probes the endpoint (no credential
   sent), takes the presented **ed25519** host key, computes the code from it
   and the offer salt, and compares in constant time.
   - Match: the executor proposes a paired enrollment permit (D4). The UI
     shows host, endpoint, SSH user, credential, full SHA-256 fingerprint and
     "matches the pairing code from the host"; the operator approves with the
     security key, exactly like **Enroll hosts** today (HIGH, user
     verification).
   - Mismatch: see D3 failure handling.
6. **Commit.** As in `CommitEnroll`: the executor re-probes the endpoint,
   pins only if the presented key is still the approved one, then tries a
   login when the keys are unlocked and reports the result. The offer becomes
   `enrolled`. Hosts pinned this way get no criticality record (they count as
   HIGH until set on the executor host), as today.

Nothing is sent from the host to NOS by the script (no callback, no token in
the other direction). The only channel host → NOS is the operator.

### D2: Offer ID and offer lifecycle

- **Offer ID:** 128 random bits or more from `crypto/rand` (recommended 160
  bits, 32 characters of lowercase RFC 4648 base32 without padding), generated
  by the executor. It is a capability for one download; the executor stores
  only its SHA-256, never the ID itself, and logs only the first 8 hex
  characters of that hash.
- **States:** `open` → `downloaded` → `pairing_proposed` → `enrolled`;
  from any non-final state → `expired`, `revoked` or `failed`. Final states
  never return to `open`.
- **Expiry:** 15 minutes from creation for the download and the code
  submission (Q2). An approval started before expiry may finish within the
  permit's own lifetime; a commit after the permit expired fails.
- **Single use:** the first successful download moves the offer to
  `downloaded`; a second download returns the same `404` as an unknown ID
  (no oracle). One well-formed code submission is accepted per offer (D3).
- **Binding:** only the web session that created the offer may submit the
  code, approve and commit; another session (also of the same user) sees the
  offer read-only and may revoke it. Lock, restart or session end of the
  privileged session does not resurrect it.
- **Revocation:** the operator can revoke an open offer in the UI; the
  executor-local CLI can list and revoke offers (`nebula host offers`,
  `nebula host offer-revoke`). Revoking also revokes the NetBird setup key if
  it is unused (D6).
- **Limits** (named constants in the implementation): at most 10 non-final
  offers per executor, at most 30 offers created per hour, at most 5 probes
  per offer, at most 3 rejected (malformed) code submissions per offer.
- **Audit** (executor and server, no secret values): `enroll_offer_created`,
  `enroll_script_downloaded` (with the client address the server saw),
  `enroll_code_rejected` (malformed), `enroll_code_mismatch`,
  `enroll_paired_proposed`, `host_enrolled`, `enroll_offer_expired`,
  `enroll_offer_revoked`, `netbird_setup_key_created`,
  `netbird_setup_key_revoked`, `netbird_peer_joined`.
- **Retention:** final offers are kept as audit records without salt, script
  and setup key reference; salt, script bytes and setup key are wiped when the
  offer becomes final.

### D3: Pairing code

**Construction (recommended; Q1).**

```
digest = SHA-256( "nos-enroll-pair-v1" || 0x00 || salt[32] || ed25519 host key blob )
code   = first 60 bits of digest, as 12 Crockford base32 characters,
         plus 1 Crockford check character (mod 37), shown as XXXX-XXXX-XXXX-C
```

The host key blob is the SSH wire format of the public key (the bytes the
SHA-256 fingerprint is computed over), so the code is "derived from the host
key fingerprint" with the offer salt mixed in. The script computes it with
coreutils (`base64 -d`, `sha256sum`, `basenc`), present on every supported
host (Debian 12, Ubuntu 22.04/24.04, Proxmox VE); the executor computes it
with `crypto/sha256`. This is a composition of SHA-256 and an encoding, not
new cryptography; shared test vectors bind script and Go code (EN-03).

The script reads the key sshd actually serves: the `hostkey` lines of
`sshd -T` whose public half is `ssh-ed25519`, falling back to
`/etc/ssh/ssh_host_ed25519_key.pub`. A host without an ed25519 host key gets
no code and a message to use the classic path (§7.2); one-step enrollment
pins ed25519 only.

**Why salted, not the plain fingerprint.** A plain truncated fingerprint is
a function of a public, long-lived value: anyone who can connect to the
host's sshd before enrollment can read its key, compute the code and grind a
key with the same code at leisure, so a 15-minute window would bound
nothing. With the salt, grinding can start only when the attacker knows the
salt, which is in the script and the offer page, and must finish before the
executor's probe, inside the 15-minute offer lifetime.

**Entropy versus grinding.** The attacker needs a second preimage of the
60-bit truncation (an ed25519 key whose code equals the host's), not a
collision: expected work 2^60 ≈ 1.2·10^18 key generations plus hashes.

| Code bits | Grind rate (keys/s) | Expected time |
| --- | --- | --- |
| 40 (8 chars) | 10^9 (one large GPU, optimistic) | ≈ 18 minutes: too weak |
| 60 (12 chars) | 10^9 | ≈ 37 years |
| 60 (12 chars) | 10^12 (large cluster) | ≈ 13 days; P(success in 15 min) ≈ 2^-10 |
| 80 (16 chars) | 10^12 | ≈ 38,000 years |

Recommendation: **60 bits minimum, 12 characters + check character.** With
the salt this leaves an attacker a chance below 1 in 1,000 even with a
cluster-scale budget dedicated to one enrollment, and that attacker must also
have learned the salt and sit in the network path at probe time. 80 bits (16
characters) is the conservative alternative if the maintainer prefers typing
four more characters (Q1).

**Online guessing does not apply.** The operator types the code; an attacker
gains nothing from submitting codes. The probe limit (5 per offer) bounds the
other direction: an attacker in the path who answers each probe with a fresh
random key has a 2^-60 chance per probe.

**Failure handling.**

- *Malformed code* (wrong length, characters outside Crockford base32, wrong
  check character): rejected before any probe, counted (max 3), audit
  `enroll_code_rejected`. The check character catches typing errors so that
  a typo is not mistaken for an attack.
- *Well-formed code that does not match the presented key*: the offer
  becomes `failed`, the endpoint is not pinned, the NetBird setup key is
  revoked if unused, audit `enroll_code_mismatch` with the presented
  fingerprint and endpoint, dashboard notice and notification as for a host
  key mismatch. The UI states: "The host at this endpoint presents a key that
  does not match the code from the host. Either the endpoint is a different
  machine, or something is in between. Check the endpoint, then create a new
  offer." Re-offer means a new salt, so the script must be run again (it is
  idempotent) and prints a new code.
- *Probe failure* (unreachable, timeout, no ed25519 key): not counted as a
  mismatch; the operator may pick another endpoint within the probe limit.
- *Host already pinned*: the offer cannot be created for a pinned or blocked
  host; re-pinning stays the existing approved re-pin flow (§7.3).

### D4: Approval and pinning are unchanged in strength

- The paired enrollment permit is a HIGH action with user verification, the
  same requirement as `ProposeEnroll`. It binds offer ID hash, host ID,
  endpoint, SSH user, credential reference, the full SHA-256 fingerprint and
  the fact "code matched" (with the code). It is single-use and expires like
  other enrollment permits.
- The executor, not the server, decides whether the code matched; the server
  only forwards the operator's input.
- Commit re-probes and pins only an unchanged key, then tests the login,
  exactly as `CommitEnroll` does. The pin is per host; every endpoint added
  later must present the same key; a mismatch later blocks the host (spec 08).
- `nebula approve` on the executor host shows the same binding (host,
  endpoint, fingerprint, "code matched", offer creation time and download
  address), so the hardened, independent view of ADR 0007 is available.

**What the code replaces, and its trust anchor.** The code replaces the
operator's eye comparison of fingerprints; it does not replace the approval.
Its authenticity rests on the operator's own session to the host where they
read the code. On the console or over an SSH session whose host key the
operator already trusts, this is as strong as today's comparison. Over a
first SSH login with trust on first use (typical for a fresh VPS), the code
is only as authentic as that first login: an attacker who intercepts the
operator's session can also forge the printed code. The UI and the guide say
so and recommend the provider's web console or a verified known_hosts entry
for internet-facing hosts.

**Residual risk equal to today.** A compromised server can show the operator
one thing and submit another code or endpoint; WebAuthn signs the permit's
challenge, not the page (ADR 0007). To pin a wrong key it must also control
the network path to the endpoint. This is the same exposure as the web
**Enroll hosts** flow today; the executor-local `nebula approve` view is the
mitigation.

### D5: Script generation

- The executor generates the script from the same template as
  `nebula host enroll-script` (shared generator, EN-04); the CLI output stays
  byte-identical for the same options (golden test).
- `from=` addresses come from **executor-local configuration** (new executor
  flag or config entry: enrollment source addresses), never from the server
  or the browser. With D6 the executor adds the NOS machine's own NetBird
  address, read from the NetBird API, not from input.
- The user name and credential reference are validated as in
  `cmd/nebula/enroll.go`; the key line is re-encoded from the parsed key.
- One-step additions, all at the end: the optional NetBird section (D6),
  the pairing code (D3) and the address list (`ip -o addr show scope global`,
  plus the NetBird address). Addresses are hints for the operator; NOS
  treats whatever the operator types as an endpoint to validate (spec 09:
  syntax, length, IP or DNS name), never as trusted.
- The script carries no secret except, optionally, the NetBird setup key.
  It writes the setup key only to a `0600` file under a `mktemp -d`
  directory removed by `trap` on exit, passes it to the NetBird client
  without putting it on a command line where the client allows that
  (verified per supported client version in EN-12; otherwise documented as a
  residual risk of a short `/proc` exposure on the host itself), and deletes
  itself (`nos-enroll.sh`) at the end when it contained a setup key.
- Size limit of the rendered script: 64 KiB; the executor refuses larger.

### D6: Optional NetBird join

**Precondition.** A NetBird management API token is stored in the executor
vault (`nebula netbird token set`, non-echoing input, like PVE tokens; never
in argv, environment, server configuration or browser). The token belongs to
a dedicated NetBird **service user**; the executor uses it only for typed
calls (create/revoke setup key, read peers, read the NOS peer), with no
generic HTTP proxy. Management URL and TLS trust are executor-local
configuration (public CA for NetBird Cloud; pinned CA or leaf for
self-hosted management). Without a token, the NetBird option is hidden and
the script works exactly without NetBird.

**Per-offer setup key.** For each offer with NetBird the executor creates
one setup key:

- type one-off (`usage_limit` 1), expiry ≤ 1 hour (default: offer expiry
  plus 45 minutes, so a download at minute 14 still has time to join);
- `auto_groups` exactly the configured managed group (default
  `nos-managed`), nothing else;
- not ephemeral by default (a server that is offline for a while must not
  disappear from NetBird); ephemeral only by explicit option;
- name `nos-offer-<first 8 hex of offer ID hash>`, so it can be found and
  revoked; it reveals nothing usable.

The executor stores the setup key encrypted in the vault until the offer is
final, then wipes it. It revokes the key when the offer expires, is revoked
or fails while the key is unused.

**Join on the host.** The script installs the NetBird client from the
official package repository if it is missing (repository signing key
fingerprint pinned in the script template, not fetched blindly), runs the
join with the setup key and the configured management URL, waits a bounded
time (60 s) for the NetBird address and prints it as the first address.

**Executor cross-check.** Before the operator can submit the code with a
NetBird endpoint, the executor reads the peer list through the API and finds
the peer that joined with this offer's setup key (exactly one, in exactly the
managed group). It shows that peer's NetBird IP as the suggested endpoint.
If no peer, more than one peer, or a peer in other groups is found, the
NetBird endpoint is not offered and the operator is told why. The pairing
code still decides the pin; the NetBird check only protects the endpoint
suggestion.

**Policy (operator-set, documented, not created by NOS).**

- Groups: `nos` (the NOS machine only) and `nos-managed` (enrolled hosts).
- One policy rule, **one direction**: source `nos` → destination
  `nos-managed`, TCP 22 (plus the hosts' SSH port if different). NetBird
  rules can be bidirectional; this one must not be.
- No rule from `nos-managed` to anything, including to `nos-managed` itself,
  unless the operator adds it deliberately for other reasons.
- The guide documents how to check this; NOS reads the policies through the
  API and shows a warning when a rule lets `nos-managed` reach `nos` or other
  groups (read-only check, Q3).

**Why a stolen setup key is bounded.** If the setup key leaks (offer page,
proxy log of the download, compromised server), the holder can join one peer
into `nos-managed` within the hour. That peer can be reached by NOS on TCP 22
and by nothing else under the documented policy; it cannot reach NOS. It
cannot get pinned, because the pairing code is bound to the real host's key.
Its use consumes the key, so the real host's join fails visibly, and the
executor's cross-check reports a peer that did not come from this host. The
executor then deletes that peer (typed call, audited) when the operator
confirms.

**Token scope.** NetBird's role model may not allow a token that can only
create setup keys; a service user with the admin role can also change
policies and groups. That is a real widening of executor authority (the
executor already holds root on all managed hosts, so the marginal risk is
the NetBird network itself). The executor code uses only the calls listed
above. Q3 asks whether this is acceptable or whether NetBird stays a manual
step until a narrower role exists.

### D7: Download security

- **Origin:** the URL is built from the server's configured public origin
  (the reverse proxy's `https://<rp-id>`); plain HTTP is never offered. The
  command uses `curl --proto '=https' --tlsv1.2 -fsS` (or `wget --https-only`)
  and never `-k`. If the host does not trust the proxy's CA, the guide shows
  `--cacert`; with a NetBird setup key in the script, TLS verification is
  mandatory, because the hash check protects integrity but not the key's
  confidentiality.
- **Endpoint:** `GET /enroll/<offer-id>`, outside the authenticated UI. The
  server validates the ID's syntax, rate-limits per client address (10 per
  minute, 60 per hour), calls the executor (`FetchEnrollScript`, server role)
  and streams the bytes. Responses: `200` with `Content-Type: text/plain;
  charset=utf-8`, `Content-Disposition: attachment`, `Cache-Control:
  no-store`, `X-Content-Type-Options: nosniff`; every refusal (unknown,
  expired, consumed, revoked, malformed, rate-limited) is the same `404` body.
  The server does not log the path; the guide tells operators to exclude
  `/enroll/` from proxy access logs.
- **Integrity:** the SHA-256 of the script is computed by the executor and
  shown on the offer page; the command checks it before running. A changed
  script (proxy, cache, wrong offer) does not run.
- **No `curl | sh`:** the command writes a file, checks the hash, then runs
  it; the operator can read it in between.
- **New exposure:** this is the first unauthenticated endpoint that returns
  executor-generated content. It returns only scripts of open offers, at most
  once each, and the content is public except for the optional setup key.
  Spec 02 and 03 must record it (EN-02).
- **Residual:** a compromised server can serve a different script and show
  its hash, and so run code as root on the new host. The same server can
  already show a manipulated script today when the operator copies from the
  web UI; with the CLI path the script comes from the executor host. For
  high-assurance hosts the guide recommends `nebula host enroll-script` or
  comparing the hash with `nebula host offers` on the executor host
  (Q6).

### D8: Hosts that cannot reach NOS

A remote host may not reach the NOS origin before it is in NetBird (for
example the IONOS VPS when NOS is LAN-only). Then the operator uses
**Download in browser** on the offer page (same single use, same hash) and
copies the file once (scp, paste); the rest of the flow is unchanged. Making
the NOS origin reachable for this purpose is not part of this ADR.

### D9: Compatibility

- `nebula host enroll-script`, `nebula host probe/pin/test`, `known_hosts`
  import and the bulk **Enroll hosts** page stay unchanged, including the
  RPCs `ProposeEnroll`/`CommitEnroll` and their permits.
- The ADR 0008 guest join (preset key or fingerprint review) is unchanged;
  one-step enrollment is for hosts NOS did not provision.
- Hosts enrolled either way are indistinguishable afterwards except for the
  audit record (`source` `paired` versus `probe`/`known_hosts`).
- Windows and BSD hosts are out of scope (Q5), as are hosts without
  coreutils `basenc` (the script stops with a message pointing to §7.2).

## Threat model additions

| Threat | Mitigation | Residual |
| --- | --- | --- |
| Machine in the path between executor and host at probe time | Pin only a key whose salted code matches the operator-carried code; re-probe at commit; mismatch fails the offer and notifies | Grinding success ≤ 2^-10 for a 10^12 keys/s attacker who also knows the salt (D3) |
| Precomputed key grinding against a known host key | Salt per offer; code computed over salt and key | None beyond the row above |
| Forged code shown to the operator | Code is read in the operator's own session or console | Equal to the operator's trust in that session (TOFU on a fresh VPS) |
| Leaked or guessed offer ID | ≥ 128 bits, single use, 15 min, uniform 404, rate limit, hashed at rest | A leaked ID before the download lets someone take the script; the real download then fails and the operator sees the download address |
| Script tampered in transit | TLS to the NOS origin, SHA-256 check before running, no `curl \| sh` | — |
| Compromised server | Executor decides code match, builds the permit, holds token and setup keys; `nebula approve` independent view | Can serve a malicious script (root on the new host) and deceive the approval page, as today |
| Leaked NetBird setup key | One use, ≤ 1 h, auto-group only `nos-managed`, one-way policy, executor peer cross-check and revocation | One rogue peer in `nos-managed` for a short time, reachable only from NOS |
| NetBird token misuse | Executor vault, typed calls only, audit, dedicated service user | Role may be broader than needed (Q3) |
| Hostile host output (addresses) | Addresses are hints the operator retypes; endpoint syntax validated; text-only rendering | — |
| Offer flooding | Limits per executor and hour; offers require a privileged session | — |

## Non-goals

- No agent, callback or polling from the host to NOS.
- No automatic trust on first use: an endpoint is never pinned without a
  matching code and an approval.
- No creation of NetBird policies or groups by NOS.
- No change to how existing pins, blocks and re-pins work.
- Windows, BSD and network devices (ADR 0010).

## Open questions for the maintainer

- **Q1: Code length and format.** 12 Crockford base32 characters (60 bits)
  plus one check character, shown as `XXXX-XXXX-XXXX-C` (recommended), or 16
  characters (80 bits)? Case-insensitive input, `O`/`0` and `I`/`L`/`1`
  folded as Crockford defines. Crockford's mod-37 check symbol adds five
  extra characters (`*~$=U`); a decimal or Luhn-style check digit is the
  alternative if those are awkward to type.
- **Q2: Offer lifetime.** 15 minutes for download and code (recommended), or
  longer for slow remote installs (the NetBird client install can take a few
  minutes)? Should the code submission get its own window after the download
  (for example 15 minutes from download, at most 60 from creation)?
- **Q3: NetBird token scope and group names.** Is a service user with the
  NetBird role needed for setup-key creation acceptable in the executor
  vault, or does NetBird stay a manual step until a narrower role exists?
  Group names `nos` and `nos-managed`? Should NOS read and warn on policies
  (recommended), or not touch policies at all? Self-hosted management or
  NetBird Cloud in the reference lab (decides the TLS trust setting)?
- **Q4: Inventory entry in the same step.** May the one-step dialog create
  the inventory host (recommended: yes, as a normal inventory entry shown
  "not enrolled" until the pin; deleted again if the offer fails and the
  operator chooses so), or must the host exist first?
- **Q5: Platforms.** Windows and BSD stay out of scope (recommended)?
  Proxmox VE nodes are Debian and included.
- **Q6: Script authenticity against a compromised server.** Accept the
  residual risk of D7 with the documented CLI alternative (recommended), or
  require the executor-local CLI to display the hash for every one-step
  offer?
- **Q7: Mismatch handling.** One well-formed mismatch fails the offer
  (recommended, with the check character catching typos), or allow a second
  code submission?

## Required specification changes

- `docs/spec/08-ssh-transport.md`: a third way to avoid blind trust
  (paired enrollment with an offer-salted code), ed25519 only, re-probe at
  commit, mismatch handling.
- `docs/spec/06-credentials.md`: NetBird management token custody, per-offer
  setup keys in the vault, wipe on final state.
- `docs/spec/05-authentication.md`: paired enrollment permit (HIGH, UV),
  session binding of offers.
- `docs/spec/02-architecture.md`, `03-processes-and-data.md`: the
  unauthenticated download endpoint, the offer table (executor), executor
  egress to the NetBird management URL.
- `docs/spec/09-untrusted-host-data.md`: script-printed addresses are
  operator hints; endpoint validation.
- `docs/spec/12-inventory.md`: one-step dialog and (Q4) inventory creation.
- `docs/spec/04-revision-history.md`, `17-frozen-decisions.md`: record the
  revision. Afterwards admin guide §7 and a NetBird policy section.

## Consequences

- Enrollment of a single host becomes: one dialog, one command on the host,
  one code typed into NOS, one security-key touch. The fingerprint
  comparison is done by the executor against a value the operator carried,
  not by eye.
- Host-key pinning is not weakened: the same pin, the same HIGH approval,
