# Execution model: permits, stages, durable jobs, reconciliation

<a id="v23-07-01"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-01 -->
Every execution runs under executor authority for one exact request: an interactive single-use permit, a member permit derived from an approved batch, or a read execution authorized by an exact standing read grant. Read grants never authorize mutations. Anything that changes the approved binding invalidates affected authority.

**Canonical request.** `execution_id`, `action_id`, `module_version`, `artifact_sha256`, `parameters_hash`, `credential_refs[]`, `risk_class`, `stage_plan_hash`, `expiry` and `resolved_targets[]`, where each target is host ID plus the host's pinned key fingerprint. Dynamic selections (“group Docker, environment PROD”) are resolved and frozen before approval; a changed membership needs a new approval.

**Executor checks before each host run.** Permit valid and unused for this host; artifact bytes hash to `artifact_sha256`; module and action match; host and its key fingerprint are in `resolved_targets`; parameters hash matches; only permitted credentials are used; not expired; risk authorization satisfied; signature trust satisfied where the module requires it.

<a id="v23-07-15"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-15 -->
**Stage engine.** One engine for everything; DEV → QA → PROD, canary and waves are presets. Each stage may set a failure threshold, an unreachable threshold, required postchecks, and manual or automatic continue subject to the approval gates. For a single-action rollout one permit covers the rollout; mixed-action batches use the member permits and dependencies below. Expiry is the planned duration plus margin, at most 24 h. Continuing past a gate needs a click in the privileged session for LOW and MEDIUM, and a fresh user-verified assertion bound to digest and stage number for HIGH and CRITICAL (CLI in hardened mode). Batch HIGH continuation is never automatic. A host still unreachable at stage timeout offers Retry, Skip or Abort stage; Skip is audited, and a batch retry needs fresh exact-target approval.

**Attached and durable runs.** Short read-only actions (facts, service status, update listing) run attached to the SSH session. Mutating or long actions run as durable jobs started by the OS adapter (Debian adapter: transient systemd units) in `/var/lib/nebula/jobs/<execution-id>/` with only `action.sh`, `state.json`, `result.json`, `execution.log`. Results are written atomically: write `.tmp`, fsync, rename.

**Job states.** queued, prechecking, dispatching, running, reconciling, success, warning, failed, not\_executed, cancelled, interrupted, unknown.

**Reconciliation.** After a Nebula restart the executor finds unfinished executions, reconnects, reads remote state, collects log and result, runs postchecks and updates central state. It never re-runs a mutating action whose outcome is unknown.

**Retry classes.** `safe` (facts, update checks), `reconcile-first` (package installs, reboot), `never` (restore).

**Remote cleanup.** The executor deletes a job directory once it has stored the result. As a fallback, enrollment installs `/etc/tmpfiles.d/nebula.conf`, which removes job directories older than 14 days without any Nebula daemon.

**Error classes.** network\_unreachable, connection\_timeout, connection\_refused, authentication\_failed, host\_key\_mismatch, credential\_unavailable, vault\_locked, precheck\_failed, policy\_blocked, insufficient\_privileges, execution\_timeout, script\_failed, script\_interrupted, result\_missing, postcheck\_failed, host\_rebooting, host\_not\_returned, unknown.

<a id="v23-07-02"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-02 -->
**Canonical provider targets.** Add versioned typed provider targets, never fake SSH host IDs. Bind remote ID, guest generation/kind, exact node and VMID (or explicit node target), CA/leaf pin and trust generation, approved API endpoint set, action/adapter version and artifact digest, credential reference/version, canonical parameters, precondition digests, stage plan and expiry. The executor reconstructs paths and hashes bytes itself. Migration binds both nodes/storages; reboot freezes every impacted guest and blocks if the set changes. A guest moving nodes requires a new proposal; failover may change only the API entry node within the approved endpoint set. Autonomous HA relocation is observed external change, stops affected dispatch and needs approval again.

<a id="v23-07-03"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-03 -->
**Versioned read grants.** One executor-owned registry, authorization path, revocation API and budget accounting serves ordinary, telemetry and provider profiles; “read lease” is the user-facing name. A versioned canonical document binds grant ID, issuer, creation, absolute expiry (default 7 days, maximum 30 days), trigger (scheduled, on demand or both), and at most 32 explicit action entries with action ID, module/adapter version, trusted artifact SHA-256 and exact canonical parameters hash. Bind at most 1,000 SSH host IDs and pinned fingerprints, plus credential references/versions where applicable. Provider scope binds approved remote/resources, pin/trust generation, credential version and typed methods, with executor-validated child enumeration inside that remote only. Bind the rate profile, minimum intervals, per-target rolling-hour run budget and provider request budget into the digest. Exact document version identifier and encoded-size limits remain [open questions](17-frozen-decisions.md); the implementation must not accept an unbounded document.

<a id="v23-07-04"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-04 -->
**Frozen read scope.** Resolve all-host, tag and environment selections before approval, show every host/key and retain the frozen snapshot. Enrollment, tag changes and replacement keys do not join automatically; removal disables the host immediately, expansion needs a new grant. Server tags are never live authorization predicates. Enumeration does not authorize arbitrary follow-up commands, SSH access or provider mutations. Parameterized inspection binds an exact container incarnation or unit; destinations for service checks are explicit. Approved provider child enumeration remains subject to resource identity/generation validation.

<a id="v23-07-05"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-05 -->
**Ordinary read budgets.** Default 24 runs/host/rolling hour, maximum 240, aggregated across actions and scheduled/on-demand triggers, retaining a 15-minute per-action floor. “Refresh now” for one host, a selection or all shares the same allowance; show cached age and next eligible time when throttled. Atomically reserve the grant budget and executor-wide target ceiling before dispatch, durably across restart. Overlapping grants cannot multiply that ceiling; failed/disconnected attempts spend their claimed budget, without free retries or catch-up bursts. Storage errors deny dispatch and clock rollback cannot replenish allowance. The exact executor-wide ceiling policy below the stated maxima remains an open question.

<a id="v23-07-06"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-06 -->
**Telemetry profile.** Separately approve exact SSH host/key/action/parameters/version scope for five-minute history and ten-second live reads, with an explicit aggregate budget up to 4,096 runs/host/rolling hour and bounded concurrency. This is the reviewed exception to the ordinary 15-minute floor, not a change to it. Costly scans retain slower action-specific limits. Provider telemetry additionally obeys four live targets and one metrics request/s per remote. A 30-second visible-target request binds remote/node/VMID/generation or SSH host/key and read-grant versions; it selects work within existing authority and budget, never creates authority. Coalesce viewers; hiding/closing/disconnecting stops renewal. SSE carries sanitized values every 10 s without execution rights. Per-host concurrency/default budgets and costly-action intervals not fixed by the ADRs remain explicit open questions.

<a id="v23-07-07"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-07 -->
**Provider profile.** Authorize exact remote/trust/credential versions, typed enumeration methods, minimum intervals, request budgets and absolute expiry under the same 7/30-day grant mechanism. The `pve-collector` UID schedules only these reads; neither it nor the server can widen methods, resource scope or frequency. The executor validates each discovered node/guest child. Defaults: one poll/remote at a time, two concurrent API requests/remote, 10 s connect/30 s request timeouts, jitter and exponential backoff capped at 15 min. Collection cadence and staleness are in [12-inventory.md](12-inventory.md). Grant request budgets are approval-bound; the ADRs leave their exact non-metrics defaults/maxima open. Private registry metadata also uses typed repository/tag grants with credential versions and the separate origin/cache/request constraints in [11-operations.md](11-operations.md); no generic API/URL proxy is permitted.

<a id="v23-07-08"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-08 -->
**Read eligibility and dispatch.** Only approved read-only contracts in [10-modules.md](10-modules.md) qualify, and effective risk must remain LOW. Before every run recheck expiry/revocation, canonical parameters, exact artifact bytes/version, read-only contract, current trust/risk, pin/block state and credential version. Untrusted or newly HIGH actions fail closed; no automatic assertion fallback or artifact substitution. Trusting a new built-in version does not amend a lease; approve a replacement grant. An unchanged version stays covered only while installed, available and allowed by current policy. Use a fresh execution ID for every run and link it to grant ID, action/version, exact target, trigger, budget claim and outcome.

<a id="v23-07-09"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-09 -->
**Read lifecycle and audit.** Standard approval uses one grant-bound UV assertion without a prior privileged session; hardened approval is executor-local CLI, and recovery cannot create grants. Approved grants and spent budgets persist, pending proposals do not. Runs require unlocked execution credentials but neither a privileged session nor per-run approval. Session expiry leaves leases usable. Lock wipes keys, pauses grants and cancels queued dispatch; restart starts locked. Explicit local unlock resumes still-valid grants; paused time counts toward expiry. UI/CLI revocation needs no assertion and blocks every future claim; serialize revocation/lock with dispatch so queued work cannot escape. Running work may finish. Re-pin, removal, rotation, trust withdrawal or raised risk blocks affected scope; identity/version changes need replacement grants. Credential removal/recovery pauses grants until local review/unlock. Audit proposals, approver, digest/scope/budget, renewal, pause/resume, revocation, denials and each run's claim/outcome, keeping sanitized results in execution history. Show expiry, budget, blocked reasons and a prominent Revoke.

<a id="v23-07-10"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-10 -->
**Legacy schedules.** `read-schedule-v1` keeps its original schedule-only scope and expiry, including existing 90-day approvals. Never reinterpret an old signature as on-demand authority. New grants and renewals use the 7-day default/30-day maximum, superseding ADR 0006's proposed 90-day provider maximum. Migrate storage/accounting without duplicating authority; legacy grants share the executor target ceiling. List them with revoke or explicitly approved replacement.

<a id="v23-07-11"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-11 -->
**Canonical batches.** `batch-v1` binds batch ID, expiry, stage/dependency graph and hash, and an ordered list of member IDs and complete canonical execution requests. Bounds: 1–100 expanded action-target members, 1 MiB canonical plan bytes, 20 stages and at most 24 h execution expiry. Twelve host updates plus three container restarts are fifteen members; no wildcard, implicit descendants or automatic approval chunks. Each member binds exact action/module/adapter version, artifact hash, target/key or provider identity/generation/pin, credential references/versions, canonical parameters hash, precondition hashes and executor-derived risk. Container members also bind full ID, configuration and old/new image digests. Supply bounded parameter documents/artifact bytes for executor validation; secret values remain opaque executor-held references. Reject duplicate IDs or action-target-parameter tuples, malformed UTF-8, unknown/duplicate keys, cycles, missing dependencies and excessive sizes. Order matters: any reorder, insertion, removal or edit needs a new digest.

<a id="v23-07-12"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-12 -->
**Batch member authority.** The executor approves the strictest member under [05-authentication.md](05-authentication.md), rejecting the whole proposal for any CRITICAL member. It derives internal single-use member permits bound to parent digest, index/ID, exact request and parent expiry; no bearer batch token may authorize arbitrary children. Claim execution IDs atomically under the spent-ID discipline before dispatch. Recheck ordinary per-run trust, risk, pin, parameter, credential and stage conditions; concurrent/replayed members cannot run twice. A raised risk invalidates remaining batch authority and needs a fresh plan. Batch/child approval and gates stay memory-only: lock/restart revokes them, and expiry ends undispatched rights. Persist intent/outcomes only for reconciliation. Audit approver/digest, member derivation, claims, dispatch, outcomes, denials, gates, skips and revocation without secrets.

<a id="v23-07-13"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-13 -->
**Member stages and partial outcomes.** Extend the existing stage unit from host to member so actions on one host cannot bypass order or reuse permits. Show success, failure, skipped, not-executed and unknown separately; a batch is not a transaction. Dependencies enforce ordering and required postchecks. Default failure policy stops every undispatched member; only explicitly approved thresholds may let independent members continue. Reconcile running jobs first. Retry/rollback needs fresh exact-target approval, with no automatic rollback or uncertain redispatch. Manual LOW/MEDIUM gates require a privileged-session click; HIGH gates need fresh UV bound to batch digest and stage (CLI in hardened mode), never automatic HIGH continuation. Skips are audited and cannot satisfy unmet dependencies.

<a id="v23-07-14"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-14 -->
**Provider durable jobs.** Persist intent and claim single-use authorization in `executor.db`, fsync before sending the mutation. Persist returned UPID, task node, exact target tuple, request digest and timestamps before reporting it. Reuse job states with the PVE task as remote job, without uploaded shell/systemd unit. Poll typed status and require action-specific postchecks; accepted request/UPID is not success. After either process restarts, stored jobs allow read-only reconciliation with read credentials once unlocked, never mutation authority. Lost responses enter reconciling then unknown if the exact task cannot be identified; power state alone is not success, and missing/expired task records preserve uncertainty. HA operations without UPIDs require durable intent and observed manager/guest convergence. Cancellation stops undispatched work; cancelling a remote task requires separately approved authority. Lock cannot undo an accepted task.
