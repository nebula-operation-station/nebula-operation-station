# Execution model: permits, stages, durable jobs, reconciliation

<a id="v23-07-01"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-01 -->
Every execution runs under executor authority for one exact request: an interactive single-use permit, a member permit derived from an approved batch, or a read execution authorized by an exact standing read grant. Read grants never authorize mutations. Anything that changes the approved binding invalidates affected authority.

**Canonical request.** `execution_id`, `action_id`, `module_version`, `artifact_sha256`, `parameters_hash`, `credential_refs[]`, `risk_class`, `stage_plan_hash`, `expiry` and `resolved_targets[]`, where each target is host ID plus the host's pinned key fingerprint. Dynamic selections (“group Docker, environment PROD”) are resolved and frozen before approval; a changed membership needs a new approval.

**Executor checks before each host run.** Permit valid and unused for this host; artifact bytes hash to `artifact_sha256`; module and action match; host and its key fingerprint are in `resolved_targets`; parameters hash matches; only permitted credentials are used; not expired; risk authorization satisfied; signature trust satisfied where the module requires it.

<a id="v23-07-15"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-15 -->
**Stage engine.** One engine for everything; DEV → QA → PROD, canary and waves are presets. Each stage may set a failure threshold, an unreachable threshold, required postchecks, and manual or automatic continue subject to the approval gates. For a single-action rollout one permit covers the rollout; mixed-action batches use the member permits and dependencies below. Expiry is the planned duration plus margin, at most 24 h. Continuing past a gate needs a click in the privileged session for LOW and MEDIUM, and a fresh user-verified assertion bound to digest and stage number for HIGH and CRITICAL (CLI in hardened mode). Batch HIGH continuation is never automatic. A host still unreachable at stage timeout offers Retry, Skip or Abort stage; Skip is audited, and a batch retry needs fresh exact-target approval.

**Attached and durable runs.** Short read-only actions (facts, service status, update listing) run attached to the SSH session. Mutating or long actions run as durable jobs started by the OS adapter (Debian adapter: transient systemd units) in `/var/lib/nebula/jobs/<execution-id>/` with only `action.sh`, `state.json`, `result.json`, `execution.log`. Results are written atomically: write `.tmp`, fsync, rename.

**Job states.** queued, prechecking, dispatching, running, reconciling, success, warning, failed, not\_executed, cancelled, interrupted, unknown.

**Reconciliation.** After a Nebula restart the executor finds unfinished executions, reconnects, reads remote state, collects log and result, runs postchecks and updates central state. It never re-runs a mutating action whose outcome is unknown.

**Retry classes.** `safe` (facts, update checks), `reconcile-first` (package installs, reboot), `never` (restore).

**Remote cleanup.** The executor deletes a job directory once it has stored the result. As a fallback, enrollment installs `/etc/tmpfiles.d/nebula.conf`, which removes job directories older than 14 days without any Nebula daemon.

**Error classes.** network\_unreachable, connection\_timeout, connection\_refused, authentication\_failed, host\_key\_mismatch, credential\_unavailable, vault\_locked, precheck\_failed, policy\_blocked, insufficient\_privileges, execution\_timeout, script\_failed, script\_interrupted, result\_missing, postcheck\_failed, host\_rebooting, host\_not\_returned, unknown.

<a id="v23-07-02"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-02 -->
**Canonical provider targets.** Add versioned typed provider targets, never fake SSH host IDs. Bind remote ID, guest generation/kind, exact node and VMID (or explicit node target), CA/leaf pin and trust generation, approved API endpoint set, action/adapter version and artifact digest, credential reference/version, canonical parameters, precondition digests, stage plan and expiry. The executor reconstructs paths and hashes bytes itself. Migration binds both nodes/storages; reboot freezes every impacted guest and blocks if the set changes. A guest moving nodes requires a new proposal; failover may change only the API entry node within the approved endpoint set. Autonomous HA relocation is observed external change, stops affected dispatch and needs approval again.

<a id="v23-07-03"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-03 -->
**Versioned read grants.** One executor-owned registry, authorization path, revocation API and budget accounting serves ordinary, telemetry and provider profiles; “read lease” is the user-facing name. A versioned canonical document binds grant ID, issuer, creation, absolute expiry (default 7 days, maximum 30 days), trigger (scheduled, on demand or both), and at most 32 explicit action entries with action ID, module/adapter version, trusted artifact SHA-256 and exact canonical parameters hash. Bind at most 1,000 SSH host IDs and pinned fingerprints, plus credential references/versions where applicable. Provider scope binds approved remote/resources, pin/trust generation, credential version and typed methods, with executor-validated child enumeration inside that remote only. Bind the rate profile, minimum intervals, per-target rolling-hour run budget and provider request budget into the digest. Exact document version identifier and encoded-size limits remain [open questions](17-frozen-decisions.md); the implementation must not accept an unbounded document.

<a id="v23-07-04"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-04 -->
**Frozen read scope.** Resolve all-host, tag and environment selections before approval, show every host/key and retain the frozen snapshot. Enrollment, tag changes and replacement keys do not join automatically; removal disables the host immediately, expansion needs a new grant. Server tags are never live authorization predicates. Enumeration does not authorize arbitrary follow-up commands, SSH access or provider mutations. Parameterized inspection binds an exact container incarnation or unit; destinations for service checks are explicit. Approved provider child enumeration remains subject to resource identity/generation validation.

<a id="v23-07-05"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-05 -->
**Ordinary read budgets.** Default 24 runs/host/rolling hour, maximum 240, aggregated across actions and scheduled/on-demand triggers, retaining a 15-minute per-action floor. “Refresh now” for one host, a selection or all shares the same allowance; show cached age and next eligible time when throttled. Atomically reserve the grant budget and executor-wide target ceiling before dispatch, durably across restart. Overlapping grants cannot multiply that ceiling; failed/disconnected attempts spend their claimed budget, without free retries or catch-up bursts. Storage errors deny dispatch and clock rollback cannot replenish allowance. The exact executor-wide ceiling policy below the stated maxima remains an open question.

<a id="v23-07-06"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-06 -->
**Telemetry profile.** Separately approve exact SSH host/key/action/parameters/version scope for five-minute history and ten-second live reads, with an explicit aggregate budget up to 4,096 runs/host/rolling hour and bounded concurrency. This is the reviewed exception to the ordinary 15-minute floor, not a change to it. Costly scans retain slower action-specific limits. Provider telemetry additionally obeys four live targets and one metrics request/s per remote. A 30-second visible-target request binds remote/node/VMID/generation or SSH host/key and read-grant versions; it selects work within existing authority and budget, never creates authority. Coalesce viewers; hiding/closing/disconnecting stops renewal. SSE carries sanitized values every 10 s without execution rights. Per-host concurrency/default budgets and costly-action intervals not fixed by the ADRs remain explicit open questions.

<a id="v23-07-07"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-07 -->
**Provider profile.** Authorize exact remote/trust/credential versions, typed enumeration methods, minimum intervals, request budgets and absolute expiry under the same 7/30-day grant mechanism. The `pve-collector` UID schedules only these reads; neither it nor the server can widen methods, resource scope or frequency. The executor validates each discovered node/guest child. Defaults: one poll/remote at a time, two concurrent API requests/remote, 10 s connect/30 s request timeouts, jitter and exponential backoff capped at 15 min. Collection cadence and staleness are in [12-inventory.md](12-inventory.md). Grant request budgets are approval-bound; the ADRs leave their exact non-metrics defaults/maxima open. Private registry metadata also uses typed repository/tag grants with credential versions and the separate origin/cache/request constraints in [11-operations.md](11-operations.md); no generic API/URL proxy is permitted.

<a id="v23-07-08"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-08 -->
**Read eligibility and dispatch.** Only approved read-only contracts in [10-modules.md](10-modules.md) qualify, and effective risk must remain LOW. The built-in `net.facts` traffic-map snapshot read (ADR 0009 D1) is an approved read-only contract on this allowlist: LOW, read-only, non-durable, no parameters; it collects bounded base64 network sections, runs `ss` without `-p`, and changes nothing on the host; its sections, size limits and statuses are in [09-untrusted-host-data.md](09-untrusted-host-data.md). Before every run recheck expiry/revocation, canonical parameters, exact artifact bytes/version, read-only contract, current trust/risk, pin/block state and credential version. Untrusted or newly HIGH actions fail closed; no automatic assertion fallback or artifact substitution. Trusting a new built-in version does not amend a lease; approve a replacement grant. An unchanged version stays covered only while installed, available and allowed by current policy. Use a fresh execution ID for every run and link it to grant ID, action/version, exact target, trigger, budget claim and outcome.

<a id="v24-07-01"></a>
<!-- Spec revision (ADR 0011, VU-02): v24-07-01 -->
**Vulnerability inventory reads (ADR 0011 D3).** `package.list_installed` (`os-debian`) and the optional `image.packages` (host-local Trivy, image by platform digest) are approved read-only contracts on this allowlist (previously: not on it): LOW and read-only. `package.list_installed` has its own cost limit of at most one run every 6 h per host (ADR 0011 D3). ADR 0011 sets no action-specific cost limit for `image.packages`. Spec rules applied here, not ADR 0011 decisions (VU-05 and VU-06 are open, so no merged code backs them yet): both reads count inside the ordinary per-host budget and "Refresh now" shares its allowance ("Ordinary read budgets" above); the 6 h limit is a slower action-specific limit in the sense of the costly scans above and is bound into the lease with the other minimum intervals ("Versioned read grants" above); `image.packages` binds the exact image platform digest as its parameter, as inspection reads bind exact parameters ([10-modules.md](10-modules.md#v23-10-01)). Neither read is triggered by Hermes, a finding or the vulnerability export: the export uses stored observations only, and no finding, score or assessment ever creates, widens or spends a lease or permit (ADR 0011 D1). Result fields, limits and the completeness flag are in [10-modules.md](10-modules.md#v24-10-01) and [09-untrusted-host-data.md](09-untrusted-host-data.md#v24-09-01).

<a id="v26-07-01"></a>
<!-- Spec revision (ADR 0015, IG-01): v26-07-01 -->
**Integrity scan read (ADR 0015 D5, D9, Q1, Q2).** The built-in `fim.scan` action ([10-modules.md](10-modules.md#v26-10-02)) is an approved read-only contract on this allowlist (previously: not on it): LOW and read-only, run by the executor over its own SSH connection with a fixed script that leaves nothing on the host. Scheduled and on-demand runs go through a normal read lease bound to the exact action, script hash, parameters, hosts and budgets; the server's scheduler (or a collector role) only triggers, the executor authorizes and dials. The grant freezes exactly these parameters and no free-form path: the **profile ID** (`fim-default-v1` or an admin-approved variant whose excludes and additional roots from the fixed list are covered by the grant digest, Q1), the **mode** (`incremental` or `full`) and the profile's fixed look-back window for incremental runs (default 26 hours, so a missed run still overlaps).

- **Intervals (Q2).** Incremental every 6 hours and full weekly by default; hourly incremental on hosts the admin marks as crown jewels (ADR 0011 D10). These are action-specific minimum intervals bound into the lease with the other minimum intervals ("Versioned read grants" above), and all runs count inside the ordinary per-host read budget ("Ordinary read budgets" above). When an incremental run sees a metadata change of a file it did not hash, NOS opens a "changed, not yet hashed" finding and schedules a full run inside the existing lease budget, never outside it.
- **Load per run.** The script runs under `nice -n 19` and `ionice -c3` where available; a full run hashes at most 8 GiB and stops after 30 minutes (partial). Files larger than 512 MiB are hashed only in full runs; incremental runs record them by metadata only.
- **No authority from findings.** An integrity finding never creates or widens a lease or permit (the follow-up full run above only spends the existing lease budget), and never starts a restore, reinstall or other mutation ([01-product.md](01-product.md#v26-01-01)).

Result fields, limits and the partial-run rule are in [09-untrusted-host-data.md](09-untrusted-host-data.md#v26-09-01).

<a id="v28-07-01"></a>
<!-- Spec revision (ADR 0016, ag01): v28-07-01 -->
**Execution origin (ADR 0016 D9, D14).** The server's execution record gains an **origin** field (previously: none). For an execution or batch member that the server attributes to an ops-agent suggestion ([05-authentication.md](05-authentication.md#v28-05-01)) it holds `suggestion:<note ID>.<step>` (the create request carried a valid suggestion reference) or `suggestion-match:<note ID>` (a stored `fix` note holds a step of the same action family on the same host); otherwise it is empty. The attribution rules of ADR 0016 D9, which [v28-05-01](05-authentication.md#v28-05-01) summarises as "An unknown reference is refused": an unknown, expired or malformed suggestion reference is refused with `400`, and the server never falls back to an unmarked execution; a valid reference always marks the execution, also when the human changed action or targets in the form. The match is checked for every interactively created execution and batch member, with or without a reference, against every stored `fix` note that is not yet pruned (dismissed or not, outdated or not); removing the reference from the request therefore changes nothing. The audit entry `execution_proposed` carries it, and the operation page shows "From an agent suggestion" and "Risk MEDIUM (raised; the action declares LOW)". The origin is server data only: it is not a field of the canonical request above, and the executor sees only its effect, the raised `risk_class`, which is bound into the execution digest and the challenge like any other class. It applies to executions and batches created in the web UI; it does not apply to leased reads (no read action is on the suggestion allowlist) and adds nothing to schedule or read-grant approval.

<a id="v29-07-01"></a>
<!-- Spec revision (ADR 0007 amendment, op02): v29-07-01 -->
**Rejecting a pending proposal (ADR 0007 amendment R1–R7).** A pending execution permit, or a pending `batch-v1` plan before its initial approval (rejected as a whole by its batch digest, never per member), can be rejected (previously: it could only expire). Who may reject is in [05-authentication.md](05-authentication.md#v29-05-01); rejecting needs no assertion because it only removes authority. Approved permits, running rollouts and stage gates are not rejected; they keep abort, lock and revocation. Pending read-grant and schedule-grant proposals, enrollment permits and integrity baselines are not covered.

- **Executor RPC `RejectPending`.** Request: the execution digest or batch digest, an optional reason and, from the `server` UID only, the field `relayed_user` (previously: digest and reason only): the user name of the privileged session, as claimed by the server. For the `server` UID it is required and must be 1–64 bytes of valid UTF-8 with no control characters (C0, C1, DEL), no bidirectional control characters and no whitespace other than U+0020; for the `admin` UID it must be empty. Anything else is refused with `invalid_request`. The executor never uses it for a decision; it only records it. Next to it the executor records, from its own state and never from the request, the credential ID of the user-verified assertion that opened the current privileged session (`session_credential_id`; previously: not recorded), so that the signed event names the security key that opened the session even where the server-claimed name is false; for the `admin` UID it is empty. Allowed for the `server` and `admin` UIDs ([03-processes-and-data.md](03-processes-and-data.md#v29-03-01)); every other UID is refused. A call from the `server` UID is refused with `privileged_session_required` while no privileged session is open; the `admin` UID (`nebula reject <digest> [--reason <text>]`, which first shows the executor's own view of the proposal as `nebula approve` does) needs none. The request carries no assertion, approval field or mode, and the executor offers no way to turn it into an approval.
- **Atomic and final.** The executor holds the same lock that serialises approval (`SubmitAssertion`, `ApproveCLI`, batch approval, derivation of batch member permits) and proposal from the first check to the last in-memory delete, in three phases (previously: one step whose post-commit failure was described as "nothing changes"):
  1. *Checks, nothing written,* in this order; the first that fails returns its code from the table below (previously: no order was given):
     1. The request passes the limits above and below (`invalid_request`), and a server-UID call finds a privileged session open (`privileged_session_required`).
     2. The digest is looked up in `rejected_proposals`. A row answers `permit_already_rejected`, whether or not the approval window has ended and also after lock or restart: the persisted marker takes precedence over every in-memory answer (previously: the precedence of `permit_already_rejected` and `permit_expired` was not stated). A failed read answers `storage_error`.
     3. The executor first drops ended entries, as `SubmitAssertion` and `ApproveCLI` and batch proposal already do (`gcLocked` of the execution permit authority and of the batch authority, both called here; batch approval itself uses `getLocked` and is not changed: a pending permit or plan whose approval window has ended, and an approved one whose request or plan has expired, is deleted from memory), then looks the digest up in memory. Absent answers `permit_not_found`: never proposed, approval window ended, or dropped by lock or restart. These cases are one code because `gcLocked` keeps nothing of an ended pending entry, so the executor cannot tell them apart (previously: a separate `permit_expired` for an ended window). Approved, in use or consumed answers `permit_already_approved`. Pending goes on to phase 2.
  2. *One `executor.db` transaction, the only fallible write.* The executor first builds and signs the event `permit.rejected` (Audit below), then in one transaction:
     1. reads the existing binding in the table `execution_ids` and checks that it names this digest: for an execution, the binding of its execution ID that `Propose` wrote through `Store.BindExecution` before the permit existed; for a batch, the binding of every member execution ID to the batch digest that batch `Propose` wrote before the plan existed;
     2. inserts the **rejected marker**, a row in the table `rejected_proposals` ([03-processes-and-data.md](03-processes-and-data.md#v29-03-01)) (previously: executor memory only, dropped by lock and restart);
     3. appends the event to the executor's event chain (table `events`).

     The transaction inserts, updates and deletes nothing in `execution_ids` (previously: it "marks the execution ID or batch ID as spent", which as a second insert would hit the row `Propose` already wrote): the execution ID has been spent since the proposal, its binding stays as it is and is pruned by `PruneExecutions` as before. A missing binding, or one that names another digest, cannot occur with an intact database and fails like a failed statement. If building or signing the event or any statement or the commit fails, the transaction is rolled back, nothing is written, the in-memory pending permit or plan and its challenge are untouched, and the call fails with `storage_error`; the digest is then still pending and may be rejected again, approved or left to expire.
  3. *After the commit, nothing can fail.* Once the transaction has committed, the rejection is final and the call returns success. The executor then deletes the pending permit or plan and its challenge from memory and records the **pending-slot placeholder** for the digest (below); these are map deletions and one map insertion under the held lock, with no I/O and no other step that can fail, and no `storage_error` or other error is returned after the commit.

  The persisted marker, not the in-memory state, decides: under the same lock every approval path (`SubmitAssertion`, `ApproveCLI`, batch approval, member permit derivation) looks the digest up in `rejected_proposals` before its in-memory lookup and refuses a rejected digest with `permit_rejected`, so a stale in-memory entry could never be approved, and a rejected digest is answered `permit_rejected` and never `permit_not_found` or `permit_expired`, also after its window, lock or restart; a failed read refuses with `storage_error`. The marker survives lock and restart and is pruned no earlier than `RetainSpentExecutions` (30 days) after the original approval window ended. While it exists the digest is final and cannot be approved.

  Re-proposal is refused by the stores that already exist plus the marker (previously: "every proposal path refuses a spent execution ID or batch ID", without naming where a batch ID is spent):
  - *Execution.* No new check: the execution ID stays bound in `execution_ids`, and `Propose` refuses it with `execution_id_reused` as for every reused ID, also after lock or restart, until `PruneExecutions` removes the binding `RetainSpentExecutions` after the request expiry.
  - *Batch.* Every member execution ID has been bound since batch proposal, so an identical plan is refused with `execution_id_reused` in the same way. The batch ID itself is spent in the marker row (kind `batch`, ID column unique per kind; [03-processes-and-data.md](03-processes-and-data.md#v29-03-01)), the only durable store of batch IDs (previously: none; batch IDs were spent only in the authority's in-memory `seen` set, emptied by lock and restart). Batch `Propose` checks it next to `seen`, in `admit` and again before it stores the plan, and refuses a match with the code it already uses for a seen batch ID (`permit_wrong_state`, "batch ID already proposed"), also after lock or restart. After the row is pruned, a new plan under the same batch ID is accepted as after a restart today; the rejected plan's own expiry has long passed.

  **Pending slot.** A rejected proposal keeps its slot in the in-memory pending limit until its original approval window would have ended, or until lock or restart drops every pending permit: rejecting frees no capacity early, so a caller that may reject cannot cycle proposals faster than the approval window allows (previously: stated, but no state held the slot, and `pendingCountLocked` counts only pending permits). The slot is held by the placeholder from phase 3: an in-memory entry per rejected digest, holding only the digest and the end of the original approval window, kept apart from the permits and plans, so no approval, lookup or `GetPermitState` path ever sees it. The count that `Propose` checks against `MaxPending` (`pendingCountLocked` for executions, the entry count for batches) adds the placeholders whose window end has not passed; `gcLocked` drops a placeholder once its window end has passed, and lock and restart drop all placeholders with the pending permits. A placeholder replaces exactly one pending entry, so it never raises the count. For a batch, the plan bytes leave the retained-bytes budget (`MaxRetainedBytes`) at once, because the placeholder holds none; only the count slot is held.
- **State `rejected`.** `PermitState` gains `REJECTED` (previously: `UNSPECIFIED`, `PENDING`, `APPROVED`); `GetPermitState` returns it while the rejected marker exists (also after the approval window, lock and restart, until the row is pruned) together with the rejecting role from the marker, `server` or `admin` (previously: the state only), and reveals nothing else (no reason, no user name, no credential ID). The server's executions table gains the state `rejected` next to `expired` (detail "rejected; nothing was run", `finished_at` set, `waiting` host rows `finished` with class `not_executed`). It is shown muted, labelled "Rejected" (never "Expired"), with *Plan again*, and the operations list filters by it. The server sets it only from the executor's answer: from a successful `RejectPending`, or when its approval check or the expiry sweep receives `REJECTED` from `GetPermitState` (then it marks the execution `rejected`, not `expired` or `approved`). The expiry sweep already asks `GetPermitState` for every execution it would mark `expired` before marking it (m0 decision 82) and now also acts on `REJECTED` (previously: it acted only on `APPROVED` and expired every other answer); because the marker is persistent and outlives the approval window by at least `RetainSpentExecutions`, the sweep, which runs after the window plus the server's expiry grace, still sees `REJECTED` for a rejection made in the last check interval, during server downtime or before an executor lock or restart. If the executor cannot be reached, the sweep leaves the execution `pending` and asks again on its next run; it never marks an execution `rejected` without `REJECTED` from the executor. A `rejected` execution never returns to `pending`.
- **Server crash between `RejectPending` and its update.** Before it calls `RejectPending` the server stores a **rejection intent** in the pending execution record (user of the privileged session, reason text, time; previously: none) without changing the state; the intent is server data only and has no effect on authority. A refused call (any error code) clears it; a successful call is followed by the guarded update to `rejected` and the audit record `execution_rejected`. If the server crashes or loses the answer after the executor committed, it learns the rejection later from `GetPermitState` (approval check or sweep) and attributes it by the rejecting role: role `server` with an intent present writes `execution_rejected` with the intent's user and reason length, marked "recorded after restart", and shows the stored reason; role `server` without an intent writes `execution_rejected` with an empty user and shows "Rejected in the web UI; user not recorded"; role `admin` writes `execution_rejected_on_cli`, shows "Rejected on the executor host" and drops any intent left over from a server call that never reached the executor. The signed executor event stays the authoritative record of who rejected.
- **Batches.** Everything in this section for the executions table applies equally to the server's record of a `batch-v1` plan, keyed by the batch digest (previously: the server side of a batch rejection was unspecified): the batch gets the state `rejected` as a whole by the same guarded update (`WHERE id=? AND state='pending'`), and in the same server transaction every member execution record of that batch gets the state `rejected` with the detail above; no member is ever dispatched. `GetPermitState` accepts a batch digest as well as an execution digest (previously: execution digest only) and answers `PENDING`, `APPROVED` or `REJECTED` for the plan; the approval check and the expiry sweep ask it for every pending batch exactly as for executions, so a batch rejected with `nebula reject` on the executor host, or during server downtime, is learned and recorded like an execution, with the intent and role rules above. The server stores no batch plans yet (m0); this applies to the batch record when it is added and is an acceptance criterion of that ticket.
- **Error codes.** Each refusal changes nothing.

  | Code | When |
  | --- | --- |
  | `permit_already_rejected` (new) | `RejectPending` for a digest with a row in `rejected_proposals`, also after its approval window, lock or restart (takes precedence over every other digest answer) |
  | `permit_already_approved` (new) | `RejectPending` for a digest that is approved, in use or consumed |
  | `permit_rejected` (new) | `SubmitAssertion`, `ApproveCLI`, batch approval or member permit derivation for a digest with a row in `rejected_proposals` (takes precedence over `permit_not_found` and `permit_expired`) |
  | `permit_not_found` | `RejectPending` for a digest that is not rejected and not in memory: never proposed, approval window ended, or dropped by lock or restart (previously: an ended window was `permit_expired`; `RejectPending` never returns `permit_expired`) |
  | `privileged_session_required` | Server-role `RejectPending` without an open privileged session |
  | `invalid_request` | Malformed digest, a reason outside the limits below, or a `relayed_user` outside its limits (or present from the `admin` UID) |
  | `storage_error` | `RejectPending` whose marker lookup, event signing or `executor.db` transaction (binding check, rejected marker and event) fails before or at the commit; the transaction is rolled back and nothing is changed. Never returned after a successful commit |

  The server maps them to its own refusals before and after the call: it refuses a rejection of an execution that is not `pending` in its database before contacting the executor, as it does for approval. On `permit_not_found` for a record it still holds as `pending`, it changes nothing and shows "No longer pending on the executor (expired, or the executor was locked or restarted)"; the expiry sweep then sets the final state from `GetPermitState` as above.
- **Race of approval and rejection.** Both are decided only inside the executor, under the lock above: whichever reaches it first wins; the second receives `permit_rejected` (late approval) or `permit_already_approved` (late rejection). A browser assertion, a `nebula approve` confirmation and a rejection that arrive together therefore never both succeed. The server updates its record with the same guarded update as `Approve` (`WHERE id=? AND state='pending'`) and dispatches only when its approval update moved the row; it never dispatches a rejected execution.
- **Reason.** Optional; at most 200 characters (Unicode code points) and at most 800 bytes, valid UTF-8, no control characters (C0, C1, DEL) and no bidirectional control characters; otherwise `invalid_request`. The executor checks the limits and records only the length; the server stores the text in the execution record and renders it as text only. The reason is never part of a digest, challenge or authorization input, and it is never sent to an LLM (help assistant facts, ops agent work items, vulnerability agent) or to a notification target; no notification event is raised for a rejection. A rejection made with `nebula reject` shows its reason on the executor host only; the server shows "Rejected on the executor host".
- **Audit.** The executor writes one signed, hash-chained event `permit.rejected`, appended in the transaction of phase 2 above (so a committed rejection always has its event, and a failed one has none), with digest, kind, execution or batch ID, calling role, the request's `relayed_user` only after it passed the limits above (marked server-claimed; empty for the admin UID), the executor-known `session_credential_id` (empty for the admin UID), time and reason length, never the text. Refused rejections are logged with digest and code. The server writes `execution_rejected` (execution ID or batch ID, digest, user, time, reason length) for a rejection from the UI, also when recorded after restart as above, and `execution_rejected_on_cli` (execution ID or batch ID, digest) when `GetPermitState` reports `REJECTED` with role `admin`.
- **Authoritative wording.** The input rules for `relayed_user` and the reason, the phases of the atomic step and the error codes in this section are authoritative; ADR 0007 R3–R6 summarise them.

<a id="v23-07-09"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-09 -->
**Read lifecycle and audit.** Standard approval uses one grant-bound UV assertion without a prior privileged session; hardened approval is executor-local CLI, and recovery cannot create grants. Approved grants and spent budgets persist, pending proposals do not. Runs require unlocked execution credentials but neither a privileged session nor per-run approval. Session expiry leaves leases usable. Lock wipes keys, pauses grants and cancels queued dispatch; restart starts locked. Explicit local unlock resumes still-valid grants; paused time counts toward expiry. UI/CLI revocation needs no assertion and blocks every future claim; serialize revocation/lock with dispatch so queued work cannot escape. Running work may finish. Re-pin, removal, rotation, trust withdrawal or raised risk blocks affected scope; identity/version changes need replacement grants. Credential removal/recovery pauses grants until local review/unlock. Audit proposals, approver, digest/scope/budget, renewal, pause/resume, revocation, denials and each run's claim/outcome, keeping sanitized results in execution history. Show expiry, budget, blocked reasons and a prominent Revoke.

<a id="v23-07-10"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-10 -->
**Legacy schedules.** `read-schedule-v1` keeps its original schedule-only scope and expiry, including existing 90-day approvals. Never reinterpret an old signature as on-demand authority. New grants and renewals use the 7-day default/30-day maximum, superseding ADR 0006's proposed 90-day provider maximum. Migrate storage/accounting without duplicating authority; legacy grants share the executor target ceiling. List them with revoke or explicitly approved replacement.

<a id="v23-07-11"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-11 -->
**Canonical batches.** `batch-v1` binds batch ID, expiry, stage/dependency graph and hash, and an ordered list of member IDs and complete canonical execution requests. Bounds: 1–100 expanded action-target members, 1 MiB canonical plan bytes, 20 stages and at most 24 h execution expiry. Twelve host updates plus three container restarts are fifteen members; no wildcard, implicit descendants or automatic approval chunks. Each member binds exact action/module/adapter version, artifact hash, target/key or provider identity/generation/pin, credential references/versions, canonical parameters hash, precondition hashes and executor-derived risk. Container members also bind full ID, configuration and old/new image digests. Supply bounded parameter documents/artifact bytes for executor validation; secret values remain opaque executor-held references. Reject duplicate IDs or action-target-parameter tuples, malformed UTF-8, unknown/duplicate keys, cycles, missing dependencies and excessive sizes. Order matters: any reorder, insertion, removal or edit needs a new digest.

<a id="v23-07-12"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-12 -->
**Batch member authority.** The executor approves the strictest member under [05-authentication.md](05-authentication.md), rejecting the whole proposal for any CRITICAL member. It derives internal single-use member permits bound to parent digest, index/ID, exact request and parent expiry; no bearer batch token may authorize arbitrary children. Claim execution IDs atomically under the spent-ID discipline before dispatch. Recheck ordinary per-run trust, risk, pin, parameter, credential and stage conditions; concurrent/replayed members cannot run twice. A raised risk invalidates remaining batch authority and needs a fresh plan. Batch/child approval and gates stay memory-only: lock/restart revokes them, and expiry ends undispatched rights. Persist intent/outcomes only for reconciliation. Audit approver/digest, member derivation, claims, dispatch, outcomes, denials, gates, skips and revocation without secrets.

<a id="v23-07-13"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-13 -->
**Member stages and partial outcomes.** Extend the existing stage unit from host to member so actions on one host cannot bypass order or reuse permits. Show success, failure, skipped, not-executed and unknown separately; a batch is not a transaction. Dependencies enforce ordering and required postchecks. Default failure policy stops every undispatched member; only explicitly approved thresholds may let independent members continue. Reconcile running jobs first. Retry/rollback needs fresh exact-target approval, with no automatic rollback or uncertain redispatch. Manual LOW/MEDIUM gates require a privileged-session click; HIGH gates need fresh UV bound to batch digest and stage (CLI in hardened mode), never automatic HIGH continuation. Skips are audited and cannot satisfy unmet dependencies.

<a id="v23-07-14"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-07-14 -->
**Provider durable jobs.** Persist intent and claim single-use authorization in `executor.db`, fsync before sending the mutation. Persist returned UPID, task node, exact target tuple, request digest and timestamps before reporting it. Reuse job states with the PVE task as remote job, without uploaded shell/systemd unit. Poll typed status and require action-specific postchecks; accepted request/UPID is not success. After either process restarts, stored jobs allow read-only reconciliation with read credentials once unlocked, never mutation authority. Lost responses enter reconciling then unknown if the exact task cannot be identified; power state alone is not success, and missing/expired task records preserve uncertainty. HA operations without UPIDs require durable intent and observed manager/guest convergence. Cancellation stops undispatched work; cancelling a remote task requires separately approved authority. Lock cannot undo an accepted task.
