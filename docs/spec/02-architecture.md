# Architecture and trust boundary

```
            Browser (WebAuthn)                    nebula CLI (admin UID)
                  |  HTTPS                          unlock / approve / lock
                  v                                         |
          Reverse proxy (TLS, fixed hostname)               |
                  |  localhost                              |
+-----------------v-----------------------------------------v---------------+
| Nebula machine - one OS user per role                                     |
|                                                                           |
|  nebula-server  ---- gRPC over Unix socket ---->  nebula-executor         |
|  web UI, inventory,   (SO_PEERCRED decides)       keyring, vault, permits,|
|  planning, read API                               WebAuthn + hash checks  |
|  holds no keys                                    no network listener     |
|                                                                           |
|  nebula-discovery: one-shot Nmap, CAP_NET_RAW only, results to staging    |
+------|------------------------------------|------------------|------------+
       | outbound                           | SSH with permit  | scan
       v                                    v                  v
  Notifications                       Managed hosts         Network
  (ntfy, webhook, Telegram)           (untrusted input)     (reviewed import)
```

<a id="v23-02-01"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-02-01 -->
The server faces the browser and plans work; the executor holds every managed-host/provider credential, verifies each request independently and is the only process that talks SSH to hosts or HTTPS to PVE. The server and collector can trigger reads only inside executor-approved grants. Only the admin CLI may unlock or give hardened approval, enforced by the caller's UID on the socket.

<a id="v23-02-02"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-02-02 -->
**Provider read path.** In addition to the SSH path in the diagram, `nebula-server` writes typed poll/visible-target requests to a request spool; `nebula-pve-collector` (peercred role `pve-collector`) schedules typed metadata/read RPCs; the executor alone dials admin-approved PVE HTTPS origins, checks TLS and read authority, and returns sanitized fields. The collector alone writes result spool files; the server revalidates and imports them. The collector has no network access, listener, capabilities, credentials or database access. Neither spool direction accepts URLs, raw API paths or generic commands. PVE is a built-in typed provider, never a server-side module plugin.

<a id="v23-02-03"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-02-03 -->
**Registry egress boundary.** The server may additionally fetch anonymous public registry metadata within administrator-approved HTTPS registry/auth origins and the limits in [11-operations.md](11-operations.md). This permission does not include PVE API access, private registry credentials or image-layer pulls. Private registry metadata is executor-only under typed repository/tag read grants and vault custody. The unresolved approval lifecycle of public-origin configuration and private auth/pull profiles is recorded in [17-frozen-decisions.md](17-frozen-decisions.md); it must not be inferred from host-supplied image references.

<a id="v25-02-01"></a>
<!-- Spec revision (ADR 0013, EN-02): v25-02-01 -->
**One-step enrollment boundary (ADR 0013 D1, D2, D7).** One-step enrollment adds the first **unauthenticated endpoint that returns executor-generated content**: `GET /enroll/<offer-id>` on `nebula-server`, served through the reverse proxy outside the authenticated UI chain ([03-processes-and-data.md](03-processes-and-data.md#v25-03-05)). It returns only the script of an open enrollment offer, at most once, and the script is public content except for the optional NetBird setup key. The authority stays where it was: the **executor** creates and holds the offer (ID hash, salt, state), renders the script on demand, decides whether a pairing code matches, builds the paired enrollment permit and pins; the **server** only validates the ID syntax, determines the client address, rate-limits, calls the executor (`FetchEnrollScript`) and streams the bytes, and for the authenticated steps forwards operator input. No component on the host calls back to NOS: the only channel host → NOS is the operator, who carries the pairing code from the host's terminal into the web UI ([08-ssh-transport.md](08-ssh-transport.md#v25-08-01)). The reverse proxy is part of this boundary: it must run `/enroll/` (and the UI's "Show script" and "Download in browser" routes) without buffering to disk, without cache and without access log, and it is the only address whose `X-Forwarded-For` the server may honour, and only when configured as a trusted proxy ([03-processes-and-data.md](03-processes-and-data.md#v25-03-06)).

<a id="v25-02-02"></a>
<!-- Spec revision (ADR 0013, EN-02): v25-02-02 -->
**Executor NetBird egress (ADR 0013 D6; Q3, decided 2026-11-11).** In addition to SSH to hosts and HTTPS to PVE ([v23-02-01](#v23-02-01)), the executor may dial exactly one more destination: the **NetBird management API** at the management URL and with the TLS trust from executor-local configuration (public CA for NetBird Cloud; pinned CA or leaf for self-hosted management; never accept-any), never from the server or the browser. It uses only typed calls (create and revoke a setup key, get a setup key by key ID, list setup keys without a name filter, which reconcile filters locally ([06-credentials.md](06-credentials.md#v25-06-02) steps 3 and 5; previously: create, revoke and list setup keys by name), read with one request per pass because the endpoint is not paginated, within the key and byte limits of [03-processes-and-data.md](03-processes-and-data.md#v25-03-04); only a list that is complete as defined in [06-credentials.md](06-credentials.md#v25-06-02) step 5 is matched, any other result counts as truncated, matches nothing, revokes nothing and raises the unresolved alert instead of "no candidate" (previously: read page by page with an unnamed last-page indication; before that: no limit stated); list peers, get a peer, read the NOS peer; delete a peer after operator confirmation; read policies) with a token of a dedicated NetBird service user held in the executor vault ([06-credentials.md](06-credentials.md#v25-06-01)); there is no generic HTTP proxy, and NOS never creates or changes NetBird policies or groups. Without a configured token there is no NetBird egress and the NetBird option is hidden. The server, collector and discovery processes gain no NetBird access. Whether the reference lab uses self-hosted management or NetBird Cloud is established in the lab test before EN-12; both trust settings are supported.

<a id="v27-02-01"></a>
<!-- Spec revision (ADR 0014, AS-02): v27-02-01 -->
**Help assistant LLM egress (ADR 0014 D5; Q8, decided 2026-11-12).** When the help assistant is enabled ([01-product.md](01-product.md#v27-01-01); `assistant.enabled`, default off), `nebula-server` gains exactly **one** new outbound destination: the admin-configured LLM base URL (OpenAI-compatible chat API, as in ADR 0011 A1.4). Disabled, or without a configured URL, there is no such egress (previously: the server's own egress was notifications and anonymous registry metadata ([v23-02-03](#v23-02-03)) only; the diagram above does not show this optional destination). The rules:

- **Who dials.** Only `nebula-server`, through a dedicated HTTP client and dialer. The browser never talks to the LLM; `nebula-executor`, `nebula-discovery` and `nebula-pve-collector` gain no access, and the executor is not involved in an assistant request: the pin-derived enrollment state is read from the server's pin-state copy in `nebula.db`, which a separate server component refreshes through the existing server-role `ListHostKeys` method ([03-processes-and-data.md](03-processes-and-data.md#v27-03-01)); the executor criticality record is not sent (previously: "criticality, pin-derived enrollment state … from a server-side copy", without a writer).
- **Where.** The dialer connects only to the host and port of the configured URL and applies the **lab-only trust rule of ADR 0011 A1.4** to the address actually connected to, on every connection: loopback, RFC 1918, IPv6 ULA, or a **lab network** of the assistant settings (at most `MaxLabNetworks` = 8 CIDR ranges of at most 43 bytes each; previously: "operator-listed networks" without owner or bound). A lab network is checked on save by the parse, canonical-form, no-host-bits and duplicate rules of the NOS source addresses ([01-product.md](01-product.md#v27-01-01)) and must lie **inside `100.64.0.0/10`**: loopback, RFC 1918 and ULA are always accepted, so an entry inside them would have no effect and is refused, as is any entry outside `100.64.0.0/10` (previously: "inside these ranges or `100.64.0.0/10`", which admitted entries without effect). A lab network therefore can only widen the accepted set within `100.64.0.0/10`, never to a public address; `100.64.0.0/10` also holds ISP carrier-grade NAT and overlay-network peers (for example Tailscale) that may lie outside the operator's lab, so the admin lists only ranges the lab controls and the admin guide says so; IPv4-mapped IPv6 addresses are unmapped first; NAT64 addresses are always refused; a name that resolves to any other address, also after a DNS change, is refused. A hosted (non-lab) model is not allowed, with or without inventory facts (Q8). HTTP redirects are not followed; proxy environment variables are ignored. Transport is `https` with verified TLS, or plain `http` only with an explicit `allow_plain_http`, and then never with a credential. A refused endpoint fails closed: no request leaves, the user gets an error text, nothing else is affected.
- **Who configures it.** URL, model, credential reference, `allow_plain_http` and the lab networks are admin-only (as are `assistant.enabled` and the NOS source addresses, under the same rule; [01-product.md](01-product.md#v27-01-01)); a lab network widens the egress surface like a URL change; a URL with user info, query or fragment is refused on save; every change needs a fresh WebAuthn assertion bound to the complete new settings and the replaced settings version ([05-authentication.md](05-authentication.md#v27-05-01)), is audited with the same structured fields as the event in [13-notifications.md](13-notifications.md#v27-13-01): the admin, the time, which settings changed, the old and new URL in full (scheme, host, port and path), the old and new model name, the old and new credential reference name, the old and new `allow_plain_http`, the old and new enabled state, the old and new NOS source addresses, the old and new lab networks, and the replaced and the new settings version; never the credential (previously: only the URL host, so a change of scheme, port or path on the same host was not visible; and this list left out `allow_plain_http`, the enabled state, the source addresses and the settings versions), and raises `assistant.settings_changed` ([13-notifications.md](13-notifications.md#v27-13-01)). The credential is stored like the notification provider tokens, in the server configuration (owner `nebula-server`, mode 0600; [03-processes-and-data.md](03-processes-and-data.md#v27-03-01)), and never shown back, logged, sent to the browser or put into a prompt.
- **What is sent.** Per question one chat request with: a fixed system prompt; at most `k` = 6 documentation chunks (≤ 24 KiB) from the embedded handbook, FAQ and admin guide, in a delimited block; only if the user opted in for this question, the inventory facts for the hosts the question names (≤ 10 hosts, ≤ 4 KiB, only the fields listed in [01-product.md](01-product.md#v27-01-01)) in a delimited block marked as data; the question (≤ 2 KiB, after the secret-pattern guard); and at most 6 earlier turns of the same panel session, oldest dropped first when they do not fit (refused without an LLM call if even none fits; [01-product.md](01-product.md#v27-01-01)). The prompt is ≤ `MaxPromptTokens` = 12,000 tokens as NOS estimates them from bytes (⌈bytes ÷ 3⌉ plus 8 per message, no tokenizer; [01-product.md](01-product.md#v27-01-01)), the requested output ≤ `MaxOutputTokens` = 1,500 tokens. **Never sent:** secrets, credentials, key references or material, host-key fingerprints, vault, TOTP or WebAuthn data, API tokens, audit entries, execution logs or outputs, vulnerability findings, flows, topology, Proxmox credentials, notification targets, any user name (the asker's included; previously: "other than the asker's display name"), or anything of another user's conversations.
- **What comes back.** The response is untrusted input: the body is read to at most `MaxLLMResponseBytes` = 64 KiB plus one byte before parsing, and a longer body is discarded unparsed (previously: no named limit); it is accepted only as a chat API response carrying one JSON object of the ADR 0014 D4 schema (≤ 8 KiB), otherwise discarded with "the assistant returned an invalid answer"; only validated schema fields are rendered, and only as text.
- **Bounds.** Request timeout 90 s; a cancelled browser request cancels the LLM call; a dedicated bounded worker pool, so a slow or failing LLM cannot starve other server handlers: at most `MaxAssistantWorkers` = 4 LLM calls at once, at most `MaxAssistantQueue` = 16 requests waiting, each for at most `MaxAssistantQueueWait` = 10 s (the 90 s timeout starts when a worker takes the request); a request that finds the queue full or waits longer gets "the assistant is busy, try again later", makes no LLM call, releases the user's one in-flight slot (which a waiting request holds) and counts against neither the per-user hourly nor the global daily limit; a request counts against both when a worker takes it, and the binding limit check is made at that moment, atomically with the increment and before the LLM call, so queued requests cannot pass the 300/day cap ([01-product.md](01-product.md#v27-01-01)) (previously: pool size and queue not named, and only the daily limit stated for "busy"); the per-user and global rate limits of [01-product.md](01-product.md#v27-01-01).

Authority does not move: the assistant's output is never an input to planning, proposals, permits, schedules, leases or the executor.
