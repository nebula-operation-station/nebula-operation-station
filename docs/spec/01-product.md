# Product definition, principles and non-goals

Nebula Operation Station is a self-hosted operations control plane for Linux homelabs of about 5 to 100 hosts. It makes administrative changes visible, controlled, reviewable, reproducible, recoverable and auditable.

It combines a network asset inventory with light IPAM, a managed host inventory, SSH-based operations, Debian/Ubuntu patching, service and Docker operations, versioned runbooks, extensible host-side modules, staged multi-host rollouts, execution history and executor-held credentials.

Stack: Go, SQLite, Linux, SSH. One static binary per role, no external database or message broker.

Principles:

<a id="v23-01-01"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-01-01 -->
- **Agentless-first.** No persistent Nebula daemon on managed hosts. Hosts may keep small state under `/var/lib/nebula/` (`inventory.json`, `jobs/`); scripts are transferred only for execution.
- **Operator-driven.** Nebula never patches, reboots, updates containers, rolls back hosts or changes network configuration on its own in V1. Scheduling and on-demand read leases are limited to reviewed read-only work under the exact scopes, expiry and budgets in [07-execution-model.md](07-execution-model.md); discovery retains its separate reviewed scan scope.
- **Pull-first.** Nebula fetches information. Managed hosts never receive Nebula credentials and never write into Nebula's databases.
- **The server proposes, the executor authorizes.** Every privileged action is bound to the exact artifact, targets, parameters and credentials that were approved.
- **Host data is untrusted input.**
- **Honest limits.** Where a protection is partial, the documentation says so.

<a id="v23-01-02"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-01-02 -->
Not a goal for V1: Windows, a persistent agent, event-triggered or scheduled mutations, automatic patching, reboots, Docker updates or rollbacks, Kubernetes, general storage management, general vulnerability scanning or monitoring dashboards, DNS or DHCP management, OIDC, enterprise RBAC, a full Ansible replacement, third-party server plugins, a self-updater. The bounded inventory telemetry and optional local-image CVE observations below are the only monitoring/scanning exceptions introduced here; no InfluxDB endpoint is added. ADR 0011 adds advisory vulnerability management below; it scans nothing itself (previously: the two exceptions above only). ADR 0015 adds bounded, advisory integrity monitoring below as a further exception (previously: no integrity monitoring). ADR 0014 adds an optional, default-off, advisory help assistant below; it decides, executes and authorises nothing (previously: no LLM-based feature in NOS).

<a id="v24-01-01"></a>
<!-- Spec revision (ADR 0011, VU-02): v24-01-01 -->
**Vulnerability management (ADR 0011, accepted 2026-11-09).** NOS records which known vulnerabilities apply to its hosts, images and network devices, prioritises them and shows attack paths to the maintainer's crown jewels. The Hermes agent on its own VM fetches the CVE feeds, matches and writes an assessment; NOS exports a bounded package inventory to it, stores and re-checks its findings and computes priorities and paths itself. Findings are **advisory**: no finding, score, path or assessment ever patches, updates, proposes, schedules or approves anything, so this does not change "Operator-driven" above. Still not goals: automatic patching from findings, feed fetching or matching inside NOS, an LLM that decides, executes or authorises anything (previously: "an LLM inside NOS"; reworded by ADR 0014 D7, see the help assistant below), an agent on managed hosts, active vulnerability probing or exploitation, matching distro packages on upstream versions, compliance reporting, device firmware updates.

<a id="v26-01-01"></a>
<!-- Spec revision (ADR 0015, IG-01): v26-01-01 -->
**Integrity monitoring (ADR 0015, accepted 2026-11-11).** A bounded monitoring exception next to vulnerability management above. **I1** checks NOS's own binaries, systemd units, built-in module files, web assets and root keys on the NOS machine against the YubiKey-signed `installed-files.json` of the admitted release, and NOS configuration against an admin-approved baseline. **I2** reads selected paths on managed Debian, Ubuntu and PVE hosts agentlessly with the fixed read-only built-in action `fim.scan` inside an approved read lease and compares them with a NOS-held, admin-approved baseline, and package files additionally with signed archive references once the package reference builder exists (ADR 0015 D8, Q6). I3 (measured boot and TPM attestation) is not part of this revision; it needs its own ADR (Q5). Findings are **advisory**, like ADR 0011 findings: no integrity finding ever patches, restores, reinstalls, rolls back or quarantines anything, and none starts, approves or authorizes an action, so this does not change "Operator-driven" or "Agentless-first" above (no daemon, timer, state file or baseline on the host). The only reactions that *withhold* NOS authority are the I1 unlock refusal on a code mismatch ([06-credentials.md](06-credentials.md#v26-06-01)) and the opt-in per-host "block mutations on open critical integrity finding", which withholds new permits, never cancels a running job, never touches the host and can always be overridden by the admin with a fresh assertion (Q3). **Honest limits.** A root attacker on a machine controls every answer that machine gives: I1 and I2 detect operator error, faulty automation and ordinary attackers, not a root attacker who tampers with the checker. A clean I2 result means "the host reported no unexpected change", never "the host is not compromised", and the UI and documentation use exactly that wording; the limits are listed in ADR 0015 "Honest limits". Still not goals: a persistent agent, inotify/fanotify, auditd or eBPF sensor on managed hosts, automatic restore or rollback, proving the absence of a rootkit, integrity of databases, logs and spools, containers or LXC guests as separate subjects, Windows and network devices.

<a id="v27-01-01"></a>
<!-- Spec revision (ADR 0014, AS-02): v27-01-01 -->
**Help assistant (ADR 0014, accepted 2026-11-12).** An **optional** how-to assistant in the web UI, **off by default** (`assistant.enabled`, admin-only, see below): it answers questions about operating NOS (German or English, in the language of the question, with a user-selectable override) with steps and command **suggestions** taken from the embedded documentation of the running release, and cites the sections it used. It lives in an "Assistant" panel on `/help` and a collapsible side panel that no page loads until it is opened. Disabled, the panel offers the static FAQ and handbook search only and no LLM call is made. The assistant is **advisory**: it never executes a command, calls the executor, creates a proposal, plan, permit, lease, schedule or approval, prefills a form that does, or changes any state other than its own rate-limit counters, audit entries and the opt-in conversation store; no endpoint accepts its output as input, there is no "run", "create proposal" or "open in operations" path, and the assistant code may not import the executor client, permits, operations, proposals, schedules or leases (import-boundary test). It is not a general chat, a troubleshooting agent that reads hosts, logs or execution output, or a tool-using agent; it fetches no web content and follows no links. So it does not change "Operator-driven" or "The server proposes, the executor authorizes" above. The rules (ADR 0014 D1–D5):

- **Who.** Every logged-in user may ask (Q9). Only an admin changes the assistant settings: LLM base URL, model name, optional credential reference (own values, with a "copy from vulnerability agent" action, Q1, that copies only the base URL and the model name into the form, never a credential or credential reference, because the server holds no vulnerability agent credential (ADR 0011 A1.8), and that saves nothing by itself: the copied values go through the same save, assertion, audit and event as typed ones; previously: the scope of the copy was not stated), `allow_plain_http`, `assistant.enabled` and the **NOS source addresses** offered for `--from` (Q6: an admin-set server setting, never inferred; at most `MaxSourceAddresses` = 4 entries, each an IPv4 or IPv6 address literal or CIDR range of at most 43 bytes, checked on save by the **source address rules** below; they enter the trusted host set of V5 below, so they are guarded like the URL; previously: no assertion, audit or event for this setting) and the **lab networks** the egress dialer accepts ([02-architecture.md](02-architecture.md#v27-02-01); previously: "operator-listed networks" without an owner); every such change needs a **fresh WebAuthn assertion** bound to the complete new settings and the settings version it replaces ([05-authentication.md](05-authentication.md#v27-05-01); previously: no binding stated), is audited and raises `assistant.settings_changed` ([13-notifications.md](13-notifications.md#v27-13-01)). Where each setting is stored: [03-processes-and-data.md](03-processes-and-data.md#v27-03-01). A base URL with user info, query or fragment is refused on save, so the URL holds no credential and the audit entry and event can carry it in full. Disabling the vulnerability assessor does not disable the assistant and vice versa.
  **Source address rules (checked on save; previously: "checked on save" without rules, so `0.0.0.0/0` or `::/0` would have been accepted and V5 would then have admitted a copyable `--from` that allows any address).** Each NOS source address entry is parsed as an IP address or a CIDR prefix (Go `net/netip`) and refused unless all of the following hold: (1) **canonical form**: the entry is byte-equal to the canonical text of the parsed value (IPv4 dotted decimal without leading zeros, IPv6 in lower-case RFC 5952 form), no zone (`%eth0`), no IPv4-mapped IPv6 form (`::ffff:a.b.c.d`), no surrounding space; (2) **no host bits**: a CIDR entry equals its own masked prefix (`192.168.22.0/24`, not `192.168.22.1/24`); (3) **minimum prefix length**: IPv4 prefixes at least `/MinSourcePrefixIPv4` = `/24`, IPv6 prefixes at least `/MinSourcePrefixIPv6` = `/64`; a single address counts as `/32` or `/128`; (4) **no special addresses**: not unspecified (`0.0.0.0`, `::`), not multicast, not the IPv4 limited broadcast `255.255.255.255`, not inside `0.0.0.0/8`, and no prefix that contains one of them; (5) **no duplicates**, also not one entry contained in another. A refused entry refuses the whole save with the entry and the rule it broke; nothing is rewritten into canonical form silently. The same parse, canonical-form, no-host-bits and duplicate rules apply to the **lab networks** ([02-architecture.md](02-architecture.md#v27-02-01)), whose range rule there replaces rules (3) and (4) and which, unlike source addresses, must be CIDR prefixes (a bare address is refused; previously: not stated). Through source 3 of V5, a `--from` element is admitted only when its text, exactly as it appears in the command, is byte-identical to the stored text of one entry (an address to an address entry, a CIDR element to a CIDR entry, as in ADR 0014 D4). The validator applies **no canonicalisation** before this comparison: it does not parse, mask host bits, unmap `::ffff:` forms, strip zones, change case or remove leading zeros, and stored entries are already canonical by rule (1), so only the canonical text can match. A non-canonical element, such as `192.168.22.1/24`, `192.168.022.0/24`, `::FFFF:192.168.22.1`, `fd00::1%eth0` or upper-case IPv6, therefore matches no entry and is red, and the command is shown unchanged (previously: "byte-identical, after the same canonicalisation", without a defined canonicalisation). An address inside a CIDR entry is not admitted by that entry, so these rules bound the widest copyable `--from` at a `/24` or `/64` that an admin set under a fresh assertion.
- **Knowledge (D2).** Only the operator handbook incl. FAQ and the admin guide embedded in the release (Q4: no spec, ADRs or plans), never fetched or added at runtime, no operator upload. One chunk per H2 section (split at H3, then at paragraphs, above `MaxChunkBytes` = 6 KiB); deterministic lexical retrieval (BM25, standard library, no embedding model, Q3); German questions through a reviewed synonym table (Q2); top `k` = 6 chunks up to `MaxContextDocBytes` = 24 KiB per prompt. Every answer must cite chunk IDs that were in its prompt; NOS builds every link from its own index, never from model output; an answer without a valid citation is shown as "no documentation section supports this answer" and all its commands are flagged.
- **Inventory facts (D3).** Only per question and opt-in (checkbox, default off, Q5); only for hosts the question names (address, CIDR, inventory name or ID) **and** the asking user can see in the inventory; at most `MaxFactHosts` = 10 hosts and `MaxFactBytes` = 4 KiB. Allowed fields only: display name and inventory ID (name ≤ 64 bytes), up to 4 endpoints, criticality (the inventory value, labelled "inventory"; previously: also the executor value), enrollment state with its observation date, OS family and release (≤ 32 bytes), up to 4 NOS source addresses. **Never** secrets, credentials, key references or material, host-key fingerprints, vault, TOTP or WebAuthn data, API tokens, audit entries, execution logs or outputs, vulnerability findings, flows or topology, Proxmox credentials, notification targets, or any user name, the asker's included (previously: "user names other than the asker's display name", which left open whether the asker's name is sent; it is not); the fact projector is a fixed struct with no access path to other stores. The pin-derived enrollment states "host key pinned" and "blocked (key changed)" come only from the server's pin-state copy in `nebula.db`, which the server refreshes through the existing server-role `ListHostKeys` method and which the assistant code only reads ([03-processes-and-data.md](03-processes-and-data.md#v27-03-01): writer, method, refresh at most every 60 s, older than 10 min gives "unknown"); never from `executor.db` or an executor call by the projector, so the import boundary above stays intact. The executor's own criticality record is not sent (previously: the source of these values was not stated, and the executor criticality was an allowed field). Facts are validated as untrusted data and sent in a delimited block that the prompt marks as data, not instructions.
- **Output (D4).** One JSON object, checked strictly (unknown fields or invalid UTF-8 discarded; ≤ `MaxAnswerBytes` = 8 KiB; summary ≤ 1 KiB; ≤ 12 steps, step text ≤ 1 KiB, command ≤ 512 bytes on one line; ≥ 1 citation when in scope); an off-topic question gets a fixed NOS text. Everything is rendered as escaped text: no Markdown, HTML or links from model output, control, bidi and zero-width characters replaced. Every answer and the panel header carry the label "Generated by an LLM – check every command against the cited section before you run it." (German: "Von einem LLM erzeugt – prüfe jeden Befehl am zitierten Abschnitt, bevor du ihn ausführst."). Each command passes the deterministic **command validator** in NOS, an allowlist by shape: printable ASCII only (V1); a `nebula` command only with subcommands and flags from the catalog built from the `cmd/nebula` command tree (V2); any other command only as an exact shape from a code block of a cited section (V3); values of fixed classes, ≤ 255 bytes each (V4); host values only from the question's exact tokens, the inventory endpoints of the fact hosts (for reviewed commands that send no credential only) or the NOS source addresses (V5); destructive shapes at least amber (V6). Anything else is **red**. The validator never rewrites a command. Red commands have no Copy button (Q7); amber ones do; a command with an unchanged placeholder is never copyable. The Copy button copies exactly the shown text and is a convenience, not a control; the control is the visible flag and label.
- **Limits and storage (D5).** Per user 20 questions per hour and 1 in flight; 300 questions per day overall (Q9); question ≤ 2 KiB; prompt ≤ `MaxPromptTokens` = 12,000 and output ≤ `MaxOutputTokens` = 1,500 tokens; request timeout 90 s, a cancelled browser request cancels the LLM call; a bounded worker pool ([02-architecture.md](02-architecture.md#v27-02-01): `MaxAssistantWorkers` = 4, `MaxAssistantQueue` = 16, `MaxAssistantQueueWait` = 10 s). A question counts against the per-user hourly and the global daily limit when a worker takes it; a waiting question holds the user's one in-flight slot, and a "busy" refusal (queue full or wait exceeded) releases that slot and counts against neither limit, because no LLM call is made (previously: only the daily limit was stated). **When the limits are checked** (previously: not stated, so a check only at enqueue would have let up to `MaxAssistantWorkers` + `MaxAssistantQueue` = 20 queued and running questions pass the 300/day cap): at enqueue as a pre-check that counts nothing (a question that would already exceed a limit is refused without queuing), and again, binding, when a worker takes the question: the check and the increment of both counters are one atomic step under the limiter's lock, before the LLM call; a question that fails it is refused with the limit text, makes no LLM call, releases the in-flight slot and counts nothing. Within one server process lifetime the global daily count therefore never exceeds 300 and a user's hourly count never exceeds 20, whatever the queue holds (a restart resets the counters, see below). The windows are a sliding hour per user and the UTC calendar day overall, measured with the injected clock; the counters are in memory, so a restart resets them (spec 03). **How NOS counts tokens** (ADR 0014 D5: "estimated conservatively from bytes"; previously: not carried over, so the bound depended on the implementation and the model's tokenizer): NOS uses no tokenizer; the estimate of a text is ⌈UTF-8 bytes ÷ `PromptBytesPerToken`⌉ with `PromptBytesPerToken` = 3, plus `PromptMessageOverheadTokens` = 8 per chat message, summed over every message of the request (system prompt, the delimited docs and facts blocks, earlier turns, the question). `MaxPromptTokens` = 12,000 is checked against this estimate only, so the bound NOS enforces is in bytes and the same for every model: at most 36,000 bytes of message content minus the message overhead. The startup refusal and the oldest-turn rule below use the same estimate. The request asks for at most `MaxOutputTokens` (`max_tokens`), and the output is bounded independently by `MaxLLMResponseBytes` and `MaxAnswerBytes`. The estimate is **not** an upper bound on the model's own count and is not model-independent in that sense: a model's tokenizer can count more tokens than the estimate (runs of digits, symbols or non-Latin text can reach about one token per byte), so a prompt that passes `MaxPromptTokens` can still exceed a model's context window. Such a request is rejected by the model, and NOS then shows an error text and stores and retries nothing (fail closed). The admin guide therefore states the requirement in bytes, not in estimated tokens: the model's context window must hold 36,000 bytes of prompt content plus its chat-message overhead and `MaxOutputTokens` of output in the model's own count; for any content this needs at least 36,000 + 1,500 = 37,500 tokens plus the model's per-message template tokens, and a smaller window works only for typical prose and fails closed otherwise (previously: "a context window of at least `MaxPromptTokens` + `MaxOutputTokens` in its own count", which does not guarantee that a 36,000-byte prompt fits). A configuration whose fixed prompt parts (system prompt, `k` chunks at `MaxContextDocBytes`, facts at `MaxFactBytes`, question at its limit) cannot fit `MaxPromptTokens` is refused at startup. Earlier turns are added per request: if they do not fit, NOS drops the **oldest** earlier turns until the prompt fits and tells the user how many were left out; if it still does not fit without any earlier turn, the question is refused with an error text and no LLM call (previously: the per-request case was not stated). A question containing a private-key block, an `AGE-SECRET-KEY-`, a NOS API token or an `otpauth://` URI is rejected before sending (a guard, not a guarantee). Conversations are **not stored** by default: follow-ups carry at most 6 earlier turns of the same panel session, in server memory only, for at most 30 minutes, cleared at logout or restart. Per-user opt-in storage (Q10): at most `MaxStoredConversations` = 50 conversations, at most 30 days, at most `MaxStoredTurns` = 20 turns and `MaxStoredConversationBytes` = 256 KiB per conversation (so at most 12.5 MiB per user; previously: no per-conversation bound); a further question in a full conversation starts a new one, and a new conversation beyond 50 deletes the user's oldest; deletable by the user, not in backups by default (a separate file, [03-processes-and-data.md](03-processes-and-data.md#v27-03-01), [15-backup-and-upgrades.md](15-backup-and-upgrades.md#v27-15-01)), never visible to other users, admins included; facts sent in a turn are never stored, only the rendered answer. One audit entry per **counted** question, that is per question that passed the binding limit check at worker take-up, whatever its outcome afterwards (answer, prompt does not fit, LLM error, timeout, cancellation, discarded output): user, time, language, chunk IDs, facts on and host count, token counts, validator flag counts, outcome, keyed question hash; never the question or answer text. A question refused **before** that point (size limit, secret-pattern guard, enqueue pre-check, "busy", or the binding check itself) writes **no** audit entry, event or per-question log line; NOS only increments an in-memory counter per refusal reason (lost at restart). Audit entries of the assistant are thus bounded by the rate limits: at most 20 per user per hour and 300 per UTC day overall within one process lifetime (previously: "one audit entry per question", which read literally let a user create audit rows without limit through refused questions). The **keyed question hash** is HMAC-SHA-256 under the server's assistant audit key over the domain separator `nebula-assistant-question-v1`, a zero byte and the question bytes as received (previously: an unsalted SHA-256, so a short secret that got past the pattern guard, such as a pasted password, could be confirmed by a dictionary attack against the audit log). Equal questions under the same key still give equal hashes, so abuse correlation is kept; without the key the hash confirms nothing. The key is 32 bytes from `crypto/rand`, generated by `nebula-server` on first use, stored as described in [03-processes-and-data.md](03-processes-and-data.md#v27-03-01), and never logged, audited, sent, shown or put into a prompt; a lost or replaced key only breaks correlation with older entries.
- **Egress.** Only `nebula-server` calls the LLM, at exactly the configured URL and only inside the lab ([02-architecture.md](02-architecture.md#v27-02-01)); the browser never talks to it, and `nebula-executor` gains nothing.

**Honest limits.** A user who ignores the label and runs a plausible but wrong command that the validator does not flag (for example a documented command with a wrong host argument) is not protected; the assistant reduces typing, not responsibility. The threat items are in [docs/threat-model.md](../threat-model.md#llm-output-help-assistant-adr-0014). Placement (Q11): after the embedded docs (hb01) and the LLM settings model (va09). Nothing here is implemented yet (tickets AS-03 to AS-13 in `docs/implementation/help-assistant.md`).

**Proxmox integration phases.** Phase 1 adds read-only PVE remotes, reviewed inventory links and staging, an org chart, patch/image state, optional host-local image CVE observations, backup-freshness warnings, GPU/CPU/RAM/filesystem values with 24 h averages, service checks, drift hints and PVE deep links. Phase 2 adds explicitly approved VM/LXC operations and tree-triggered OS/container/Compose updates and rollback; lifecycle actions ship first, with each further privilege profile gated separately. Phase 3 adds optional snapshot-before-update and provisioning; consoles require a separate credential/session review. Rolling node maintenance, cross-remote migration, WoL, Datacenter Manager and hypervisor shells remain separately scoped follow-ups. These phases do not imply unattended mutations.

<a id="v23-01-04"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-01-04 -->
**Standing reads and exact change plans.** The executor holds durable read grants for frozen actions, targets and parameters; the server or collector may trigger only those reads and spend their budgets, without a privileged session or per-run assertion. A compromised server can consume this bounded disclosure/load authority and see sanitized results. Mixed-action batches authorize one fully enumerated change plan, with single-use members, existing gates and no CRITICAL members; they do not authorize future plans. See [05-authentication.md](05-authentication.md) and [07-execution-model.md](07-execution-model.md).
