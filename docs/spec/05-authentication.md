# Authentication, sessions and approval

WebAuthn is the primary login and the only way to approve privileged work in the browser. TOTP exists for account recovery only.

**Login.** WebAuthn with several credentials per admin (security key, platform passkey). The RP ID is the fixed hostname under which Nebula is served, with TLS the browser trusts; an IP address cannot be an RP ID. After a TOTP recovery the admin must register a new WebAuthn credential before any privileged action.

**Sessions.**

<a id="v23-05-01"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-05-01 -->
- Web session for reading (dashboard, inventory, history): long-lived, revocable.
- Privileged session, held by the executor in memory: 60 minutes by default, configurable to 15–240 minutes only in executor-local configuration validated at startup. A user-verified assertion opens it; lock/restart ends it. The server displays executor-reported expiry and remaining time and cannot choose the duration.

**Approval flow.**

1. The server sends the canonical execution request to the executor. Canonical encoding is RFC 8785 (JSON Canonicalization Scheme), so both sides hash the same bytes.
2. The executor computes `execution_digest` itself, stores a pending permit and returns a challenge = SHA-256(`execution_digest` ‖ 32-byte nonce ‖ expiry).
3. The browser signs that challenge; the assertion travels through the server to the executor.
4. The executor checks: credential known in `executor.db`, rpIdHash, origin on the allowlist, user-verified flag where required, signCount increased (if the authenticator counts), challenge matches the pending permit, not expired, not used before.
5. The executor issues a single-use permit.

<a id="v23-05-02"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-05-02 -->
| Effective risk | Required approval |
| --- | --- |
| LOW | Active privileged session for an interactive permit; the permit is issued automatically and logged. An exact approved read lease instead uses the separate grant path below |
| MEDIUM | Per-execution assertion (user presence), or one presence assertion for an exact batch; browser mutation approval also needs an active privileged session |
| HIGH | Per-execution assertion with user verification, or one user-verified assertion for an exact batch; browser mutation approval also needs an active privileged session; hardened mode uses the local CLI |
| CRITICAL | Per-execution assertion with user verification plus typing the number of targets; in hardened mode only `nebula approve`; reject the entire batch if any member is CRITICAL |

**Limit, stated in the docs.** An authenticator signs a challenge, not the human-readable request. A fully compromised server can show one request and propose another. `nebula approve <id>` shows action, artifact hash, targets, parameter summary and risk from the executor itself and is the defence; hardened mode makes it mandatory for HIGH and CRITICAL.

**Default approval mode.** V1 defaults to **Standard mode**: browser-based approval is permitted according to the risk table above, while the independent CLI approval path remains available. Hardened mode can be enabled to require CLI approval for HIGH and CRITICAL operations.

<a id="v23-05-03"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-05-03 -->
**Session extension.** One fresh user-verified assertion binds the session-extension operation and configured duration. Set expiry to approval time plus that duration; never accumulate extensions. An expired session uses the same single assertion to open a new one. Browsing, leased reads and mutation approval never silently extend it. Extension neither renews read grants nor resurrects permits. Read leases do not require a privileged session, and session expiry alone does not pause them. Audit session open/extension, configured duration/expiry, denials and lock/restart termination without secrets.

<a id="v23-05-04"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-05-04 -->
**Read-grant approval.** In Standard mode one fresh user-verified assertion approves the complete versioned grant digest, including frozen targets, exact actions/parameters, duration and budgets. Neither proposal nor approval requires opening a privileged session first. Use a grant-specific domain separator, nonce, five-minute challenge expiry and single-use verification with the normal RP/origin/counter checks. Recovery mode cannot create grants. Hardened mode requires executor-local admin CLI approval of the complete grant. New grants and renewals default to 7 days and last at most 30 days; renewal needs new approval. UI/CLI revocation needs no assertion. Execution, pause/recovery and audit rules are in [07-execution-model.md](07-execution-model.md).

<a id="v23-05-05"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-05-05 -->
**Batch approval.** The executor validates and holds the complete ordered `batch-v1` plan: 1–100 expanded action-target members, at most 1 MiB canonical bytes and 20 stages. The strictest member sets initial approval: LOW-only uses a privileged session, MEDIUM requires presence, any HIGH requires user verification. A batch-domain challenge binds its digest, nonce and five-minute approval window; execution expiry is at most 24 h. Reject CRITICAL members together with the entire proposal, displaying their identities; the admin must explicitly remove them and approve them separately. Never silently omit or automatically chunk members. Browser mutation approval retains the privileged-session prerequisite.

<a id="v23-05-06"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-05-06 -->
**Review and hardened batches.** Before confirmation, show every member, exact parameters, action/version/hash, target, effective risk, dependency, gate and total count; a summary or truncated list is insufficient. Escape all labels as text. Hardened HIGH approval uses `nebula approve <batch digest>`: only the local admin UID retrieves the executor's complete frozen plan and scanner findings and confirms it once, without a browser session. MEDIUM browser approval remains available. Fresh HIGH stage-gate UV (CLI in hardened mode) and LOW/MEDIUM privileged-session gate clicks remain required; initial batch approval does not remove gates. Audit the approver, complete plan digest, member permits/outcomes, gate releases, skips, denials and revocation. Lock/restart revokes pending and approved batch authority; running tasks may still finish.

<a id="v23-05-07"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-05-07 -->
**Approval deception.** Batch binding prevents substitution, replay and expansion at the executor but cannot prove what a compromised server showed the human. An authenticator signs the challenge, not the displayed plan. The independent executor-local CLI view remains the mitigation, mandatory for hardened HIGH/CRITICAL approval. Read leases deliberately allow bounded reads and budget consumption by a compromised server; a LOW label or clean scanner result is not proof that a root script is harmless.

<a id="v25-05-01"></a>

**Enrollment permits (ADR 0013 D1, D4, D6).** One-step enrollment adds three executor-built permits (previously: only the `ProposeEnroll`/`CommitEnroll` enrollment permit, which stays unchanged). All three are **HIGH with user verification** under the risk table above (privileged session for browser approval; hardened mode uses the local CLI), single-use, expire like other enrollment permits, and are shown with every bound field by `nebula approve` on the executor host. Substituting any bound field invalidates the permit.

| Permit | Proposed when | Binds | Authorises |
| --- | --- | --- | --- |
| Paired enrollment permit | The executor found that the pairing code matches the key presented at the endpoint | Offer ID hash, host ID, endpoint, "endpoint to add" flag, SSH user, credential reference, full SHA-256 fingerprint, the fact "code matched" (with the code); `nebula approve` also shows offer creation time and download address | One commit: re-probe, pin only the approved key, add the endpoint to the inventory host if flagged, test login ([08-ssh-transport.md](08-ssh-transport.md#v25-08-01)) |
| NetBird offer permit | An offer with NetBird is created (state `awaiting_approval`) | Offer ID hash, host ID, SSH user, credential reference, managed group, ephemeral flag, setup-key expiry | Creation of exactly one one-off setup key for that offer ([06-credentials.md](06-credentials.md#v25-06-02)); without it the offer has no setup key, no stored script hash and no download; "Show script" then shows only the placeholder render without a hash ([03-processes-and-data.md](03-processes-and-data.md#v25-03-04)) (previously: "no script") |
| NetBird peer delete permit | The operator deletes an orphan or rogue NetBird peer that is attributed only by the time-window fallback (Q8) | Peer ID, peer name, NetBird IP, offer ID hash, attribution method | One typed delete call for that peer ([06-credentials.md](06-credentials.md#v25-06-05)) |

The executor, not the server, decides whether a code matched and builds every one of these permits; the server only forwards the operator's input. A NetBird enrollment therefore takes two security-key touches (one to release the setup key, one to pin).

<a id="v25-05-02"></a>
<!-- Spec revision (ADR 0013, EN-02): v25-05-02 -->
**Offer session binding (ADR 0013 D1, D2).** Creating an enrollment offer requires an open privileged session. The offer is bound to the web session that created it: only that session may show the script, use the browser download, submit the pairing code, approve in the browser and commit. Another session, also of the same user, sees the offer read-only and may revoke it; the executor-local admin CLI may list and revoke offers. Lock, restart or the end of the privileged session does not resurrect the binding to a new session. **Approval path for the three enrollment permits ([v25-05-01](#v25-05-01)):** in Standard mode a permit is approved either by the creating session's browser approval (user verification, open privileged session) or by `nebula approve` on the executor host, whichever comes first; the permit is single-use, so the second approval of the same permit is refused. In hardened mode only `nebula approve` approves them; the executor refuses a browser approval, also from the creating session. In both modes the session binding still decides who may show, browser-download, submit the code and send the commit request, and an approval by `nebula approve` neither moves the binding nor lets another session commit.

<a id="v25-05-03"></a>
<!-- Spec revision (ADR 0013, EN-02): v25-05-03 -->
**Pairing-code trust anchor and approval deception (ADR 0013 D4, D7).** The pairing code replaces the operator's eye comparison of fingerprints, not the approval. Its authenticity rests on the operator's own session to the host: on the console or over an SSH session whose host key the operator already trusts it is as strong as the fingerprint comparison; over a first SSH login with trust on first use it is only as authentic as that login, and the UI and guide say so and recommend the provider's web console or a verified `known_hosts` entry for internet-facing hosts. A compromised server can still show the operator one thing and submit another code or endpoint, and it can serve a different script with its own hash (root on the new host); to pin a wrong key it must also control the network path to the endpoint. This equals the exposure of the web **Enroll hosts** flow ([v23-05-07](#v23-05-07)); the executor-local `nebula approve` view, and for high-assurance hosts `nebula host enroll-script` or comparing the hash with `nebula host offers`, are the mitigation (Q6, accepted 2026-11-11).

**Integrity baseline approvals (ADR 0015 D3, D7, D9, Q3).** Integrity monitoring ([01-product.md](01-product.md#v26-01-01)) adds two baseline approvals (previously: none). Each uses a fresh user-verified assertion like a read grant ([v23-05-04](#v23-05-04)): its own challenge domain, nonce, five-minute challenge expiry, single-use verification and the normal RP/origin/counter checks. Recovery mode cannot approve either baseline, in the browser or in the CLI.

| Baseline | Challenge domain | The signed challenge binds | Approval path |
| --- | --- | --- | --- |
| I1 configuration baseline of the NOS machine (D3): `(path, type, size, mode, owner, keyed SHA-256)` of `/etc/nebula/*`, admin-created `nebula-*` unit drop-ins and a locally edited iconfetch nftables file | `nebula-integrity-baseline-v1` | The digest of the complete list, which the executor shows with old and new values | Standard mode: browser assertion. Hardened mode: **only** the executor-local CLI; the executor rejects a browser assertion for a D3 baseline |
| I2 host baseline (D7) | `nebula-fim-baseline-v1` | The host ID, the currently approved digest the proposal was built on (the previous digest) and the new executor-computed digest | Browser assertion for entries that are not critical-class; every critical-class entry and the initial baseline only in the executor-local CLI ([v26-05-02](#v26-05-02)) |

- **The executor alone computes what is approved.** The digest is computed by the executor from the approved list (accepted only if its digest equals the executor-stored digest; otherwise an `integrity.baseline_tamper` finding and no approval) plus, for the paths the admin selects, the record values of the executor's own retained `fim.scan` run, or removal of the entry where that run shows the path absent. The server only names paths to include or remove; it cannot supply record values, a list or a digest. The approval screen is rendered from the executor's data; a server-supplied list or digest is at most compared, and a mismatch is a baseline tamper finding, never a reason to approve. The executor rejects an approval for another host or when its stored digest is no longer the bound previous digest (the baseline changed meanwhile).
- **Critical-class entries never in the browser.** Whether an entry is critical-class (ADR 0015 D9) is decided by the executor from its own data, never by the server. The executor rejects a browser assertion for a digest whose difference from the approved baseline adds, changes or removes a critical-class entry; unchanged critical-class entries carried over from the approved baseline do not prevent a browser approval.
- **Bulk approval.** Bulk approval per host and per finding batch is allowed except for critical-class entries. In Standard mode the verified expected changes of one NOS job, except critical-class entries, may be approved in one bulk `nebula-fim-baseline-v1` assertion offered right after the job (Q3). In every mode such changes enter the baseline only through an executor-computed digest, never through the job approval, which is given before the job and cannot bind a scan result. "Changed during NOS job, unverified" entries are never approved together with the job; they need their own baseline assertion, batched only for entries that are not critical-class, and the screen labels each "unverified: NOS cannot tell this change from an attacker's change made during the job". Every approved entry is audited with old and new values.
- **Limit, stated in the docs.** As for every browser approval ([v23-05-07](#v23-05-07)), an authenticator signs the challenge, not the displayed list: for browser baseline approvals a compromised server can show a harmless list while the assertion covers the executor digest of other paths it named; the record values still come from the executor's own scan. The executor-local CLI closes this gap for critical-class entries and, in hardened mode, for D3 baselines; its view is only as trustworthy as the NOS machine.

<a id="v26-05-02"></a>
<!-- Spec revision (ADR 0015, IG-01): v26-05-02 -->
**`nebula integrity pending` and `nebula integrity approve` (ADR 0015 D7).** A proposed I2 baseline that adds, changes or removes **any** critical-class path is approved only on the NOS machine, by the admin UID, audited, in every mode (the same independent executor view as `nebula approve`). These commands are its only approval path.

- **One entry per critical-class approval.** A proposal that changes a critical-class entry is built by the executor as the approved list plus exactly one added, changed or removed entry; `approve` rejects a digest whose difference from the approved baseline has more than one entry when any of them is critical-class (the initial baseline is the one exception, below).
- **Stored proposals.** For each proposed digest the executor stores, in executor-owned storage, the previous approved digest it was built on, the run ID of the retained records it took the values from, every differing entry with its old values (from the digest-checked approved list) and new values (copied from the retained run when the proposal was built), and that run's derived set. A newer run does not change a stored proposal. Bounds (named constants, fixed in IG-05): at most 16 stored proposals per host, of which at most one initial proposal (a new one replaces it); expiry 7 days after the executor built it (executor clock); on every new approved digest the executor deletes the host's proposals whose previous digest is no longer the approved digest. Bytes, measured as the stored difference entries plus derived set: one non-initial proposal at most 16 MiB (`maxProposalBytes`), the initial proposal at most 128 MiB (`maxInitialProposalBytes`), all proposals of one host at most 256 MiB (`maxProposalStoreBytesPerHost`), all proposals of all hosts at most 2 GiB (`maxProposalStoreBytes`). The executor refuses to build a proposal over its own limit (the admin approves in smaller batches; an initial run over the limit cannot be proposed and the admin is told so). When a per-host cap would be exceeded, the oldest non-initial proposals of that host are evicted; when the executor-wide cap would be exceeded, the oldest non-initial proposals of any host are evicted, and if it still does not fit (initial proposals are never evicted by another host's request) the request is refused. At most 30 new proposals per host per hour (`maxProposalsPerHostHour`, sliding window, executor clock); further requests are refused without evicting anything. An evicted or expired proposal is refused like an unknown digest.
- **`nebula integrity pending <host>`** lists stored proposed digests and approves nothing.
- **`nebula integrity approve <host> <digest>`**, whatever the source of the digest (typed, pasted from `pending` or from the browser), refuses a digest without a stored proposal and refuses when the executor's current approved digest is not the proposal's previous digest. Otherwise it renders **every** entry of that stored proposal's difference with old and new values, from the stored proposal and never from the current retained records, escaped as in [09-untrusted-host-data.md](09-untrusted-host-data.md#v26-09-01) "Display", together with the host ID and both digests. It approves only after an interactive confirmation on the terminal, has no flag that skips it and refuses when stdin is not a terminal. On confirmation it checks the previous digest again and, in one step, stores exactly the digest of the list it rendered as the new approved digest. The CLI never approves an entry it did not show.
- **`nebula integrity approve --initial <host> <digest>`** approves the first baseline. While the executor holds no approved digest for a host, the initial proposal is the executor's whole retained complete run and nothing else: the server names no paths and cannot add, drop or change an entry; its stored previous digest is "none". It is never approved in the browser. `--initial` is refused when the executor already holds an approved digest for the host, and a digest without `--initial` is refused while it holds none. The CLI first shows the "trust on first scan" warning, the host ID, the run ID, the digest and the number of entries per class, then **every critical-class entry** (escaped, paged), and asks the admin to confirm by typing the host ID; no flag skips the listing or the confirmation, and it refuses when stdin is not a terminal. Entries that are not critical-class are counted, not listed. The approval stores the digest and that run's derived set as S ([v26-05-03](#v26-05-03)).

<a id="v26-05-03"></a>
<!-- Spec revision (ADR 0015, IG-01): v26-05-03 -->
**Stored derived SSH set (ADR 0015 D7).** The executor classifies SSH configuration and SSH login files as critical-class from a set it derives itself from the `fim.scan` SSH configuration array ([09-untrusted-host-data.md](09-untrusted-host-data.md#v26-09-01)): the `Include` values (paths and globs as written, resolved against `/etc/ssh` like sshd), the files they matched and the SSH login file targets. It never keeps SSH configuration content, so next to the approved baseline digest it stores an approved derived set S and changes it only on a baseline approval, by this rule. Let R be the complete run the approved proposal was built from. The **SSH configuration entries** of a baseline are its entries for `/etc/ssh/sshd_config` and for every path that an `Include` value in S or in R's derived set names or matches. S is **replaced** by R's derived set only when all three hold:

1. the approval is an executor-local CLI approval (`nebula integrity approve`, including `--initial`); a browser approval never replaces S;
2. for **every** path in R's SSH configuration array, the newly approved baseline holds an entry equal to R's record of that path (type and content hash); and
3. the newly approved baseline holds **no** SSH configuration entry whose path is not in R's array.

In every other case S becomes the **union** of S and R's derived set and never shrinks. Classification uses the union of S and the latest complete run's set, so a pending `sshd_config` change or a deleted include never makes an entry non-critical; before the first approved baseline the run's set alone is used. S and the derived set of any one run hold at most 4,096 values (new named constant, fixed in IG-05); a run over it supplies no usable derived set, and a union that would exceed it marks S **overflowed**: while overflowed, every entry a proposed digest of that host adds, changes or removes is critical-class, until a replacement under the three conditions clears the mark. Without a usable derived set from the latest complete run, every changed entry of that host is critical-class.
