# Untrusted host data and log safety

<a id="v23-09-01"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-09-01 -->
Everything a managed host, PVE endpoint, registry, collector spool or host-local scanner returns is untrusted input: hostnames, facts, service, package and container names, `inventory.json`, `state.json`, `result.json` and log output. A compromised host must not be able to attack Nebula or the admin's browser.

- Strict schemas per capability contract (for example `package.list_updates@1`); unknown fields are dropped.
- UTF-8 validation, maximum field length, maximum object count, maximum payload size.
- Default limits, configurable: `result.json` 1 MB, `state.json` 64 KB, `inventory.json` 1 MB, execution log 10 MB per host and run.
- The UI renders host data as text only: no raw HTML, no host-provided templates, a strict Content Security Policy without inline scripts.
- Logs are stored in chunks with a size limit and a visible truncation marker, escaped on display and redacted for known secret values.
- Parsers for host data get fuzz tests before the beta (Go native fuzzing).

<a id="v23-09-02"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-09-02 -->
**Provider and spool limits.** Enforce named limits of 1 MiB decoded per response/spool page, 1,000 objects/page, 10,000 guests/remote, 128 interfaces/guest and 4 KiB/text field, with bounded nesting and pagination. Validate schemas, UTF-8, identifiers and numeric ranges, dropping unknown fields. Mark oversize/incomplete data as such, never as a complete empty dataset. Exact nesting/page-count limits are unresolved and must be specified before readers ship. These limits also apply to the new SSH observation contracts; runtime/action-specific limits must additionally bound expensive work.

<a id="v23-09-03"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-09-03 -->
**Allowlisted observations only.** Discard Cloud-Init passwords, SSH keys, snippets, descriptions, hook scripts, storage credentials and other non-allowlisted fields before spooling. Never persist raw API responses/errors, image configuration/files, raw scanner findings or secrets; phase 1 excludes PVE task logs/command output. Any phase-2 task-log excerpts must be bounded and sanitized. Registry auth challenges and pagination links cannot choose arbitrary origins/private addresses. Keep output redaction as an extra safeguard and render all labels, task actors, registry/image metadata and scanner summaries through escaped text templates.

<a id="v23-09-04"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-09-04 -->
**Spool integrity.** Separate server-written request and collector-written result directories enforce ownership; use bounded reads, no symlink following, atomic writes and collection IDs. Revalidate schemas, identity/generation, sizes and collection completeness at server ingestion. Do not accept URLs, raw API paths or raw commands in poll/visible-target requests. Spool content is presentation/input to executor checks, never trust, credential custody or mutation authority.

<a id="v23-09-05"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-09-05 -->
**Browser presentation.** The chart/details enhancement uses only self-hosted external scripts/styles, no inline handlers/styles, module JavaScript or host/registry HTML, under the existing strict CSP. Deep links are built from approved endpoint metadata and encoded identifiers with `noopener noreferrer`; release-note links need a reviewed HTTPS upstream/template and validated version. An untrusted URL or label cannot select a new dial target or rendered template.

<!-- Spec v2.3 (ADR 0009): v23-09-06 -->
**`net.facts` fields and limits.** The built-in read-only `net.facts` action (ADR 0009 D1, `internal/executions/actions/scripts/net_facts.sh`) returns one JSON document — `format` `net-facts-v1`, `phase` `done` — with one base64 section per fixed read-only command, in this order: `addr` (`ip -j addr`), `link` (`ip -j -d link`), `route` (`ip -j route`), `route6` (`ip -j -6 route`), `neigh` (`ip -j neigh`), `neigh6` (`ip -j -6 neigh`), `bridge_vlan` (`bridge -j vlan`), `lldp` (`lldpcli -f json show neighbors`), `sockets` (`ss -tinuaH`) and `conntrack` (`conntrack -L`). Each section is an object `{status, truncated, data}` where `data` is base64; the schema is strict, so unknown fields and any data after the document are rejected. Member names are matched exactly (byte for byte, after JSON unescaping), never case-insensitively, and must be ASCII: encoding/json matches member names to struct fields case-insensitively (Unicode simple case folding, so U+212A KELVIN SIGN matches `k` and U+017F LONG S matches `s`), so the check is defined so that it is at least as strict as the decoder whatever its folding: (1) a member name, in the document, in a section object or in any object of a parsed section, that contains a non-ASCII byte after JSON unescaping (any escaped or raw character above U+007F, including U+0130, U+0131, U+212A, U+017F and the U+FFFD that replaces invalid UTF-8) is rejected; (2) two members of one object whose names are equal under ASCII case folding (A–Z to a–z), a duplicate or a case variant, are rejected; (3) in the document and in every section object, a member that is not exactly one of the schema names is an unknown field, and nothing nests deeper than a section object. Inside an `ok` parsed JSON section (`addr`, `link`, `route`, `route6`, `neigh`, `neigh6`, `bridge_vlan`) rules (1) and (2) apply to every object at every level, and a member that equals a field name the parser reads under ASCII case folding without being spelled exactly like it (for example `IFNAME` or `Dst`; the field names are the exact `json` tags of the internal/netfacts parser structs, or the Go name of an untagged exported field) is refused; such a member, or nesting deeper than 64 arrays and objects, marks the section `invalid` (empty table, result incomplete); other unknown ASCII members are ignored. Real `ip -j` and `bridge -j` output uses ASCII member names only. Tests check the rule against encoding/json itself (decoding each candidate name into structs with the schema and parser field names), not against a model of its folding. The key check runs before the document is decoded into the schema, so the decoder never reports a host-supplied member name; rejection errors quote at most 64 bytes of a host-supplied member name or `format`/`phase` value, and every `ErrInvalidResult` detail is capped at 256 bytes. The check is one linear, bounded pass over the at most 1 MiB document and each section.
- **Size limits.** Each section's decoded data is at most 256 KiB; all sections together at most 720 KiB; the raw document at most 1 MiB (the executor result limit), so the base64 document always fits. A section cut at its cap is `truncated: true`. Only `ok` sections spend the budget, and each command keeps at most min(256 KiB, remaining total budget) bytes, so a section whose output exceeds the rest of the 720 KiB budget is cut at the remaining budget (status `ok`, `truncated: true`) even when that is below 256 KiB. Once the budget is spent, the remaining commands do not run and their sections are `skipped` (`truncated: true`, no data); the tool check comes first, so a section whose tool is not installed stays `absent` even after the budget is spent.
- **Section statuses.** `ok` (the command ran and exited 0; `data` is its stdout), `absent` (the tool is not installed; no data), `failed` (the command exited non-zero, e.g. `conntrack` without `CAP_NET_ADMIN`; no data), `skipped` (the total budget was spent; `truncated: true`, no data) and `unavailable` (an IPv6 section whose command failed because the host has IPv6 disabled, `ipv6.disable=1`, "Address family not supported"; no data). Only `route6` and `neigh6` may be `unavailable`; any other `ip -6` failure stays `failed`. `absent`, `failed` and `unavailable` carry no data and are not truncated.
- **Rejected results.** A contract violation rejects the whole result (`ErrInvalidResult`): nothing from it is used and it is not presented as a partial or `invalid` snapshot. This applies when the raw document exceeds 1 MiB, is not one strict JSON object (unknown field, a duplicate or case-variant member, data after the document), or has a `format` other than `net-facts-v1` or a `phase` other than `done`; when a section is missing or lacks one of `status`, `truncated` and `data`; when a section's decoded data exceeds 256 KiB or all sections together exceed 720 KiB; when `data` is not strict standard padded base64 (any other byte, including CR or LF, is rejected); and when a status is unknown or disagrees with `data`/`truncated`: `absent`, `failed` or `unavailable` with data or `truncated: true`, `unavailable` on a section other than `route6` and `neigh6`, or `skipped` with data or without `truncated: true`.
- **`truncated` and `invalid`.** `truncated` is set when a section was cut at its cap or skipped. `invalid` is set when an `ok` section's data is rejected by its parser (for example JSON cut by truncation), when raw `lldp` or `conntrack` text is not valid UTF-8 or carries a character other than newline (U+000A), tab (U+0009) or a character Go's `unicode.IsPrint` accepts (letters, marks, numbers, punctuation, symbols and the ASCII space U+0020; so CR, other control and format characters such as U+200B or U+202E, non-ASCII spaces such as U+00A0, private-use and unassigned code points are refused), or when the `sockets` section carries a `users:((…))` column.
- **Incomplete.** A result is incomplete when any section is truncated, invalid or skipped, when a required section is absent or failed, or when a parsed table dropped entries; it must be presented as incomplete, never as an empty table. `bridge_vlan`, `lldp` and `conntrack` are optional: their absence or failure is not a loss of data. `unavailable` sections do not by themselves make the result incomplete, so a host with IPv6 disabled (both `route6` and `neigh6` `unavailable`) still yields a complete result.
- **`ss` without `-p`.** `net.facts` runs `ss -tinuaH` without `-p`, so process names are never collected (they need root and are off unless the admin installs the documented sudo rule, ADR 0009 Q3). `Sockets.Process` is always empty; a `sockets` section carrying a `users:((…))` column did not come from that command (a wrapped or replaced `ss`) and is refused as `invalid` with an empty table.
- **Unparsed sections.** `lldp` and `conntrack` have no parser yet and are kept as raw, bounded, untrusted bytes that are valid UTF-8 in which every character is newline, tab or accepted by `unicode.IsPrint` (the same rule as under `truncated` and `invalid`); a cut section drops a trailing incomplete UTF-8 sequence.

**Traffic map API.** This is the contract of the traffic map API handler (`internal/web/api/trafficmap`), served at `GET /api/v1/trafficmap?window=…&focus=<node id>` once nebula-server mounts it; mounting lands with the traffic map page (TM19), so the endpoint is not served yet. It returns the bounded traffic map model built from inventory and the traffic store (ADR 0009 D3).
- **Windows and retention.** Window names are `1h`, `24h`, `7d` and `21d`; the default is `24h`. The effective retention is the builder's `Limits.Retention` (zero means the default of 21 days; there is no admin setting for it yet), lowered to the traffic store's own retention when the store reports one, and must lie in 1 h–21 d. Only windows no longer than the effective retention are accepted and offered: the window list named in the 400 responses is clamped to it, and when `24h` exceeds it the default is the longest remaining window. An unknown window, or one longer than the effective retention (`ErrBadWindow`), is answered with HTTP 400 `window must be one of <accepted windows>`; a malformed query (an empty or repeated `window=`, an unknown parameter) gets a different HTTP 400, `query: <reason>; use window=<accepted windows> and focus=<node id>`.
- **`unmapped_flows`.** Counts selected flows that cannot form an edge: an end is no inventory node (for example an internet peer or another peer outside the inventory), both ends are the same node, or, in a focus view, neither end is the focused node. These flows are not a cap: they are not counted in `omitted` and do not set `truncated`. Only flows with an end on a node that the overview node cap left out (a valid, mapped node beyond the overview's node limit) are counted in `omitted.flows` instead; the focus view applies no node cap, so there `omitted.flows` stays 0. Nodes dropped earlier, while the inventory is read (beyond the inventory input cap, an invalid ID, or two nodes claiming one ID), and addresses dropped from a node (invalid, over `MaxAddrsPerNode`, or claimed by more than one node) are absent from the address-to-node map, so flows to or from them count in `unmapped_flows`, not `omitted.flows`; those drops themselves are counted in `omitted.nodes` and `omitted.addresses`. Any non-zero `omitted` counter sets `truncated`.
