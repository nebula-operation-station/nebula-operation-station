# SSH transport and host identity

The executor speaks SSH through Go `x/crypto/ssh`, never through the `ssh` binary, so every failure maps to one error class and host-key trust is decided in code.

**Endpoints.** A host has an ordered list of endpoints (for example LAN, VPN, management network), each with an optional port; the default is 22. The order is set by the admin and never changes because of temporary failures. The precheck is a TCP connect to the configured port; ICMP is only a hint.

| Failure | Behaviour |
| --- | --- |
| TCP timeout or refused | Try the next endpoint |
| SSH handshake failure before authentication | Try the next endpoint once |
| Host-key mismatch | Hard stop for this host, security event, notification |
| Authentication failure | Hard stop; no other endpoint is tried with the same key, which keeps fail2ban quiet and the problem visible |

**Host keys are pinned per host, not per address.** Every endpoint must present the pinned key. To keep negotiation deterministic, the client prefers `ssh-ed25519`, then ECDSA, then `rsa-sha2-512`, and after pinning it offers only the pinned key type for that host.

**Enrollment.** Connect, complete the handshake, show the fingerprint, and send credentials only after the admin confirms it. Bulk enrollment shows a table of address and fingerprint for confirmation. Three ways avoid blind trust (previously: two; the third added by ADR 0013): importing existing `known_hosts` lines, comparing with `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` run on the host console, or [paired enrollment](#v25-08-01) with an offer-salted pairing code. Re-pinning a changed key is a HIGH action with user verification.

**Privileges on the host.** Recommended: a dedicated `nebula` user with Nebula's key and NOPASSWD sudo, documented as effectively root. Also supported: unprivileged (read-only actions) and direct root. The enrollment helper writes the key with `from="<Nebula addresses>",no-agent-forwarding,no-port-forwarding,no-X11-forwarding` and the docs recommend adding Nebula's addresses to fail2ban `ignoreip` as IPs, not hostnames.

**Timeouts.** Connect 10 s, keepalive every 15 s, session dropped after 4 missed keepalives; action timeouts come from the module manifest.

**PVE remote identity.** The built-in HTTPS provider supplements SSH; it does not turn provider guests into enrolled SSH hosts. A remote is one cluster with ordered node API endpoints, or one standalone host with one API endpoint; VPN routing creates no extra remote, and standalone endpoint aliases are deferred. Assign immutable local `remote_id`; nodes use `(remote_id, node)`, guests `(remote_id, vmid)` plus QEMU/LXC kind and local generation. Intra-cluster moves preserve identity but change placement; cross-remote moves require explicit relinking. Keep deletion tombstones and compare available UUID, creation/config metadata and MACs to detect VMID reuse. Never inherit links, criticality or approvals across reuse; ambiguity suspends actions for review. The executor owns endpoints, pins, credential references, criticality and generations. Reject duplicate registration of the same trust identity under another remote ID; names and server copies cannot authenticate or lower risk.

**PVE TLS enrollment.** Pin the cluster CA's SHA-256 DER fingerprint as the exclusive root; verify every leaf's chain, validity and configured DNS/IP SAN. Standalone remotes pin the served leaf and still check validity/SAN. Never fall back to system roots or accept-any TLS. Custom/ACME proxy certificates need an explicitly compatible reviewed trust choice. Only the local admin CLI adds remotes: probe without credentials, display each endpoint/leaf/CA fingerprint, import a cluster CA from a trusted local file, compare out of band and require typed `yes` before storing trust or sending either token. Server-supplied CAs and unauthenticated API data cannot establish trust.

<a id="v23-08-03"></a>

**PVE transport failures and re-pin.** Admin-approved HTTPS origins normally use port 8006; disable redirects and environment proxies. Discovery never adds dial targets, and credentials never follow API URLs. Only connection failures/timeouts allow ordered read failover; authentication failure stops the request. Changed pin, invalid chain or SAN mismatch persistently blocks the whole remote, stops failover and emits an executor event and notification. Re-pin is an explicit admin operation with old/new fingerprints and HIGH user-verified approval; increment trust generation and revoke affected grants/permits. CA-preserving leaf renewal needs no re-pin. An uncertain mutation is reconciled, never repeated at another endpoint. Same-CA endpoint membership and exact supported certificate profiles remain [open questions](17-frozen-decisions.md).

**Paired enrollment (ADR 0013 D1, D3, D4; Q1, Q7 decided 2026-11-11).** The third way to avoid blind trust replaces the operator's eye comparison of fingerprints by a comparison the executor makes against a value the operator carried; it does not replace the approval.

- **Code.** The enrollment script on the host computes, and the executor recomputes, `digest = SHA-256("nos-enroll-pair-v1" ‖ 0x00 ‖ salt[32] ‖ ed25519 host key blob)`, where the salt is the offer's 256-bit salt and the blob is the SSH wire format of the public key. The first 120 bits `v` are split into two 60-bit halves `hi`, `lo`, each written as 12 Crockford base32 characters, followed by one Crockford check character for `v mod 37` (alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ*~$=U`): 25 characters, shown as `XXXXX-XXXXX-XXXXX-XXXXX-XXXXC`. The script never forms the 120-bit number (check value `((hi mod 37) · 10 + lo mod 37) mod 37`, since `2^60 mod 37 = 10`); shared test vectors bind script and Go code. This is SHA-256 plus an encoding, not new cryptography. The salt rules out precomputation against a known host key; grinding a second key with the same code needs ≈ 2^120 work, so an attacker who also knows the salt has ≈ 2^-70 success within the 15-minute offer at 10^12 keys/s.
- **ed25519 only.** The script reads the key sshd serves (`sshd -T` `hostkey` lines with an `ssh-ed25519` public half, falling back to `/etc/ssh/ssh_host_ed25519_key.pub`); a host without one gets no code and is pointed to the classic path. The probe offers **only** `ssh-ed25519` as host key algorithm, so a server cannot negotiate ECDSA or RSA instead; a server without an ed25519 host key fails the probe ("no ed25519 key"), which is not a mismatch. After the pin every connection restricts `HostKeyAlgorithms` to the pinned key's type, so a host that later presents only another key type fails the connection.
- **Submission and probe.** The operator types the code and picks the endpoint (an inventory endpoint or a script-printed address, validated as in [09-untrusted-host-data.md](09-untrusted-host-data.md#v25-09-01)). The executor rejects a malformed code before any probe (`enroll_code_rejected`, at most 3 per offer), probes the endpoint without sending a credential (at most 5 probes per offer), computes the code from the presented ed25519 key and the salt and compares in constant time. Probe failures (unreachable, timeout, no ed25519 key) are not counted as mismatches; the operator may pick another endpoint within the probe limit. A host that is already pinned or blocked gets no offer; re-pinning stays the approved re-pin flow above.
- **Match.** The executor proposes the paired enrollment permit (HIGH, user verification; [05-authentication.md](05-authentication.md#v25-05-01)) showing host, endpoint, SSH user, credential, full SHA-256 fingerprint and "matches the pairing code from the host". **Commit** re-probes the endpoint, pins only if the presented key is still the approved one, then tests a login when the keys are unlocked, exactly like the existing commit of **Enroll hosts**. The pin record carries source `paired`; the host gets no criticality record (it counts as HIGH until set on the executor host), as today.
- **Mismatch.** One well-formed code that does not match the presented key ends the offer (`failed`; no second submission): nothing is pinned, the NetBird setup key is revoked and a joined peer is handled as an orphan ([06-credentials.md](06-credentials.md#v25-06-05)), `enroll_code_mismatch` is audited with the presented fingerprint and endpoint, and a dashboard notice and notification are raised as for a host-key mismatch. The UI states that the endpoint is either a different machine or something is in between, and that a new offer is needed; a new offer has a new salt, so the (idempotent) script must run again.
- **Endpoint to add.** An endpoint that is not yet one of the host's inventory endpoints is bound in the permit as "endpoint to add" and appended to the host's endpoint list only after a successful commit, in the same step as the pin (`inventory_endpoint_added`, source `paired`); a failed, expired or revoked offer adds nothing. It never replaces or reorders existing endpoints, and every endpoint must still present the pinned key.
- **Trust anchor.** The code is as authentic as the operator's own session to the host where it is read: on the console or over an SSH session with an already trusted host key as strong as the fingerprint comparison; over a first SSH login with trust on first use only as strong as that login ([05-authentication.md](05-authentication.md#v25-05-03)).

**One-step enrollment script (ADR 0013 D1, D5, D7, D9).** The executor renders the one-step script from the same template as `nebula host enroll-script` (shared generator; the CLI output stays byte-identical for the same options). The `from=` addresses come only from executor-local configuration (enrollment source addresses), plus with NetBird the NOS machine's own NetBird address read from the NetBird API, never from the server or the browser; user name and credential reference are validated as for the CLI and the key line is re-encoded from the parsed key. The one-step additions are appended at the end: the optional NetBird join ([06-credentials.md](06-credentials.md#v25-06-04)), the pairing code and an address list (`ip -o addr show scope global`, plus the NetBird address) that is only a hint for the operator. Nothing is sent from the host to NOS; the operator is the only channel. The script is downloaded over the NOS TLS origin, hash-checked, then run, never `curl | sh` and never `-k`; the offer ID reaches `curl`/`wget` only on standard input, never in argv. Hosts whose `sh` lacks 64-bit arithmetic or that lack coreutils `sha256sum`/`base64` get a message pointing to the classic path. `nebula host enroll-script`, `nebula host probe/pin/test`, `known_hosts` import, bulk **Enroll hosts** (`ProposeEnroll`/`CommitEnroll` and their permits) and the ADR 0008 guest join are unchanged; hosts enrolled either way are indistinguishable afterwards except for the audit source (`paired` versus `probe`/`known_hosts`). Windows and BSD are out of scope (Q5).
