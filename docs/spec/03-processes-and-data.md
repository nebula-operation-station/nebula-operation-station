# Processes, data stores and what each may access

Each role runs under its own OS user, and filesystem permissions enforce the split. The split protects against a compromised web process; it does not protect against root or kernel compromise of the Nebula machine, and the documentation says so.

<a id="v23-03-01"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-03-01 -->
| Process | OS user | Holds and does | Never has |
| --- | --- | --- | --- |
| `nebula-server` | `nebula-server` | Web UI, inventory, IPAM, execution planning, read-grant triggers, audit view, read-only API, vulnerability agent API and findings store (ADR 0011; previously: read-only API only), notifications, anonymous approved public registry metadata | SSH keys, vault plaintext, vault master key, signer private keys, authority to execute |
| `nebula-executor` | `nebula-executor` | ssh-agent, vault, SSH sessions, host-key and PVE TLS trust, typed PVE/private registry HTTPS, read grants/budgets, permit and WebAuthn verification, artifact hash checks, signing of executor events | Any network listener; it only serves a Unix socket |
| `nebula-discovery` | `nebula-discovery` | One-shot Nmap runs with `CAP_NET_RAW`, results go to staging | Credentials, database access |
| `nebula-pve-collector` | `nebula-pve-collector` | Typed provider read scheduling over the executor socket, sanitized result spool | Credentials, database access, network access/listener, capabilities, mutation or approval methods |
| `nebula` CLI | an admin user | Vault unlock, hardened approval, backup, restore | Persistent state of its own |

<a id="v23-03-02"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-03-02 -->
**Executor socket.** `/run/nebula/executor.sock`, owner `nebula-executor`, group `nebula-rpc`, mode 0660. gRPC over the socket. On every connection the executor reads the peer UID via `SO_PEERCRED` and allows a fixed method set per UID: the server may propose/query work and relay browser assertions for executor verification; only the admin CLI may unlock or give hardened approval. The server may also lock and revoke read grants, since these remove capability. The `pve-collector` UID may call only provider metadata/read methods, never unlock, approve, propose mutations or reveal secrets. Group membership alone is not authorization.

**Data stores.**

<a id="v23-03-03"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-03-03 -->
| Path | Owner | Content |
| --- | --- | --- |
| `/var/lib/nebula/server/nebula.db` | `nebula-server` | Users, hosts, assets, networks, IP allocations, groups, tags, module metadata, execution metadata, audit, scheduler configuration, presentation copies of PVE inventory and links, normalized telemetry/backup/scan evidence, public registry cache, credential references (names and types only) |
| `/var/lib/nebula/server/artifacts/<sha256>` | `nebula-server` | Immutable, content-addressed scripts and manifests |
| `/var/lib/nebula/executor/executor.db` | `nebula-executor` | Host keys, trusted signers/artifact trust, WebAuthn public keys/counters, signed executor events, spent execution IDs, durable job intent/outcomes, authoritative PVE remote endpoints/pins/criticality/generations/tombstones, approved read grants and durable budget claims, encrypted vault master key and envelope-encrypted secrets |

<a id="v23-03-04"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-03-04 -->
The server and collector cannot read the executor database or key files. The executor receives artifact bytes over RPC and computes the hash itself; it never trusts a hash the server reports.

<a id="v23-03-05"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-03-05 -->
**Durable authority and volatile approval.** Approved read grants, their spent budgets and legacy schedule grants persist in `executor.db`; pending proposals, execution/batch approvals, derived permits, gate state, unlocked secrets and privileged sessions are memory-only. Every restart starts locked and revokes mutation authority; only still-valid read grants resume after explicit local unlock. Job intent/outcomes survive for observation and reconciliation, never redispatch authority. This reflects M0 decisions 15, 41 and 61, while adding the shared grant registry in [07-execution-model.md](07-execution-model.md).

<a id="v23-03-06"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-03-06 -->
**Collector authority lifecycle.** A fixed peercred UID method set is only permission to request typed reads; actual remote/method/target authority, minimum intervals, budgets and expiry come exclusively from the executor's standing read grant. Lock/restart pauses use; expiry, removal, re-pin, rotation or grant revocation stops affected reads. Record caller UID, grant and target, budget claims, denials and outcomes without secrets. The ADRs specify no independent expiry or provisioning/revocation protocol for the collector UID mapping; that remains an explicit [open question](17-frozen-decisions.md). No collector membership can outlive or widen its grant's execution authority.

<a id="v23-03-07"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-03-07 -->
**Observation storage and spool.** The server stores `pve_remotes`, `pve_nodes`, `pve_guests`, `pve_guest_configs`, `pve_interfaces`, `pve_snapshots`, `pve_backup_observations`, `pve_storages`, `pve_cluster_status`, `pve_tasks`, `pve_host_links` and `pve_staging`. Remote children carry `remote_id`, guests carry VMID/generation, and every dataset carries `observed_at`, source, collection generation and completeness/availability reason. Validate and commit each dataset atomically; partial polls never erase unseen guests, and only complete enumeration may tombstone them. Keep current inventory, 30 days of task/drift metadata and explicit link/tombstone history. Normalized metric/evidence records carry the same identity/incarnation/source fields; never raw output. Spool ownership and validation follow [09-untrusted-host-data.md](09-untrusted-host-data.md).

**Hermes as an external API client (ADR 0011 D1, D3, D5).** The Hermes agent runs on its own VM (`hermes`) outside NOS and is not a NOS process, user or role: it has no OS user on the Nebula machine, no socket access, no database access, no SSH keys, host credentials, vault or NOS secrets. It talks to `nebula-server` only through the vulnerability agent API ([13-notifications.md](13-notifications.md#v24-13-01)) with the one `hermes-vuln` token. It is the only component that fetches CVE feeds for the finding store; `nebula-server` and `nebula-executor` gain no feed egress (Q2, decided 2026-11-09: egress only from `hermes`, no proxy assumed and none that terminates TLS; the proxy part is most restrictive and the maintainer may revisit). Findings never reach the executor or the permit path. The documented exception is the operator-managed host-local Trivy database of P1-30, which never feeds the finding store.

**Vulnerability tables and retention (ADR 0011 D5, D6, D10; Q3, decided 2026-11-09).** `nebula.db` (owner `nebula-server`) adds the findings store (`vuln_findings`, `vuln_finding_history`, `vuln_held_closures`, `vuln_subject_watermarks`), run records (`vuln_runs`, `vuln_run_sources`, `vuln_run_batches`, `vuln_run_subjects`, `vuln_run_reported`, `vuln_run_rejected`), per-source high-water marks and their resets (`vuln_source_marks`, `vuln_mark_resets`), `vuln_store_state`, and the crown jewels (`crown_jewels`, `crown_jewel_history`). `executor.db` gains nothing. Feed data is never stored in NOS; only per-finding scores, basis sources and snapshot IDs (Hermes assertions kept for audit, not a trust anchor). Retention defaults: the rows with basis Q3 are decided as proposed (previously: open); rows marked *implementation choice* are not ADR 0011 decisions and record what the merged code does:

| Data | Kept | Basis |
| --- | --- | --- |

**Enrollment socket methods (ADR 0013 D1, D2, D8).** The executor socket keeps its fixed per-UID method sets ([v23-03-02](#v23-03-02)). The server UID may create an offer (`CreateEnrollOffer`), fetch the script for the download route (`FetchEnrollScript`), render the review view (`ShowEnrollScript`), fetch the browser download (`DownloadEnrollScript`), submit a pairing code (`SubmitPairingCode`), commit a paired enrollment and revoke an offer; the admin CLI UID may list and revoke offers and set the NetBird token. Show, browser download, code submission, browser approval and commit are accepted only for the web session that created the offer; which approval path counts in Standard and hardened mode is set in [05-authentication.md](05-authentication.md#v25-05-02). `ShowEnrollScript` never consumes the offer, never changes its state, never reads the setup key from the vault and never returns it (fixed placeholder `<netbird-setup-key-withheld>`; see Retention in [v25-03-04](#v25-03-04)); `DownloadEnrollScript` consumes the offer exactly like `FetchEnrollScript` and is refused, without consuming it, for an offer with NetBird. RPC names beyond those named in ADR 0013 and all messages are set by EN-08; the `pve-collector` and discovery UIDs get none of these methods.

**Enrollment data (ADR 0013 D2, D6).** `executor.db` (owner `nebula-executor`) adds an **offer store** (previously: no offer data). Per offer it holds: the SHA-256 of the offer ID (never the ID), the 256-bit salt (wiped at the final state), host ID, SSH user, credential reference, the binding to the creating web session, creation time and expiry, state, the SHA-256 of the rendered script (**never the script bytes**), download time, client and peer address of the download, the endpoint to add, the probe and rejected-code counters, **every render input** of the script, fixed when the offer is created (previously: not listed): the script options (sudo flag), the NetBird choice and ephemeral flag, the managed group, the `from=` addresses taken from the executor-local enrollment source addresses, the validated NOS NetBird address ([08-ssh-transport.md](08-ssh-transport.md#v25-08-02)), the setup-key expiry, Nebula's public key line as rendered, the script template version `EnrollScriptTemplateVersion` of the shared generator (previously: not stored), and for NetBird offers the NetBird management URL and the key-passing mode per supported NetBird client version (environment variable or key file, [06-credentials.md](06-credentials.md#v25-06-04)), both copied from executor-local configuration when the offer is created (previously: read from live configuration at render time); the SHA-256 of the placeholder variant, computed at creation for every offer ([v25-03-04](#v25-03-04) Retention; previously: not stored); and for NetBird offers the setup-key record (`none`, `pending` with key name, `created`; after an invalid create response a `created` record without vault reference or a `pending` record with a reconcile record: offer ID hash, requested key name, creation time window, managed group, and the name-mismatched marker when the create response carried another key name (previously: no marker), [09-untrusted-host-data.md](09-untrusted-host-data.md#v25-09-01)), the vault reference of the setup key, NetBird's key ID (an identifier, not a secret) and orphan NetBird peer records. The setup key itself exists at rest only envelope-encrypted in the vault ([06-credentials.md](06-credentials.md#v25-06-02)). Final offers stay as audit records without salt and setup key; the key ID is wiped only after a successful revoke or the key's expiry. `nebula.db` stores no offer ID, salt, script or setup key; the server keeps the inventory host and its endpoints ([12-inventory.md](12-inventory.md#v25-12-01)) and receives audit records without secret values. The exact schema is set by EN-05.

**Render-input format (ADR 0013 D5).** Every stored render input that reaches the root-run script has a format rule and a quoting rule (previously: only the setup key and the `from=` addresses had one). The executor checks each value when the offer is created (before anything is stored) and again at every render; a value that fails is a render error and never reaches the script bytes (a download is refused with the uniform refusal and moves the offer to `failed`, "Show script" refuses only that request). Every value placed into the script as text appears only inside one single-quoted shell literal, and every format below excludes `'`, so no escaping is ever applied; no value is rendered unquoted, inside double quotes on its own, in a here-document or in a comment except where named.

| Render input | Format (checked at creation and at render) | Placed in the script |
| --- | --- | --- |
| Sudo flag, NetBird choice, ephemeral flag | boolean | only selects fixed template text; never rendered as a value |
| SSH user | `^[a-z_][a-z0-9_-]{0,31}$`, not `root` (as `nebula host enroll-script`) | single-quoted literal |
| Credential reference | `^[a-z0-9][a-z0-9_-]{0,63}$` (as `nebula host enroll-script`) | only in a comment line |
| `from=` addresses and NOS NetBird address | each one IP address or CIDR range parsed with `net/netip`, no zone ID, re-encoded in canonical form; the NetBird address as in [08-ssh-transport.md](08-ssh-transport.md#v25-08-02) | joined with `,` inside `from="…"` of the key line, which is one single-quoted literal |
| Nebula's public key line | `ssh-ed25519` and the base64 key, re-encoded from the parsed key | inside the same single-quoted key line |
| Offer salt (read at render, not a configuration copy) | 32 bytes, rendered as exactly 64 lowercase hex characters `0-9a-f` | single-quoted literal; the script computes the pairing code from it on the host ([08-ssh-transport.md](08-ssh-transport.md#v25-08-01)), the code itself and its alphabets are fixed template text, not render inputs |
| Setup-key expiry | RFC 3339 UTC timestamp `YYYY-MM-DDTHH:MM:SSZ` | at most in a comment line |
| Managed group, offer ID hash, key ID | — | never enter the script |
| NetBird management URL | at most `NetBirdMgmtURLMaxLen` = 256 bytes of ASCII, parsed with `net/url`; scheme exactly `https`; host a DNS name of LDH labels or an IP literal (IPv6 in brackets, no zone ID); optional port 1–65535; optional path of `A-Za-z0-9-._~/` only; no userinfo, query, fragment, percent-encoding, whitespace, quote, `$`, backtick, backslash or control character; the value must equal its re-encoded form | single-quoted literal, passed to the NetBird client as one argument |
| Key-passing mode table | 1 to `NetBirdClientVersionsMax` = 16 entries; each a client version `MAJOR.MINOR.PATCH` (each part 1–5 decimal digits, no `v` prefix, no suffix) and a mode from the closed set `env`, `file` | each version as a single-quoted `case` pattern selecting one of two fixed template branches; the mode name never appears as text; any other client version stops the script before the join |
| NetBird setup key | as in [09-untrusted-host-data.md](09-untrusted-host-data.md#v25-09-01) | single-quoted literal in the download; the placeholder `<netbird-setup-key-withheld>`, also single-quoted, in "Show script" |
| Script template version | positive integer `EnrollScriptTemplateVersion` | does not enter the script bytes |

**Offer lifecycle (ADR 0013 D2, D3; Q2, Q7 decided 2026-11-11).**

- **Offer ID.** At least 128 random bits from `crypto/rand` (recommended 160 bits, 32 characters of lowercase RFC 4648 base32 without padding), generated by the executor; it is a capability for one download. Stored only as SHA-256, logged only as the first 8 hex characters of that hash.
- **States.** `open` → `downloaded` → `pairing_proposed` → `enrolled`; an offer with NetBird starts in `awaiting_approval` and moves to `open` only after its NetBird offer permit is approved and the setup key is recorded. From any non-final state → `expired`, `revoked` or `failed`. Final states (`enrolled`, `expired`, `revoked`, `failed`) never return to `open`. Every state change is one atomic compare-and-set on the offer row (expected old state → new state); a transition whose expected state no longer holds fails and changes nothing.
- **Expiry.** 15 minutes in total from creation for download and code submission (a named constant; no separate window after the download). An approval started before expiry may finish within the permit's own lifetime; a commit after the permit expired fails.
- **Single use.** The first successful download moves the offer to `downloaded`; a second download gets the uniform refusal. One well-formed code submission is accepted per offer; one mismatch ends the offer ([08-ssh-transport.md](08-ssh-transport.md#v25-08-01)). A probe failure (unreachable, timeout, no ed25519 key) does **not** use up the submission: the submitted code stays fixed and the operator may retry it against another (or the same) endpoint within the 5-probe limit. The submission is used up only by the first probe that completes the comparison (match → `pairing_proposed`, mismatch → `failed`). When the probe limit is reached without a completed comparison, further probes are refused and the offer stays as it is until it expires or is revoked.
- **Creation refused** for a host that is already pinned or blocked (re-pinning stays the approved re-pin flow), when a limit below is reached, and without an open privileged session.
- **Revocation.** The operator revokes in the UI (any session of the user), the admin with `nebula host offer-revoke`, in every non-final state including `awaiting_approval`. Revoking also revokes the NetBird setup key unconditionally ([06-credentials.md](06-credentials.md#v25-06-03)).
- **Retention.** The executor renders the script on demand from the render inputs stored in the offer row ([v25-03-03](#v25-03-03)) and the salt, never from live executor configuration, so a configuration change after creation does not change an offer's script. The stored SHA-256 is computed over the **full** render and is the hash of the downloaded script: for an offer without NetBird when it is created, for a NetBird offer in the compare-and-set that records the validated setup key and moves it to `open` ([06-credentials.md](06-credentials.md#v25-06-02)). A NetBird offer in `awaiting_approval` has no stored hash and cannot be downloaded.
  - **Placeholder hash** (previously: not stored, so "Show script" was not checkable). At creation the executor also renders the placeholder variant (setup-key line with `<netbird-setup-key-withheld>`; without NetBird there is no setup-key line and the placeholder variant equals the full render) and stores its SHA-256 in the offer row, for every offer including a NetBird offer in `awaiting_approval`. In the compare-and-set that records a validated setup key, the executor renders both variants from the same stored inputs and stores the full-render hash only if the placeholder variant matches the stored placeholder hash and the two renders differ in exactly the setup-key line; otherwise the key is handled like a key that could not be stored ([06-credentials.md](06-credentials.md#v25-06-02) step 3) and `enroll_script_hash_mismatch` is audited. So "apart from the setup-key line, Show bytes equal the download" is checked, not only claimed.
  - **Template version** (previously: not stored). Before any render, and for a NetBird offer before the approval step creates the setup key ([06-credentials.md](06-credentials.md#v25-06-02) step 1), the executor compares the offer's stored `EnrollScriptTemplateVersion` with its own; it never renders an offer with another template and never creates a setup key for one (previously: checked only at render, so a key was created first and then revoked). A difference at approval creates no key, moves the offer to `failed` and audits `enroll_script_template_changed`, before the `pending` write. On a difference (an executor upgrade within the offer's lifetime) a download is refused with the uniform refusal, the offer moves to `failed` and the executor audits `enroll_script_template_changed` (stored and current version; an operational event, not a security event), without a hash check, so a harmless upgrade never raises `enroll_script_hash_mismatch`; "Show script" refuses only that request and says the offer must be created again. The shared generator raises the constant on every change to the rendered bytes; a golden test fails if the bytes change without it.
  - **Download** (`FetchEnrollScript`, `DownloadEnrollScript`): renders the full script (for NetBird offers with the setup key read from the vault), checks the bytes against the stored SHA-256, hands them to the RPC response and overwrites its buffer. A hash difference refuses the request with the uniform refusal, moves the offer to `failed` and audits `enroll_script_hash_mismatch`.
  - **"Show script"** (`ShowEnrollScript`): renders the placeholder variant directly (the setup-key line carries `<netbird-setup-key-withheld>`); it never reads the setup key from the vault, checks the bytes against the stored **placeholder hash** (never against the download hash, which placeholder bytes cannot match; previously: no hash check) and never changes the offer's state. A placeholder-hash difference refuses only that request and audits `enroll_script_hash_mismatch` (variant `show`) at most once per offer: the offer row keeps a "show mismatch audited" flag and a mismatch counter, a later mismatch of the same offer only raises the counter, and the counter appears in `nebula host offers` and in the offer's final-state audit record (previously: one audit per request, so a reloading session could flood the audit log); the next download still runs its own check and audits its own mismatch. A render error refuses only that request (`400` with the UI's normal error page) and leaves the offer untouched; "Show script" can never move an offer to `failed`. The page shows the stored hash, labelled as the hash of the downloaded script. For a NetBird offer in `awaiting_approval` (no setup key, no stored hash yet) "Show script" is available and renders the same placeholder variant from the stored render inputs; the page shows **no** hash and says that the hash exists only after the NetBird offer permit is approved and the setup key is recorded (previously: unspecified).
  - No rendered script is written to the offer store, a temporary file, a cache or a log on the executor or the server; the server streams the RPC response without buffering it to disk.

**Audit (executor and server, no secret values):** `enroll_offer_created`, `enroll_offer_approved` (NetBird offers), `enroll_script_downloaded` (client address, peer address, whether the forwarded header was used), `enroll_script_hash_mismatch` (variant `download` or `show`), `enroll_script_template_changed`, `enroll_code_rejected`, `enroll_code_mismatch` (presented fingerprint and endpoint), `enroll_paired_proposed`, `host_enrolled` (source `paired`), `enroll_offer_expired`, `enroll_offer_revoked`, `inventory_endpoint_added` (source `paired`), `netbird_setup_key_pending`, `netbird_setup_key_created`, `netbird_setup_key_invalid` (failed check, key name prefix; [09](09-untrusted-host-data.md#v25-09-01)), `netbird_setup_key_reconciled`, `netbird_setup_key_unresolved`, `netbird_setup_key_revoked`, `netbird_setup_key_revoke_failed`, `netbird_setup_key_expired_unrevoked`, `netbird_peer_joined`, `netbird_peer_orphaned`, `netbird_peer_deleted`, `netbird_peer_kept`. Never the offer ID (only the 8-hex hash prefix), salt, setup key, token or script content.

<a id="v25-03-05"></a>
<!-- Spec revision (ADR 0013, EN-02): v25-03-05 -->
**Download endpoint (ADR 0013 D7, D8).** `GET /enroll/<offer-id>` is unauthenticated and outside the UI auth chain. The URL is built from the server's configured public origin (`https://<rp-id>`); plain HTTP is never offered. The server validates the ID syntax, determines the client address ([v25-03-06](#v25-03-06)), charges the per-client rate limit, calls `FetchEnrollScript` and streams the bytes.

- **`200`:** `Content-Type: text/plain; charset=utf-8`, `Content-Disposition: attachment`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `X-Accel-Buffering: no`.
- **Uniform refusal.** Unknown, expired, consumed, revoked, malformed, rate-limited, hash mismatch, and a trusted proxy's request without a usable forwarded header all get the same `404` body with the same headers (including CSP), so the endpoint is no oracle. The server does not log the path.
- **Reverse proxy.** For `/enroll/` and the UI's "Show script" and "Download in browser" routes the shipped reverse-proxy configuration and the guide require `proxy_buffering off`, `proxy_max_temp_file_size 0`, no proxy cache and no access log; the server sends `X-Accel-Buffering: no` on these responses. A proxy configured otherwise is an operator error the guide warns about.
- **"Show script"** is an authenticated UI route (creating session only) served as its own `text/plain` response with `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` and the same CSP; it does not consume the offer, may be called repeatedly and shows the setup-key placeholder; apart from that line its bytes equal the download. It never reads the setup key from the vault, is checked against the stored placeholder hash, not the download hash (previously: not hash-checked), and never fails the offer ([v25-03-04](#v25-03-04) Retention). **"Download in browser"** (authenticated, creating session only) sends the download headers above, consumes the offer like the download route, and is neither shown nor accepted for offers with NetBird.

**Client address and trusted proxies (ADR 0013 D7).** Two new server settings, validated at startup, both empty by default (previously: none): **trusted proxies** (single addresses only: bare, `/32` or `/128`; any other prefix fails startup) and **trusted proxy networks** (prefixes documented as "networks that contain reverse proxies and no clients", logged at startup with that statement). An entry that does not parse fails startup. "Trusted proxy" means an address in either setting.

- **Normalisation** (`net/netip`) before any comparison or use, the same for the TCP peer, every `X-Forwarded-For` entry and every configured entry: strip a port, strip an IPv6 zone ID, unmap an IPv4-mapped IPv6 address.
- **Untrusted peer.** `X-Forwarded-For` and `Forwarded` are ignored; the peer address is the client address.
- **Trusted peer.** Only `X-Forwarded-For` is read (`Forwarded` never); several header lines count as one comma-joined list. It is refused, checked in this order with the first failing check deciding, when it is missing, larger than 1 KiB combined, has more than 16 entries, contains any entry that does not normalise to an IP, or contains only trusted proxies. Otherwise it is walked from the right, skipping trusted proxies; the first untrusted entry is the client address. Entries left of it are client-supplied and ignored for the address but still count for the size, entry and syntax checks (never a partial parse).
- **Refusal without charge.** A refused forwarded header gets the uniform `404` on the download route and `400` with the UI's normal error page on the authenticated enrollment routes, with no state change: the executor is not called, the offer is not touched and **no** rate-limit bucket is charged (neither the proxy's nor any address from the header). The refusal is counted in a metric and logged without the path. There is no fallback to the proxy's address.
- **Rate limit.** 10 downloads per minute and 60 per hour per client address; IPv6 clients bucketed per /64 after normalisation. The limiter is charged on one path only, after the client address was determined without error. Buckets live in a bounded table (4096 buckets, named constant) with LRU eviction; a request is never refused because the table is full (eviction fails open for the evicted client; the limit is defence in depth behind ≥ 128-bit single-use IDs).
- **Same address for the whole flow.** The authenticated enrollment requests (create offer, NetBird offer approval, "Show script", browser download, code submission, approval, commit, revoke, orphan-peer decision) use the same function and pass client and peer address to the executor, so every audit record of the flow carries both. Other routes keep their current address handling until a separate decision.
- **Startup warning** when enrollment is enabled, no trusted proxy is configured and the listener is on loopback, a private address or a wildcard address (`0.0.0.0`, `::`): all clients then share the proxy's bucket. No warning for a public listener. The shipped reverse-proxy configuration overwrites (does not append) `X-Forwarded-For`; with an appending proxy the rules above still hold.

**Durable offer records and volatile approval (ADR 0013 D2, D6).** The offer row and its setup-key record are durable in `executor.db`, so expiry, revocation, setup-key revoke retries and reconcile survive a restart. This extends [v23-03-05](#v23-03-05) without changing it: pending proposals and permits, including the three enrollment permits ([05-authentication.md](05-authentication.md#v25-05-01)), and privileged sessions stay memory-only, and an offer carries no pin or execution authority of its own. Lock, restart or the end of the creating session does not resurrect the offer's session binding: only the creating session may submit, approve in the browser (Standard mode; hardened mode approves only with `nebula approve`, [05-authentication.md](05-authentication.md#v25-05-02)) and commit; other sessions (also of the same user) see the offer read-only and may revoke it. Setup-key revoke retries and `pending` reconciles resume after a restart from the stored records.
