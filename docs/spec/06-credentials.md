# Credentials: executor-owned agent and secret vault

SSH private keys stay in standard OpenSSH format with a passphrase on disk and are decrypted into the executor's in-process keyring on unlock, the same model as ssh-agent with keychain. The vault holds only what is not an SSH key: API tokens, provider credentials, secret runbook parameters.

<a id="release-root-custody"></a>
**Release root custody.** The SSH credentials described here authenticate to managed hosts. Offline release-signing roots are separate YubiKey-held Ed25519 keys under [spec 10](10-modules.md#release-signing): their signing secrets never enter executor storage/keyrings, the vault, CI or hosts. Only public root keys ship with Nebula. Root recovery uses a separately enrolled second YubiKey and encrypted offline non-resident key handle backups; it is not part of `nebula unlock` or instance backup/restore.

**SSH keys.**

- Stored under `/var/lib/nebula/executor/keys/` as OpenSSH private keys (bcrypt-pbkdf, the standard format). Users can bring existing keys.
- `nebula unlock` decrypts them into an in-process keyring (`x/crypto/ssh/agent`). No agent socket exists that another process could use.
- Default and recommendation: one dedicated key per Nebula instance, accepted on the hosts by a dedicated `nebula` user.
- Each host binds exactly one credential reference; the executor offers only that key (the `IdentitiesOnly` principle).
- Ephemeral keys can be uploaded for the current privileged session and are never written to disk.

**Vault.**

- Vault master key: 256 random bits, stored only encrypted.
- Unlock: passphrase → Argon2id (parameters stored with the vault, default 256 MiB, 3 passes) → key-encryption key → decrypts the master key.
- Each secret has its own data key; encryption is XChaCha20-Poly1305 with the secret's ID and version as associated data, so encrypted blobs cannot be swapped between records.
- Passphrase: at least 32 random characters from a password manager. Never stored, logged, backed up or sent to hosts.

<a id="v23-06-01"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-06-01 -->
**One unlock.** The recommended setup uses the same generated passphrase for the vault and the SSH key. `nebula unlock` asks once, tries it on both and asks again only if one fails. Lock wipes unlocked execution keys/secrets, pauses read grants and cancels queued dispatch; restart starts locked. A local unlock resumes still-valid approved read leases without a privileged session; expiry keeps advancing while paused. Web unlock is opt-in and labelled as weaker, because a compromised server could capture the passphrase. **CLI unlock is the default and recommended mode.**

**I1 unlock refusal and `nebula integrity ack` (ADR 0015 D4, Q4).** While an I1 integrity finding is open because a covered NOS binary, systemd unit, built-in module file or root key differs from the admitted signed `installed-files.json` ([10-modules.md](10-modules.md#v26-10-01)), a covered file is missing, or an unlisted executable appears under `/usr/bin/nebula*`, the executor refuses `nebula unlock` and all mutation and read-grant dispatch (previously: no integrity condition blocked unlock). The finding is critical and notified. The system stays locked; nothing is deleted, restored or rolled back. Only the executor-local CLI clears it: `nebula integrity ack <finding>`, run as the admin UID and audited, after reinstalling or after accepting a new signed release; there is no browser path. Not locking: a configuration file that differs from the approved D3 baseline is a high finding with notification, resolved by approving a new baseline ([05-authentication.md](05-authentication.md#v26-05-01)) or restoring the file; a changed web asset or template is a critical finding with notification, and the server refuses to serve that asset and shows a static "integrity failure" page instead of locking the whole system; an I1 check that could not run completely is an "integrity check incomplete" finding (high), never reported as clean. **Limit, stated in the docs.** The refusal only *withholds* authority and cannot help when the executor binary itself is the replaced one; the UI states next to every I1 result: "NOS checks cannot detect a root compromise of the NOS machine; see ADR 0015".

**Secret parameters at run time.** Passed over the SSH channel and, only if a script needs a file, written to `/run/nebula/<execution-id>/` (tmpfs, directory 0700, files 0600) and deleted right after use. Never in `jobs/`, results, state files, audit or logs. Output redaction of known secret values is an extra safeguard, not the main protection.

**Stated limit.** Go cannot reliably wipe memory. While unlocked, keys and secrets live in executor memory; the systemd unit disables core dumps and the docs recommend encrypted or no swap on the Nebula machine.

**PVE credential custody.** Use separate noninteractive PVE users per remote and purpose with expiring privilege-separated tokens (`privsep=1`); effective ACLs are the intersection of user and token rights. Both tokens remain envelope-encrypted in the executor vault in `executor.db`, decrypted only there. Phase 1 installs only the read token; phase 2's action token is optional until enabled. Neither the server nor collector receives a token, Docker config, password or authenticated bearer token. Reject `root@pam`, passwords, `Administrator` and `PVEVMAdmin`. PVE token expiry is additional to NOS grant/permit expiry; the ADRs do not prescribe its lifetime.

**PVE profile limits.** Profiles are feature-specific unions, never one all-extension role. Phase 2 initially enables only the baseline. Verify endpoint/parameter ACL checks for every supported PVE minor version before enabling an extension; unknown additional privileges keep it disabled. Pool membership changes cannot widen action scope. Neither default token includes console, guest exec/file access, permission administration, storage deletion or HA-configuration rights. PVE privileges are coarser than NOS operations (`VM.Snapshot` can permit deletion/rollback); the executor must enforce distinct typed actions and parameters. Missing PVE 8 agent or read-only backup visibility stays unavailable, never borrows action credentials.

<a id="v23-06-05"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-06-05 -->
**PVE local administration.** Only the authenticated admin UID on the executor host may manage `nebula pve remote add|rotate-token|remove|repin`. Enter tokens through a non-echoing terminal or stdin, never argv, environment, browser or server configuration. Metadata contains opaque references/versions only. Audit admin UID, remote, trust and credential version changes and resulting revocations; never record token values, headers, raw bodies, credential-bearing URLs or unnecessary token account identifiers. Probe and establish trust before any credential is sent, following [08-ssh-transport.md](08-ssh-transport.md).

<a id="v23-06-06"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-06-06 -->
**PVE rotation and removal.** Validate a separately created replacement token against pinned TLS and its permission profile, then change its credential version atomically. Revoke pending permits/read grants using the old version; reconcile running tasks read-only with the replacement, never redispatch. The admin revokes the old token in PVE after verification. Removal first disables the remote and revokes its authorizations, then removes NOS secrets; PVE-side revocation is also required. Keep nonsecret audit/tombstone history. Neither operation undoes accepted tasks. Lock/restart stops new authenticated reads and mutations until local unlock; stale observations remain visible. Re-pin increments trust generation and revokes affected authority.

<a id="v23-06-07"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-06-07 -->
**Private registry credentials.** Only the executor holds vault-encrypted private registry credentials, decrypts them after unlock and uses them for approved HTTPS registry/auth origins and typed repository/tag/platform scope. Metadata reads require a standing read grant with exact credential version, 7-day default/30-day maximum expiry, budgets and revocation/audit as in [07-execution-model.md](07-execution-model.md); they never authorize pulls. Lock or credential expiry pauses reads, and rotation invalidates old-version authority. Audit scope/version, approved origins, calls, denials and outcomes without secrets; return only sanitized metadata. Private-network origins need an explicit executor-side allowlist. Supported PAT/basic/bearer/OAuth/helper mechanisms, token lifetimes, realm approval and rotation/removal workflow remain [open questions](17-frozen-decisions.md); unsupported profiles stay unavailable. Private phase-2 pulls must be executor-mediated over authenticated SSH to the target engine, with no host Docker login file and no credentials leaving executor custody; their transfer/load profile needs review before enablement.

<a id="v23-06-08"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-06-08 -->
**Recovery and read authority.** Removing a WebAuthn credential or entering recovery pauses grants until local review and unlock. Read-grant revocation via UI/CLI blocks future claims without an assertion; already dispatched work may finish. Changing a key/pin, removing a target, rotating a credential, withdrawing artifact trust or raising effective risk blocks affected scope, with identity/version changes requiring a replacement approved grant. No secret-bearing action can enter a read lease.

**NetBird management token custody (ADR 0013 D6; Q3, decided 2026-11-11).** The optional NetBird join of one-step enrollment uses a management API token of a dedicated NetBird **service user**, stored envelope-encrypted in the executor vault (previously: no NetBird credential). Only the admin UID on the executor host sets it, with `nebula netbird token set` and non-echoing input; never argv, environment, server configuration or browser, like PVE tokens ([v23-06-05](#v23-06-05)). The executor uses it only for the typed calls in [02-architecture.md](02-architecture.md#v25-02-02), never through a generic proxy, and never puts it into errors, logs, audit or results. NetBird's role model may not offer a token that can only create setup keys, so the service user can also change policies and groups; this widening of executor authority (to the NetBird network) is accepted by the maintainer (Q3). Management URL, TLS trust and managed group name are executor-local configuration validated at startup and not settable over RPC; the management URL and the key-passing mode table are copied into each NetBird offer as render inputs and must meet the format rules of [03-processes-and-data.md](03-processes-and-data.md#v25-03-03) "Render-input format" at startup and again when an offer is created (a failing value hides the NetBird option and refuses NetBird offers; previously: "validated at startup" without a format). Without a token the NetBird option is hidden.

<a id="v25-06-02"></a>
<!-- Spec revision (ADR 0013, EN-02): v25-06-02 -->
**Per-offer setup keys (ADR 0013 D1, D6).** For each offer with NetBird the executor creates exactly one setup key, and **only after** the operator approved that offer's NetBird offer permit with the security key ([05-authentication.md](05-authentication.md#v25-05-01)); the server can neither trigger a creation without that approval nor receive more than one key per approval.

- **Key properties.** One-off (`usage_limit` 1); expiry ≤ 1 hour from creation (default: offer expiry plus 45 minutes, clamped to that 1-hour cap, so raising the offer lifetime (Q2) never lengthens a key beyond 1 hour); `auto_groups` exactly the configured managed group (default `nos-managed`); not ephemeral unless explicitly chosen; name `nos-offer-<first 8 hex of the offer ID hash>`.
- **Limits.** At most 2 non-final NetBird offers and at most 5 setup keys created per hour, on top of the general offer limits ([03-processes-and-data.md](03-processes-and-data.md#v25-03-04)).
- **Custody.** The setup key exists at rest only encrypted in the vault; the offer row holds the vault reference and NetBird's key ID. It is never in plaintext at rest on the executor or the server: not in the offer store, not as rendered script bytes (scripts are rendered on demand and only their hash is stored), not in a temporary file, cache or log. "Show script" renders the placeholder `<netbird-setup-key-withheld>` instead of the key, and the browser download is refused for NetBird offers. The plaintext exists in executor, server and reverse-proxy memory only while a download is rendered and streamed.
- **Creation order.** (1) On approval the executor first compares the offer's stored `EnrollScriptTemplateVersion` with its own ([03-processes-and-data.md](03-processes-and-data.md#v25-03-04) "Template version"); on a difference no key is created, the offer moves to `failed` and `enroll_script_template_changed` is audited (previously: checked only at render, after the key existed). Otherwise it moves the setup-key record `none` → `pending` and persists, in one atomic compare-and-set, the key name, the offer ID hash, the managed group and the creation time window (previously: key name and offer ID hash only, so a record whose create response was lost could be reconciled by name only), only if the offer is still `awaiting_approval` and not expired; otherwise no key is created (`netbird_setup_key_pending` only on success). The window runs from the executor time of this write minus `NetBirdKeyClockSkew` to that time plus `NetBirdCreateTimeout` plus `NetBirdKeyClockSkew` ([09-untrusted-host-data.md](09-untrusted-host-data.md#v25-09-01)). (2) Only then it calls create, at once and bounded by `NetBirdCreateTimeout` from the step-1 write; a call not completed by then is abandoned and handled as a call without a clear answer (step 5). Create is never called again for a record that is already `pending` (for example after a restart). (3) On success it first validates the returned setup key, key ID and key name as untrusted input ([09-untrusted-host-data.md](09-untrusted-host-data.md#v25-09-01)); a failing value fails the offer with `netbird_setup_key_invalid`; before any revoke attempt the executor, in one atomic write with the move to `failed`, stores the key ID when it passed its check (record `pending` → `created`, no vault reference, marked **unverified** and keeping the step-1 key name, window and group as its reconcile record) or otherwise leaves the record `pending` with its step-1 reconcile record (offer ID hash, requested key name, creation time window, managed group); in the same write it marks the record **name-mismatched** when the response decoded under its schema and carried a key name other than the requested one, the only case in which NetBird is known to have created a key that the stored name cannot find (previously: not recorded), and only then revokes or reconciles as stated there (previously: not validated; then: revoked by key ID without storing it; then: a key ID that passed dropped the reconcile data). **An unverified key ID** (the key ID passed, but the key name or the setup key failed) is never revoked or closed on the ID alone, because the rest of the response is known to be bad: the executor first reads the key by ID (typed get, response within `NetBirdKeyGetMaxBytes` and checked by the entry check of [09-untrusted-host-data.md](09-untrusted-host-data.md#v25-09-01) "NetBird setup-key list and get-by-ID responses"; previously: "checked like the list", with no limit of its own) and revokes it only if the returned key has exactly that ID, a name exactly equal to the record's stored requested key name (previously: only the NOS name prefix, so a bogus key ID could revoke another NOS-prefixed key) and is a candidate under step 5 (`usage_limit` 1, expiry ≤ 1 h after creation, `auto_groups` exactly the stored group, creation time inside the stored window, not revoked, not held by another offer's record); the record is closed only after that revoke succeeded. A `404`, an already revoked key, a key with any other name, a key that fails any property or a failing get never revokes and never closes the record: it is reconciled as in step 5 with the key ID treated as unknown. Only a valid response is stored: it stores the key in the vault and, in one atomic compare-and-set, moves the record `pending` → `created` (key ID, vault reference), stores the SHA-256 of the full render ([03-processes-and-data.md](03-processes-and-data.md#v25-03-04)) and moves the offer `awaiting_approval` → `open`. If that fails because the offer became final meanwhile, the vault cannot store the key (vault locked) or the render check of [03-processes-and-data.md](03-processes-and-data.md#v25-03-04) fails, the executor first stores the key ID in one atomic write (record `pending` → `created`, no vault reference) and moves the offer to `failed` if it is not final yet, and only then revokes the new key (previously: revoked at once without storing the key ID); if that write fails too, the record stays `pending` with its step-1 reconcile record and is reconciled by name (step 5; the response carried the requested name; previously: by name, else by window and group). (4) Revoke and expiry of an offer whose record is `pending` finalise the offer as usual and leave the record `pending`; "no key ID yet" never counts as "no key". (5) **Reconcile** (previously: by name only; then: by name, else by window and group excluding only key IDs held by other records, and for an invalid create response only; then: by window for every record, with only `pending` records counted for ambiguity; then: by window only for a name-mismatched record; now: by requested name only). After an executor restart, after a create call that timed out or failed without a clear "not created" answer, and for every `pending` record on a final offer, the executor moves a non-final offer with a `pending` record to `failed` and, once the record's window end has passed (so a create call still in flight is never reconciled), lists setup keys. The list response is untrusted provider data checked as in [09-untrusted-host-data.md](09-untrusted-host-data.md#v25-09-01) "NetBird setup-key list and get-by-ID responses" (previously: "checked like the create response", which named no list fields). **Order** (previously: unspecified): each reconcile pass first takes the complete key list and only then reads the snapshot of all setup-key records in one read transaction, and matches only against that snapshot. A key in the list was created by a create call that started before the list was taken, and every create call starts only after its `pending` write (step 1), so the record of every listed NOS key is in the snapshot and takes part in the exclusions below; a record written after the list was taken cannot own a listed key. **Bounded list** (implementation: EN-11; this spec text alone changes no code; amended 2026-11-11; previously: "within key, byte and page limits; a list that ends without the API's last-page indication is truncated", which named no indication, and before that: no limit stated): the NetBird setup-key list endpoint (`GET /api/setup-keys`) is not paginated: it takes no page parameter and returns every setup key of the account as one JSON array (as documented for NetBird's management API; EN-11 verifies this against the reference lab's management server and NetBird Cloud before coding and records the NetBird version in ADR 0013). A pass therefore sends exactly one list request (`NetBirdKeyListMaxPages` = 1, no follow-up request, no redirect followed) and the list is **complete** only if that one response has status `200`, a valid UTF-8 body of at most `NetBirdKeyListMaxBytes` that is a bare JSON array (no wrapping object, no pagination field), at most `NetBirdKeyListMaxKeys` entries, every entry passing the entry check of [09-untrusted-host-data.md](09-untrusted-host-data.md#v25-09-01) "NetBird setup-key list and get-by-ID responses" (exactly the fields `id`, `name`, `usage_limit`, `expires`, the creation time, `revoked` and `auto_groups`; every other field, `key` and `last_used` included, is ignored and never logged, stored or put into an error), and none of the pagination headers named there (`Link`, `X-Total-Count`, `X-Total-Pages`, `X-Total`, `X-Page`, `X-Per-Page`, `X-Next-Page`, `X-Next-Cursor`, `X-Pagination`; a closed list, previously: "`Link`, or any header naming a next page, cursor or total count"). Every other outcome is **truncated**: any other status, a transport error or timeout, a body over the byte limit (read to that limit plus one byte, never further), a body that is not valid UTF-8, not one syntactically valid JSON value with only whitespace after it, or not a bare JSON array, more entries than the key limit, one entry failing its entry check (the whole list is truncated, not just that entry dropped), or one of the named pagination headers; NOS never assumes that a list it could not read in full is complete and never asks for a further page. If NetBird adds pagination later, this rule changes only by a spec amendment that names the last-page indication; until then a paginated answer is truncated. The limits' values are in [03-processes-and-data.md](03-processes-and-data.md#v25-03-04). A truncated list matches nothing and is never read as "no candidate": no record is matched, revoked or closed from it, every unresolved record of that pass gets `netbird_setup_key_unresolved` (once per record; the record and the dashboard notice name exactly one truncation class, that of the earliest failing check in the order of [09-untrusted-host-data.md](09-untrusted-host-data.md#v25-09-01) "NetBird setup-key list and get-by-ID responses", from this closed list in that order: transport, status, pagination header, byte limit, body format (not valid UTF-8, a JSON syntax error anywhere in the body, data other than whitespace after the JSON value, not a bare array), key limit, entry check; never a value from the body; amended 2026-11-11; previously: "status, transport, byte limit, body format (not UTF-8, not a bare array), key limit, entry check or pagination header" in no defined order, and before that: no class named) and the pass is retried with the revoke backoff below, so the work per pass stays bounded by these limits. Every `pending` record carries its step-1 reconcile record, and so does an unverified `created` record that step 3 sends to reconcile, so every one is matched the same way. A record is **unresolved** while it is `pending` (including while its create call is in flight) or unverified `created`; it is resolved once a valid create response, a get by ID (step 3) or a reconcile match has confirmed its key ID:
  - **Candidates.** A listed key is a candidate only if all of these hold: a key ID that passes its check; a name with the NOS prefix `nos-offer-`; `usage_limit` 1; expiry no later than 1 hour after its creation time; `auto_groups` exactly the record's stored managed group; not revoked; creation time inside the record's stored window. Excluded are every key whose ID another offer's setup-key record holds and every key whose name equals another offer's stored key name, whatever that record's state (`pending` with a create call still in flight, `pending` after an invalid response, `created`, or closed but still held). So a key the operator created by hand (no NOS prefix or other properties), a key of another offer and an already revoked key are never candidates.
  - **Match** (amended 2026-11-11, fix round 3; previously: a record marked name-mismatched was also matched by window when no candidate had its name, so a foreign key could be the sole window candidate once that record's own key was gone). Only by the record's stored requested key name: exactly one candidate whose name equals it exactly is the match; several are ambiguous. There is no window match for any record, name-mismatched or not: a key found only by window may be one no local record knows (a second NOS instance or a restored `executor.db` on the same NetBird account and group, or an operator key that follows the naming), and such a key is never revoked automatically. A record marked name-mismatched in step 3 therefore never resolves by reconcile unless a key with its requested name exists; its mark only tells the operator that NetBird reported a key under another name. NOS revokes automatically only a key whose ID a valid create response returned (step 3), a key whose get by ID (step 3) or list entry (this step) carries exactly the record's requested name and every candidate property; every other case alerts.
  - **Result.** The match is recorded (`netbird_setup_key_reconciled`, key ID; record `pending` or unverified `created` → `created` with that key ID, no vault reference) and revoked like any final-state key ([v25-06-03](#v25-06-03)). Zero matches, several matches, a name-mismatched record without a name match or a truncated list revoke nothing (`nebula host offers` may show candidates in the record's window and group as hints for the operator, never as matches, and names a name-mismatched record as such): the record stays open, `netbird_setup_key_unresolved` is audited once, and the dashboard notice and `nebula host offers` ask the operator to check and revoke the key in NetBird by hand. "No key found" is never read as "no key created", so a record is never resolved by the absence of a key or by a revoked key. An open record is retried with the revoke backoff below, listed in `nebula host offers`, and closed only once the window end plus the key's maximum lifetime (1 hour) has passed, then with `netbird_setup_key_expired_unrevoked` (previously: closed silently when no key with the name existed).
  - **Residuals: revocation of a key no local record created** (named 2026-11-11; fix round 3 lists all of them; previously: only the 32-bit collision was named). These three are the only paths by which NOS can automatically revoke a setup key that this executor's offer did not create. R1 and R2 need a key in the same NetBird account with exactly the requested name, the same managed group, every candidate property and a creation time inside the record's window, so their effect is one revoked one-off key that expires within 1 hour anyway; R3 revokes whichever key the returned ID names, without a property check. Each NOS instance should therefore use its own NetBird account or managed group, and a copy of `executor.db` must never run next to the original.
    - **(R1) 32-bit key names.** The key name carries only the first 8 hex digits (32 bits) of the offer ID hash. If two offers of this executor collide, each excludes the other's key by name, so neither resolves by name: this fails safe (unresolved alert, operator revokes by hand, the key lives at most 1 hour). A key with a colliding name from outside this executor's records (a second NOS instance on the same NetBird account) is matched by name and revoked; the chance is about 2⁻³² per such pair of keys.
    - **(R2) The same name created elsewhere.** A key created with exactly this name by another party: a second executor running from a copy or restore of this `executor.db` that creates a key for the same offer, or a person or tool that copies the naming within the window. NOS cannot tell such a key from its own and revokes it.
    - **(R3) A wrong key ID in a valid create response.** A create response that passes every check of step 3 (including the requested name) is taken as NetBird's own answer; if the management server returned the ID of another key, that key is revoked. NOS takes the configured management server's answer about the key it just created as true; a lying management server already holds the whole NetBird network and is not defended against here.
    - Not a path any more: a window-only match (removed in fix round 3) and a get by ID of an unverified key ID whose key has another name (now refused, step 3).
  - **Residual: late create** (named 2026-11-11; previously: not named). Every match requires a creation time inside the stored window. If NetBird processes the create call later than `NetBirdKeyClockSkew` after the `NetBirdCreateTimeout` bound (a stalled request that the server still executes), the key never matches: this fails safe, the record raises `netbird_setup_key_unresolved` and is closed at its window end plus 1 hour with `netbird_setup_key_expired_unrevoked`, while that key can stay valid until its own expiry, at most 1 hour after its late creation, unless the operator revokes it by hand as the alert asks.

**Setup-key revocation at the final state (ADR 0013 D2, D6).** Whenever an offer becomes final (`enrolled`, `expired`, `revoked`, `failed`), the executor (1) wipes the setup-key secret from the vault, (2) calls revoke for the key ID **unconditionally**, without first asking whether the key was used, (3) on success audits `netbird_setup_key_revoked` and only then wipes the key ID, (4) on failure (API unreachable, timeout, non-success answer) audits `netbird_setup_key_revoke_failed` (key name prefix, error class, no secret), keeps the key ID, shows a dashboard notice, lists the key in `nebula host offers` and retries with bounded backoff (first after 1 minute, then at most every 5 minutes) until the revoke succeeds or the key's own expiry has passed; then it audits `netbird_setup_key_expired_unrevoked` and wipes the key ID. Retries resume after an executor restart from the stored key IDs. A `pending` record is part of this rule. So a live key always has either a successful revoke or an open, audited and visible retry or reconcile record.

**Setup key on the target host (ADR 0013 D1, D5, D6, D8).** The setup key reaches the host only inside the downloaded script, over TLS to the NOS origin with verification mandatory (never `-k`; `--cacert` where the host does not trust the proxy's CA). The UI command runs under `umask 077` in a fresh `mktemp -d` directory in the first writable of `/dev/shm` and `$XDG_RUNTIME_DIR`, removed by `trap` on exit, hang-up, interrupt and termination; the script itself also sets `umask 077`, writes the key only to a `0600` file under its own `0700` `mktemp -d` directory chosen by the same rule and removed by its own `trap` on `EXIT`, `HUP`, `INT` and `TERM`, and when run outside the documented command still removes its key file and, if it contained a setup key, itself. The key reaches the NetBird client **only** by environment variable or that key file, never as a command-line argument; for a client version that accepts neither, the NetBird option is not offered and the script stops before the join. The script installs the NetBird client from the official package repository with the repository signing-key fingerprint pinned in the template, joins with the management URL stored in the offer (previously: "the configured management URL") and waits at most 60 s for the NetBird address. Named residuals: `SIGKILL` or power loss can leave a `0700` file; without `/dev/shm` and `$XDG_RUNTIME_DIR` the disk-backed `$TMPDIR`/`/tmp` fallback can keep the key in freed blocks; `tmpfs` pages can reach swap. Each is bounded by one use, ≤ 1 h expiry and revocation at the final state. A host that cannot reach the NOS origin joins NetBird by hand first and then gets an offer without NetBird (Q9).

**NetBird peers: cross-check, orphans and deletion (ADR 0013 D6; Q8 decided 2026-11-11).** Before a NetBird endpoint is offered for code submission, the executor reads the peer list and requires exactly one peer that joined with this offer's setup key, in exactly the managed group; otherwise no NetBird endpoint is suggested and the operator is told why. Attribution uses the NetBird API if it can name the setup key a peer joined with; otherwise the time-window fallback: exactly one new peer in the managed group whose registration time lies between the offer's approval and the key's recorded use, with the key's use count 1; any other result attributes nothing. Which of the two applies is established against the real API before EN-12 and recorded in ADR 0013. When an offer whose key was used becomes `failed`, `expired` or `revoked`, the attributed peer is recorded as an **orphan peer** (`netbird_peer_orphaned`) and listed on the dashboard and in `nebula host offers` until the operator decides: **delete** (privileged session, typed delete call, `netbird_peer_deleted`; a peer attributed only by the time-window fallback additionally needs an approved NetBird peer delete permit) or **keep** (`netbird_peer_kept`; an ordinary peer, not pinned, not enrolled). The same rules apply to a rogue peer found by the cross-check. NOS never deletes a peer automatically; a peer it cannot attribute is reported as "unknown peer joined `nos-managed`" and not offered for deletion. NOS only reads NetBird policies and warns, next to the NetBird option, when the default `All` ↔ `All` policy is enabled, when an enabled rule has `All` as source or destination together with a group containing `nos` or `nos-managed` peers, when a rule is bidirectional, or when a rule lets `nos-managed` reach `nos` or other groups; it never creates or changes policies or groups.
