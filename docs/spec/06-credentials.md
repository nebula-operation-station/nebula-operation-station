# Credentials: executor-owned agent and secret vault

SSH private keys stay in standard OpenSSH format with a passphrase on disk and are decrypted into the executor's in-process keyring on unlock, the same model as ssh-agent with keychain. The vault holds only what is not an SSH key: API tokens, provider credentials, secret runbook parameters.

<a id="release-root-custody"></a>
**Release root custody.** The SSH credentials described here authenticate to managed hosts. Offline release-signing roots are separate YubiKey-held Ed25519 keys under [spec 10](10-modules.md#release-signing): their signing secrets never enter executor storage/keyrings, the vault, CI or hosts. Only public root keys ship with Nebula. Root recovery uses a separately enrolled second YubiKey and encrypted offline non-resident key handle backups; it is not part of `nebula unlock` or instance backup/restore.

**SSH keys.**

- Stored under `/var/lib/nebula/executor/keys/` as OpenSSH private keys (bcrypt-pbkdf, the standard format). Users can bring existing keys.
- `nebula unlock` decrypts them into an in-process keyring (`x/crypto/ssh/agent`). No agent socket exists that another process could use.
- Default and recommendation: one dedicated key per Nebula instance, accepted on the hosts by a dedicated `nebula` user.
- Each host binds exactly one credential reference; the executor offers only that key (the `IdentitiesOnly` principle).
- Ephemeral keys can be uploaded for the current privileged session and are never written to disk.

**Vault.**

- Vault master key: 256 random bits, stored only encrypted.
- Unlock: passphrase → Argon2id (parameters stored with the vault, default 256 MiB, 3 passes) → key-encryption key → decrypts the master key.
- Each secret has its own data key; encryption is XChaCha20-Poly1305 with the secret's ID and version as associated data, so encrypted blobs cannot be swapped between records.
- Passphrase: at least 32 random characters from a password manager. Never stored, logged, backed up or sent to hosts.

<a id="v23-06-01"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-06-01 -->
**One unlock.** The recommended setup uses the same generated passphrase for the vault and the SSH key. `nebula unlock` asks once, tries it on both and asks again only if one fails. Lock wipes unlocked execution keys/secrets, pauses read grants and cancels queued dispatch; restart starts locked. A local unlock resumes still-valid approved read leases without a privileged session; expiry keeps advancing while paused. Web unlock is opt-in and labelled as weaker, because a compromised server could capture the passphrase. **CLI unlock is the default and recommended mode.**

**Secret parameters at run time.** Passed over the SSH channel and, only if a script needs a file, written to `/run/nebula/<execution-id>/` (tmpfs, directory 0700, files 0600) and deleted right after use. Never in `jobs/`, results, state files, audit or logs. Output redaction of known secret values is an extra safeguard, not the main protection.

**Stated limit.** Go cannot reliably wipe memory. While unlocked, keys and secrets live in executor memory; the systemd unit disables core dumps and the docs recommend encrypted or no swap on the Nebula machine.

<a id="v23-06-02"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-06-02 -->
**PVE credential custody.** Use separate noninteractive PVE users per remote and purpose with expiring privilege-separated tokens (`privsep=1`); effective ACLs are the intersection of user and token rights. Both tokens remain envelope-encrypted in the executor vault in `executor.db`, decrypted only there. Phase 1 installs only the read token; phase 2's action token is optional until enabled. Neither the server nor collector receives a token, Docker config, password or authenticated bearer token. Reject `root@pam`, passwords, `Administrator` and `PVEVMAdmin`. PVE token expiry is additional to NOS grant/permit expiry; the ADRs do not prescribe its lifetime.

<a id="v23-06-04"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-06-04 -->
**PVE profile limits.** Profiles are feature-specific unions, never one all-extension role. Phase 2 initially enables only the baseline. Verify endpoint/parameter ACL checks for every supported PVE minor version before enabling an extension; unknown additional privileges keep it disabled. Pool membership changes cannot widen action scope. Neither default token includes console, guest exec/file access, permission administration, storage deletion or HA-configuration rights. PVE privileges are coarser than NOS operations (`VM.Snapshot` can permit deletion/rollback); the executor must enforce distinct typed actions and parameters. Missing PVE 8 agent or read-only backup visibility stays unavailable, never borrows action credentials.

<a id="v23-06-05"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-06-05 -->
**PVE local administration.** Only the authenticated admin UID on the executor host may manage `nebula pve remote add|rotate-token|remove|repin`. Enter tokens through a non-echoing terminal or stdin, never argv, environment, browser or server configuration. Metadata contains opaque references/versions only. Audit admin UID, remote, trust and credential version changes and resulting revocations; never record token values, headers, raw bodies, credential-bearing URLs or unnecessary token account identifiers. Probe and establish trust before any credential is sent, following [08-ssh-transport.md](08-ssh-transport.md).

<a id="v23-06-06"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-06-06 -->
**PVE rotation and removal.** Validate a separately created replacement token against pinned TLS and its permission profile, then change its credential version atomically. Revoke pending permits/read grants using the old version; reconcile running tasks read-only with the replacement, never redispatch. The admin revokes the old token in PVE after verification. Removal first disables the remote and revokes its authorizations, then removes NOS secrets; PVE-side revocation is also required. Keep nonsecret audit/tombstone history. Neither operation undoes accepted tasks. Lock/restart stops new authenticated reads and mutations until local unlock; stale observations remain visible. Re-pin increments trust generation and revokes affected authority.

<a id="v23-06-07"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-06-07 -->
**Private registry credentials.** Only the executor holds vault-encrypted private registry credentials, decrypts them after unlock and uses them for approved HTTPS registry/auth origins and typed repository/tag/platform scope. Metadata reads require a standing read grant with exact credential version, 7-day default/30-day maximum expiry, budgets and revocation/audit as in [07-execution-model.md](07-execution-model.md); they never authorize pulls. Lock or credential expiry pauses reads, and rotation invalidates old-version authority. Audit scope/version, approved origins, calls, denials and outcomes without secrets; return only sanitized metadata. Private-network origins need an explicit executor-side allowlist. Supported PAT/basic/bearer/OAuth/helper mechanisms, token lifetimes, realm approval and rotation/removal workflow remain [open questions](17-frozen-decisions.md); unsupported profiles stay unavailable. Private phase-2 pulls must be executor-mediated over authenticated SSH to the target engine, with no host Docker login file and no credentials leaving executor custody; their transfer/load profile needs review before enablement.

<a id="v23-06-08"></a>
<!-- Spec v2.3 (ADR 0006, ADR 0007): v23-06-08 -->
**Recovery and read authority.** Removing a WebAuthn credential or entering recovery pauses grants until local review and unlock. Read-grant revocation via UI/CLI blocks future claims without an assertion; already dispatched work may finish. Changing a key/pin, removing a target, rotating a credential, withdrawing artifact trust or raising effective risk blocks affected scope, with identity/version changes requiring a replacement approved grant. No secret-bearing action can enter a read lease.

**NetBird management token custody (ADR 0013 D6; Q3, decided 2026-11-11).** The optional NetBird join of one-step enrollment uses a management API token of a dedicated NetBird **service user**, stored envelope-encrypted in the executor vault (previously: no NetBird credential). Only the admin UID on the executor host sets it, with `nebula netbird token set` and non-echoing input; never argv, environment, server configuration or browser, like PVE tokens ([v23-06-05](#v23-06-05)). The executor uses it only for the typed calls in [02-architecture.md](02-architecture.md#v25-02-02), never through a generic proxy, and never puts it into errors, logs, audit or results. NetBird's role model may not offer a token that can only create setup keys, so the service user can also change policies and groups; this widening of executor authority (to the NetBird network) is accepted by the maintainer (Q3). Management URL, TLS trust and managed group name are executor-local configuration validated at startup and not settable over RPC; the management URL and the key-passing mode table are copied into each NetBird offer as render inputs and must meet the format rules of [03-processes-and-data.md](03-processes-and-data.md#v25-03-03) "Render-input format" at startup and again when an offer is created (a failing value hides the NetBird option and refuses NetBird offers; previously: "validated at startup" without a format). Without a token the NetBird option is hidden.

<a id="v25-06-02"></a>
<!-- Spec revision (ADR 0013, EN-02): v25-06-02 -->
**Per-offer setup keys (ADR 0013 D1, D6).** For each offer with NetBird the executor creates exactly one setup key, and **only after** the operator approved that offer's NetBird offer permit with the security key ([05-authentication.md](05-authentication.md#v25-05-01)); the server can neither trigger a creation without that approval nor receive more than one key per approval.

- **Key properties.** One-off (`usage_limit` 1); expiry ≤ 1 hour from creation (default: offer expiry plus 45 minutes, clamped to that 1-hour cap, so raising the offer lifetime (Q2) never lengthens a key beyond 1 hour); `auto_groups` exactly the configured managed group (default `nos-managed`); not ephemeral unless explicitly chosen; name `nos-offer-<first 8 hex of the offer ID hash>`.
- **Limits.** At most 2 non-final NetBird offers and at most 5 setup keys created per hour, on top of the general offer limits ([03-processes-and-data.md](03-processes-and-data.md#v25-03-04)).
- **Custody.** The setup key exists at rest only encrypted in the vault; the offer row holds the vault reference and NetBird's key ID. It is never in plaintext at rest on the executor or the server: not in the offer store, not as rendered script bytes (scripts are rendered on demand and only their hash is stored), not in a temporary file, cache or log. "Show script" renders the placeholder `<netbird-setup-key-withheld>` instead of the key, and the browser download is refused for NetBird offers. The plaintext exists in executor, server and reverse-proxy memory only while a download is rendered and streamed.
- **Creation order.** (1) On approval the executor moves the setup-key record `none` → `pending` and persists, in one atomic compare-and-set, the key name, the offer ID hash, the managed group and the creation time window (previously: key name and offer ID hash only, so a record whose create response was lost could be reconciled by name only), only if the offer is still `awaiting_approval` and not expired; otherwise no key is created (`netbird_setup_key_pending` only on success). The window runs from the executor time of this write minus `NetBirdKeyClockSkew` to that time plus `NetBirdCreateTimeout` plus `NetBirdKeyClockSkew` ([09-untrusted-host-data.md](09-untrusted-host-data.md#v25-09-01)). (2) Only then it calls create, at once and bounded by `NetBirdCreateTimeout` from the step-1 write; a call not completed by then is abandoned and handled as a call without a clear answer (step 5). Create is never called again for a record that is already `pending` (for example after a restart). (3) On success it first validates the returned setup key, key ID and key name as untrusted input ([09-untrusted-host-data.md](09-untrusted-host-data.md#v25-09-01)); a failing value fails the offer with `netbird_setup_key_invalid`; before any revoke attempt the executor, in one atomic write with the move to `failed`, stores the key ID when it passed its check (record `pending` → `created`, no vault reference, marked **unverified** and keeping the step-1 key name, window and group as its reconcile record) or otherwise leaves the record `pending` with its step-1 reconcile record (offer ID hash, requested key name, creation time window, managed group), and only then revokes or reconciles as stated there (previously: not validated; then: revoked by key ID without storing it; then: a key ID that passed dropped the reconcile data). **An unverified key ID** (the key ID passed, but the key name or the setup key failed) is never revoked or closed on the ID alone, because the rest of the response is known to be bad: the executor first reads the key by ID (typed get, response checked like the list in step 5) and revokes it only if the returned key has exactly that ID and is a candidate under step 5 (NOS name prefix, `usage_limit` 1, expiry ≤ 1 h after creation, `auto_groups` exactly the stored group, creation time inside the stored window, not revoked, not held by another offer's record); the record is closed only after that revoke succeeded. A `404`, an already revoked key, a key that fails any property or a failing get never closes the record: it is reconciled as in step 5 with the key ID treated as unknown. Only a valid response is stored: it stores the key in the vault and, in one atomic compare-and-set, moves the record `pending` → `created` (key ID, vault reference), stores the SHA-256 of the full render ([03-processes-and-data.md](03-processes-and-data.md#v25-03-04)) and moves the offer `awaiting_approval` → `open`. If that fails because the offer became final meanwhile, the vault cannot store the key (vault locked) or the render check of [03-processes-and-data.md](03-processes-and-data.md#v25-03-04) fails, the executor first stores the key ID in one atomic write (record `pending` → `created`, no vault reference) and moves the offer to `failed` if it is not final yet, and only then revokes the new key (previously: revoked at once without storing the key ID); if that write fails too, the record stays `pending` with its step-1 reconcile record and is reconciled by name, else by window and group (step 5). (4) Revoke and expiry of an offer whose record is `pending` finalise the offer as usual and leave the record `pending`; "no key ID yet" never counts as "no key". (5) **Reconcile** (previously: by name only; then: by name, else by window and group excluding only key IDs held by other records, and for an invalid create response only). After an executor restart, after a create call that timed out or failed without a clear "not created" answer, and for every `pending` record on a final offer, the executor moves a non-final offer with a `pending` record to `failed` and, once the record's window end has passed (so a create call still in flight is never reconciled), lists setup keys. The list response is untrusted provider data checked like the create response ([09-untrusted-host-data.md](09-untrusted-host-data.md#v25-09-01)). Every `pending` record carries its step-1 reconcile record, so every one is matched the same way:
  - **Candidates.** A listed key is a candidate only if all of these hold: a key ID that passes its check; a name with the NOS prefix `nos-offer-`; `usage_limit` 1; expiry no later than 1 hour after its creation time; `auto_groups` exactly the record's stored managed group; not revoked; creation time inside the record's stored window. Excluded are every key whose ID another offer's setup-key record holds and every key whose name equals another offer's stored key name, whatever that record's state (`pending` with a create call still in flight, `pending` after an invalid response, `created`, or closed but still held). So a key the operator created by hand (no NOS prefix or other properties), a key of another offer and an already revoked key are never candidates.
  - **Match.** (a) By the record's stored key name: exactly one candidate with that name is the match; several are ambiguous. (b) Only if no candidate has that name, by window: exactly one candidate is the match, and only if no other offer's `pending` record that is not yet resolved has the same managed group and a window that overlaps this one (otherwise a window match is ambiguous, since the two cannot be told apart).
  - **Result.** The match is recorded (`netbird_setup_key_reconciled`, key ID; record `pending` → `created`, no vault reference) and revoked like any final-state key ([v25-06-03](#v25-06-03)). Zero matches, several matches or an ambiguous window revoke nothing: the record stays open, `netbird_setup_key_unresolved` is audited once, and the dashboard notice and `nebula host offers` ask the operator to check and revoke the key in NetBird by hand. "No key found" is never read as "no key created", so a record is never resolved by the absence of a key or by a revoked key. An open record is retried with the revoke backoff below, listed in `nebula host offers`, and closed only once the window end plus the key's maximum lifetime (1 hour) has passed, then with `netbird_setup_key_expired_unrevoked` (previously: closed silently when no key with the name existed).

<a id="v25-06-03"></a>
<!-- Spec revision (ADR 0013, EN-02): v25-06-03 -->
**Setup-key revocation at the final state (ADR 0013 D2, D6).** Whenever an offer becomes final (`enrolled`, `expired`, `revoked`, `failed`), the executor (1) wipes the setup-key secret from the vault, (2) calls revoke for the key ID **unconditionally**, without first asking whether the key was used, (3) on success audits `netbird_setup_key_revoked` and only then wipes the key ID, (4) on failure (API unreachable, timeout, non-success answer) audits `netbird_setup_key_revoke_failed` (key name prefix, error class, no secret), keeps the key ID, shows a dashboard notice, lists the key in `nebula host offers` and retries with bounded backoff (first after 1 minute, then at most every 5 minutes) until the revoke succeeds or the key's own expiry has passed; then it audits `netbird_setup_key_expired_unrevoked` and wipes the key ID. Retries resume after an executor restart from the stored key IDs. A `pending` record is part of this rule. So a live key always has either a successful revoke or an open, audited and visible retry or reconcile record.

<a id="v25-06-04"></a>
<!-- Spec revision (ADR 0013, EN-02): v25-06-04 -->
**Setup key on the target host (ADR 0013 D1, D5, D6, D8).** The setup key reaches the host only inside the downloaded script, over TLS to the NOS origin with verification mandatory (never `-k`; `--cacert` where the host does not trust the proxy's CA). The UI command runs under `umask 077` in a fresh `mktemp -d` directory in the first writable of `/dev/shm` and `$XDG_RUNTIME_DIR`, removed by `trap` on exit, hang-up, interrupt and termination; the script itself also sets `umask 077`, writes the key only to a `0600` file under its own `0700` `mktemp -d` directory chosen by the same rule and removed by its own `trap` on `EXIT`, `HUP`, `INT` and `TERM`, and when run outside the documented command still removes its key file and, if it contained a setup key, itself. The key reaches the NetBird client **only** by environment variable or that key file, never as a command-line argument; for a client version that accepts neither, the NetBird option is not offered and the script stops before the join. The script installs the NetBird client from the official package repository with the repository signing-key fingerprint pinned in the template, joins with the management URL stored in the offer (previously: "the configured management URL") and waits at most 60 s for the NetBird address. Named residuals: `SIGKILL` or power loss can leave a `0700` file; without `/dev/shm` and `$XDG_RUNTIME_DIR` the disk-backed `$TMPDIR`/`/tmp` fallback can keep the key in freed blocks; `tmpfs` pages can reach swap. Each is bounded by one use, ≤ 1 h expiry and revocation at the final state. A host that cannot reach the NOS origin joins NetBird by hand first and then gets an offer without NetBird (Q9).

**NetBird peers: cross-check, orphans and deletion (ADR 0013 D6; Q8 decided 2026-11-11).** Before a NetBird endpoint is offered for code submission, the executor reads the peer list and requires exactly one peer that joined with this offer's setup key, in exactly the managed group; otherwise no NetBird endpoint is suggested and the operator is told why. Attribution uses the NetBird API if it can name the setup key a peer joined with; otherwise the time-window fallback: exactly one new peer in the managed group whose registration time lies between the offer's approval and the key's recorded use, with the key's use count 1; any other result attributes nothing. Which of the two applies is established against the real API before EN-12 and recorded in ADR 0013. When an offer whose key was used becomes `failed`, `expired` or `revoked`, the attributed peer is recorded as an **orphan peer** (`netbird_peer_orphaned`) and listed on the dashboard and in `nebula host offers` until the operator decides: **delete** (privileged session, typed delete call, `netbird_peer_deleted`; a peer attributed only by the time-window fallback additionally needs an approved NetBird peer delete permit) or **keep** (`netbird_peer_kept`; an ordinary peer, not pinned, not enrolled). The same rules apply to a rogue peer found by the cross-check. NOS never deletes a peer automatically; a peer it cannot attribute is reported as "unknown peer joined `nos-managed`" and not offered for deletion. NOS only reads NetBird policies and warns, next to the NetBird option, when the default `All` ↔ `All` policy is enabled, when an enabled rule has `All` as source or destination together with a group containing `nos` or `nos-managed` peers, when a rule is bidirectional, or when a rule lets `nos-managed` reach `nos` or other groups; it never creates or changes policies or groups.
